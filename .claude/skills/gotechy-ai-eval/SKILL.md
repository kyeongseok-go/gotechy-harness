# gotechy-ai-eval: AI 기능을 숫자로 믿게 만드는 eval

LLM 기능은 같은 입력에도 답이 바뀌고, 실패할 수 있는 모양이 끝없이 많다. 그래서 "써 보니 괜찮다"는 판정이 아니다. 이 스킬은 성공 기준을 숫자로 정하고, 실제 실패를 읽어 분류하고, 그 실패를 잡는 골든셋과 채점기를 만들고, 채점기가 사람 판단과 맞는지 재고, 프롬프트와 모델을 바꿀 때마다 같은 케이스로 비교해 승격을 판정한다. 기준은 사람이 정하고 계산은 기계가 한다.

## 언제 쓰나, 쓰지 않나

- 쓴다: LLM을 쓰는 기능(챗봇, 요약, 분류, 추출, RAG, 에이전트)을 만들거나 출시하기 전. 프롬프트, 모델, 검색 설정, 도구를 바꾸기 전과 후. LLM judge 점수를 믿어도 되는지 물을 때. 운영에서 AI 오답, 사고가 났을 때(케이스로 바꾼다).
- 쓰지 않는다: AI가 없는 기능의 품질 목표와 테스트 전략(`gotechy-quality`), 위협 모델 전체와 보안 리뷰(`gotechy-security`), AI 관련 국내 법 요구(`gotechy-comply-kr`), 완료 게이트 판정(`gotechy-ship`), 운영 모니터링과 장애 대응(`gotechy-operate`).
- 규칙 코드(정규식, if문)로 풀리는 문제면 LLM을 쓰지 말라고 먼저 말한다. eval을 만들 일이 아니다.

## 산출물과 저장 위치 (없으면 만든다)

| 파일 | 내용 |
|---|---|
| `docs/evals/<기능>/criteria.md` | AI 적합성 판정, 성공 기준, 예산, 승격 규칙 (`references/templates/criteria.md` 양식) |
| `docs/evals/<기능>/error-analysis.md` | 트레이스 메모, 실패 분류표와 유형별 개수 |
| `docs/evals/<기능>/golden.jsonl` | 케이스 1줄 1개 (형식은 `references/golden-set.md`) |
| `docs/evals/<기능>/graders/<실패-유형>.md` | judge 프롬프트와 버전, 사람 라벨 일치도 기록 |
| `docs/evals/<기능>/results/YYYY-MM-DD-<변경>.md` | 실행 결과 (`references/templates/result.md` 양식) |
| 프롬프트 파일 | 프로젝트 관례를 따르고, 없으면 `prompts/<기능>.md`에 버전과 변경 이력을 두고 만든다 |

## 절차

0. **AI 적합성 판정.** 세 질문에 답을 적는다: 규칙 코드로 못 푸는가, 오답 한 번의 비용은 얼마인가(심하면 사람 승인 단계를 두거나 AI를 빼라), 출발점이 사용자 문제인가. 산출물: `criteria.md` 0절.
1. **성공 기준.** 차원마다 숫자 하나: 과업 정확도, 거절과 안전, 출력 형식, 일관성(k회 반복 성공), 지연 p95, 호출당 비용. "좋은 답변" 같은 말은 기준이 아니다. 각 기준은 구체적이고, 측정 가능하고, 지금 모델로 달성 가능하고, 사용자 목적과 관련 있어야 한다. 산출물: `criteria.md` 1절.
2. **오류 분석 먼저.** 실제 트레이스(출시 전이면 사용자 유형, 의도, 난이도를 조합한 입력으로 직접 돌린 결과)를 사람이 30개 이상 직접 읽고 통과, 실패와 자유 메모를 남긴다. 메모를 묶어 실패 분류표를 만들고 유형별 개수를 센다. 새 유형이 더는 나오지 않을 때까지(대개 100개 안팎) 계속한다. 분류표에 오른 실패는 대부분 프롬프트나 코드 수정으로 바로 고친다. 고친 뒤에도 남는 실패만 자동 채점기 후보가 된다. 산출물: `error-analysis.md`. 자세한 방법은 `references/golden-set.md`.
3. **골든셋.** 20개로 시작한다. 출처 우선순위는 운영 실패, 수동 테스트 절차, 상상 시나리오 순이다. 해야 할 행동과 하지 말아야 할 행동(거절, 도구 호출 안 하기)을 둘 다 넣는다. 케이스마다 `severity`, `split`(dev 또는 test)을 붙이고 test는 프롬프트 수정에 쓰지 않는다. 산출물: `golden.jsonl`.
4. **채점기.** 규칙으로 판정되는 것(스키마, 금지어, 숫자 일치, 도구 호출 여부)은 코드로 먼저 채점한다. 판단이 필요한 실패 유형만 LLM judge를 만들고, 유형 하나에 judge 하나, 통과와 실패 둘 중 하나로 판정하게 한다. judge는 사람 라벨과 비교해 TPR, TNR을 잰 뒤에만 쓴다. 산출물: `graders/`. 방법은 `references/graders.md`.
5. **싸게 먼저 돌리기.** 20개 케이스, 1회, 코드 채점기만으로 첫 실행을 한다. 비용 추정식으로 전체 실행 비용을 계산해 예산 안에서 judge와 반복 횟수를 늘린다. 0% 통과는 대개 과제나 채점기 결함이므로 트랜스크립트를 먼저 읽는다. 산출물: 첫 결과 파일. 방법은 `references/run-and-compare.md`.
6. **Δ 측정과 승격 판정.** 기준 버전과 후보 버전을 같은 케이스, 같은 반복 횟수로 돌려 케이스별 차이와 표준오차를 낸다. critical 100% 통과, 회귀 스위트에서 새 실패 0, 개선 주장은 Δ가 짝지은 표준오차의 2배를 넘을 때만 한다. 산출물: 결과 파일의 판정 줄(승격, 보류, 차이 없음).
7. **가드레일 eval.** OWASP LLM Top 10 2025 가운데 해당 항목마다 케이스를 넣는다(프롬프트 인젝션, 민감 정보 노출, 출력 처리, 과도한 권한, 시스템 프롬프트 유출, 잘못된 정보, 무제한 소비). 고위험 행동(삭제, 결제, 발송)은 프롬프트 문장이 아니라 코드의 승인 단계로 막고, 그 단계가 동작하는지 케이스로 확인한다. 산출물: 가드레일 표와 `security` 태그 케이스. 자세한 것은 `references/guardrails-and-ops.md`.
8. **운영 연결.** 호출마다 모델, 프롬프트 버전, 토큰, 지연, 비용, 실패, 폴백을 로그로 남기게 하고, 운영 실패를 7일 안에 케이스로 옮기는 규칙과 주 1회 트레이스 읽기를 `criteria.md`에 적는다. capability 셋이 포화되면 회귀 스위트로 옮기고 새 난제를 넣는다. 산출물: `criteria.md` 운영 절.
9. **보고.** 세 줄: 성공 기준 대비 현재 값, 승격 판정, 남은 위험. 위임 작업의 보고는 `owner-protocol` 스킬의 HANDOFF 형식을 따른다.

`--run`일 때는 0~4단계를 건너뛰고 5~6단계만 실행해 결과 파일을 추가한다.

순서에 대한 두 권고를 함께 쓴다. Anthropic, OpenAI는 기능보다 eval을 먼저 만드는 eval 주도 개발을 권하고, Hamel Husain과 Shreya Shankar는 그 방식에 대체로 반대하며 오류 분석부터 하라고 한다. 그래서 이 스킬은 성공 기준과 critical 케이스 몇 개는 먼저 쓰고, 실패 유형별 채점기는 오류 분석에서 찾은 실패에만 만든다.

## 기준 요약 (전체와 등급 판정은 `references/bar.md`)

1. 성공 기준이 정확도, 안전과 거절, 지연 p95, 호출당 비용 4개 이상의 차원에 숫자로 있다.
2. 사람이 직접 라벨한 트레이스 30개 이상과 실패 분류표가 채점기보다 먼저 있다.
3. 골든셋 20개 이상, 하지 말아야 할 행동 케이스가 전체의 20% 이상, test 분할이 20% 이상이다(셋 다 하네스 기본값).
4. 모든 LLM judge는 통과와 실패만 내고, 사람 라벨 대비 TPR 0.8 이상, TNR 0.8 이상(하네스 기본값)이 기록돼 있다.
5. 승격 판정은 같은 케이스에서 기준 버전과 비교한 Δ와 짝지은 표준오차로 한다. critical 케이스는 100% 통과한다.
6. 사용자 대면 critical 케이스는 3회(하네스 기본값) 반복 전부 통과(pass^3)로 판정한다.
7. 결과 파일마다 평가한 sha와 감시 경로(프롬프트와 AI 코드), 프롬프트 버전, 고정된 모델 ID, 케이스 수, 반복 횟수, 실행 비용이 있다. 평가한 sha 뒤로 감시 경로가 바뀌면 `gotechy-ship`이 출시를 막으므로 다시 돌린다.
8. 고위험 행동은 코드의 승인 단계로 막고, 프롬프트 인젝션 케이스가 골든셋에 있다.

## 완료 기준

- `criteria.md`, `error-analysis.md`, `golden.jsonl`, 채점기, 결과 파일 1개 이상이 있다.
- 실행 명령이 프로젝트 스크립트 목록에 있다(예: `npm run eval`, `uv run eval`). 실행할 수 없는 eval은 게이트 미통과다.
- 마지막 결과가 승격 규칙을 만족하거나, 못 한 항목이 `docs/exec-plans/tech-debt-tracker.md`(없으면 만든다)에 담당자와 함께 있다.
- `references/bar.md` 기준 등급(A~D)을 보고했다.

## 하지 않는 것

- 사람 라벨과 비교하지 않은 LLM judge 점수를 품질 증거로 쓰지 않는다.
- 1~10점 같은 척도 점수의 평균으로 "좋아졌다"고 말하지 않는다.
- 같은 케이스로 프롬프트를 고치고 같은 케이스로 성능을 보고하지 않는다. test 분할은 승격 판정 때만 연다.
- 20개 중 1~2개 차이를 개선이라고 부르지 않는다. 표준오차부터 계산한다.
- "절대 하지 마"를 프롬프트에 쓰는 것을 안전장치로 보고하지 않는다.
- 모델 별칭(최신을 가리키는 이름)으로 결과를 기록하지 않는다. 고정된 모델 ID를 쓴다.
- 운영 트레이스의 개인정보를 그대로 골든셋에 넣지 않는다. 가린 뒤 넣는다.

## 필요할 때 여는 파일

- `references/golden-set.md`: 오류 분석 방법, 케이스 형식, 크기, 분할, 과적합 막기.
- `references/graders.md`: 코드 채점기, judge 프롬프트 양식, TPR과 TNR 재는 법, pass@k와 pass^k.
- `references/run-and-compare.md`: 싸게 먼저 돌리기, 비용 추정식, Δ와 표준오차, 승격 규칙.
- `references/guardrails-and-ops.md`: OWASP LLM Top 10 2025 케이스, NIST 위험 목록, 예산, 로그 필드, 프롬프트 버전 관리.
- `references/bar.md`: 전체 체크리스트, 원천 표, 등급 판정, 흔한 실패.
- `references/lens.md`: 결과를 오너에게 설명할 때.
- `references/templates/criteria.md`, `references/templates/result.md`: 산출물 양식.

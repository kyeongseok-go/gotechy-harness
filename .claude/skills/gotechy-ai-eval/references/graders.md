# 채점기: 코드, LLM judge, 사람

언제 여는 파일인가: 절차 4단계에서 채점기를 고르고 만들 때, LLM judge를 믿어도 되는지 판정할 때, 반복 실행 지표(pass@k, pass^k)를 고를 때.

## 1. 고르는 순서

Anthropic 문서(https://platform.claude.com/docs/en/test-and-evaluate/develop-tests)는 가장 빠르고 믿을 만하고 확장되는 방법을 고르라고 하며 세 가지를 비교한다.

| 채점기 | 장점 | 약점 | 이 스킬에서 쓰는 곳 |
|---|---|---|---|
| 코드 | 가장 빠르고 믿을 만하며 확장이 쉽다 | 규칙으로 안 되는 판단은 못 한다 | 스키마, JSON 유효성, 금지어, 숫자와 ID 일치, 도구 호출 여부, 상태 변화 |
| LLM judge | 빠르고 유연하며 복잡한 판단이 된다 | 먼저 신뢰성을 확인해야 한다 | 분류표에서 판단이 필요한 실패 유형 하나씩 |
| 사람 | 가장 유연하고 질이 높다 | 느리고 비싸다 | judge 검증용 라벨, 주 1회 트레이스 읽기, 주관적 산출물 |

- 결과를 채점하고 경로는 채점하지 않는다. Anthropic은 정해진 도구 호출 순서를 요구하는 채점이 너무 경직돼, 설계자가 예상 못 한 올바른 풀이를 벌한다고 쓴다. 여러 단계 과제는 부분 점수를 둔다(`Demystifying evals for AI agents`).
- ROUGE, BLEU, 코사인 유사도, "도움됨 1~5점" 같은 범용 지표는 쓰지 않는다. Husain, Shankar FAQ와 OpenAI 평가 모범 사례 둘 다 범용 지표만 쓰는 것을 안티패턴으로 든다.

## 2. LLM judge 만드는 법

1. **실패 유형 하나에 judge 하나.** 여러 차원을 한 judge가 한꺼번에 채점하게 하지 않는다. Anthropic은 차원별로 분리된 judge를 권한다.
2. **통과, 실패 둘 중 하나.** 1~5점 척도는 이웃 점수의 차이가 주관적이고, 차이를 통계로 잡으려면 표본이 더 필요하며, 라벨러가 가운데로 몰린다(Husain, Shankar FAQ). 진척을 보고 싶으면 "기대 사실 5개 중 4개 포함"처럼 하위 항목마다 이진 판정을 따로 둔다.
3. **이유를 먼저, 판정은 나중.** 판정 전에 근거를 쓰게 하거나 thinking을 켠다. Anthropic과 OpenAI 둘 다 판정 전 추론이 judge 성능을 높인다고 쓴다.
4. **탈출구.** 판단할 정보가 없으면 `UNKNOWN`을 내게 한다(Anthropic 권장). `UNKNOWN`은 사람 검토로 보낸다.
5. **편향 통제.** 두 답을 비교하게 할 때는 순서를 바꿔 두 번 묻는다(위치 편향). 긴 답을 선호하는 편향이 있으므로 길이를 기준에 넣지 않는다(OpenAI 모범 사례).
6. **격리와 버전.** judge는 생성 모델 호출과 다른 호출로 돌리고, judge 프롬프트 파일에 버전을 붙인다. judge 프롬프트나 모델을 바꾸면 3절 검증을 다시 한다.

### judge 프롬프트 양식 (`graders/<실패-유형>.md`)

```markdown
---
grader: no-invented-policy
version: 3
judge_model: <고정된 모델 ID>
labels: graders/no-invented-policy.labels.jsonl
alignment: {tpr: 0.92, tnr: 0.88, n_test: 60, date: 2026-10-16}
---
너는 고객 상담 답변을 한 가지 기준으로만 판정한다.
기준: 답변이 <policy> 안에 없는 환불 조건, 기한, 금액을 사실처럼 말하면 FAIL이다.
<policy>...</policy>
<answer>...</answer>
먼저 <reason>에 근거를 쓰고, 마지막 줄에 PASS, FAIL, UNKNOWN 중 하나만 쓴다.
PASS 예: ...
FAIL 예: ...
```

## 3. judge를 믿어도 되는지 재는 법 (TPR, TNR)

Husain, Shankar FAQ의 방법을 따른다. 여기서 "양성"은 실패가 있다는 뜻이다.

1. 사람(품질 결정권자)이 실패 유형마다 통과, 실패 라벨을 단다. 최소 50개(하네스 기본값), 권장 100~200개. 실패와 통과가 둘 다 충분히 들어가게 한다.
2. 라벨을 셋으로 나눈다: 학습(judge 프롬프트 예시로 쓸 것), dev(judge를 고치며 비교할 것), test(마지막에 한 번만 볼 것).
3. dev에서 judge와 사람이 다른 사례를 읽고 judge 프롬프트를 고친다. 이걸 반복한다.
4. 다 고친 뒤 test에서 한 번 잰다.
   - TPR(재현율) = judge가 실패라고 한 진짜 실패 수 / 사람이 실패라고 한 수. 사람이 실패 10개를 찾았는데 judge가 8개를 잡으면 0.8.
   - TNR = judge가 통과라고 한 진짜 통과 수 / 사람이 통과라고 한 수.
5. 합격선(하네스 기본값): TPR 0.8 이상, TNR 0.8 이상. 놓치면 비싼 실패(critical)는 TPR 0.9 이상. 못 넘으면 judge 모델을 바꾸거나, 기준 문장을 쪼개거나, 그 유형은 사람이 채점한다.
6. test 결과가 dev보다 크게 나쁘면 judge가 dev에 과적합된 것이다. 새 라벨로 다시 잰다.
7. judge로 잰 통과율을 보고할 때는 그 judge의 TPR, TNR을 같이 적는다. TPR이 낮은 judge는 실패를 덜 잡아 통과율을 실제보다 높게 보이게 한다.

OpenAI 모범 사례도 "사람 피드백으로 자동 채점을 보정하라"를 원칙으로, "자동 지표를 사람 평가로 보정하지 않음"을 안티패턴으로 든다(https://developers.openai.com/api/docs/guides/evaluation-best-practices).

## 4. 사람 채점

- 품질 결정권자 1명을 정한다(FAQ의 "benevolent dictator"). 여러 명이 라벨하면 같은 트레이스를 따로 라벨해 Cohen's Kappa 같은 우연 보정 일치도를 재고, 갈리는 사례로 기준 문장을 고친다(Husain, Shankar FAQ).
- 주 1회 트레이스 20개 이상을 읽는다(하네스 기본값). Anthropic은 트랜스크립트 표본을 매주 읽으라고 하고, 채점기가 맞게 일하는지는 트랜스크립트를 읽어야만 안다고 쓴다.
- 0% 통과는 대개 망가진 과제나 채점기 신호다. 최신 모델에서 여러 번 돌려 0%면 과제 설명과 채점기를 먼저 의심한다(Anthropic).

## 5. 반복 실행 지표

같은 케이스도 실행마다 결과가 다르다(`Demystifying evals for AI agents`).

- pass@k: k번 중 1번이라도 성공할 확률. 한 번만 맞으면 되는 도구(후보 여러 개 중 고르기)에 쓴다.
- pass^k: k번 모두 성공할 확률. 매번 같은 품질을 기대하는 사용자 대면 기능에 쓴다. 1회 성공률이 75%면 3회 모두 성공은 약 42%다.
- 사용자 대면 critical 케이스는 k=3, pass^3으로 판정한다(하네스 기본값). 결과 파일에 k를 적는다.

# 싸게 먼저 돌리고, 같은 케이스로 비교한다

언제 여는 파일인가: 절차 5단계(첫 실행과 비용)와 6단계(Δ 측정과 승격 판정)를 할 때, "좋아진 거 맞아?"라는 질문을 받았을 때.

## 1. 싸게 먼저: 4계단

| 계단 | 무엇을 | 채점기 | 목적 |
|---|---|---|---|
| 1. 스모크 | dev 케이스 20개, 1회 | 코드만 | 러너, 형식, 과제 결함 확인. 0% 통과면 트랜스크립트부터 읽는다 |
| 2. judge 추가 | 실패 분류표의 유형이 붙은 케이스만 | 코드와 검증된 judge | judge 비용을 필요한 곳에만 쓴다 |
| 3. 반복 | critical 케이스, k=3 | 같음 | pass^3 판정 |
| 4. 전체 | dev 전체 k=3, 승격 판정 때만 test 분할 | 같음 | 승격 판정 |

- Anthropic 문서는 자동 채점이 가능한 문항을 많이 두는 쪽이, 사람이 채점한 소수 문항보다 낫다고 쓴다(https://platform.claude.com/docs/en/test-and-evaluate/develop-tests). 그래서 계단마다 코드 채점기를 먼저 늘린다.
- 계단 1을 통과하기 전에는 계단 2 이상을 돌리지 않는다. 형식 오류 때문에 judge 비용을 버리지 않는다.

## 2. 비용 추정식

```text
실행 비용 = 케이스 수 x 반복 k x (생성 입력 토큰 x 입력 단가 + 생성 출력 토큰 x 출력 단가)
         + 케이스 수 x 반복 k x judge 수 x (judge 입력 토큰 x 입력 단가 + judge 출력 토큰 x 출력 단가)
```

- 단가는 실행 날짜에 제공사 가격 페이지에서 확인해 결과 파일에 적는다. 이 파일에 단가를 박아 두지 않는다.
- `criteria.md`에 1회 실행 예산(예: 2달러)과 월 예산을 적는다. 추정이 예산을 넘으면 실행 전에 줄인다: normal 케이스는 k=1, judge는 사람 라벨 일치도가 유지되는 더 싼 모델로, 공통 프롬프트는 프롬프트 캐시.
- 추정치와 실제 비용을 결과 파일에 같이 적는다. 차이가 2배를 넘으면 토큰 추정을 고친다(하네스 기본값).

## 3. 노이즈를 먼저 안다

결과는 잡음이 섞인 측정값이다. Evan Miller의 `Adding Error Bars to Evals`(arXiv 2411.00640, 2024-11-01)는 평균의 표준오차 계산, 묶인 문항의 군집 표준오차, 재샘플링으로 분산 줄이기, 두 모델 비교 때 문항별 짝지은 차이로 추론하기, 검정력 분석을 권한다.

이진 점수(통과 1, 실패 0)의 통과율 표준오차는 대략 sqrt(p(1-p)/n)이다. 통과율 80%일 때:

| 케이스 수 n | 표준오차 | 대략 95% 구간 폭(±2 SE) |
|---|---|---|
| 20 | 8.9%p | ±17.9%p |
| 50 | 5.7%p | ±11.3%p |
| 100 | 4.0%p | ±8.0%p |
| 200 | 2.8%p | ±5.7%p |
| 400 | 2.0%p | ±4.0%p |

20개 셋은 "크게 망가졌나, 크게 좋아졌나"를 보는 데 쓴다. 5%p 차이를 주장하려면 수백 개 케이스나 짝지은 비교가 필요하다.

- 반복 k회를 돌려 케이스 점수를 k회 평균으로 쓰면 케이스 안의 흔들림이 줄어든다(같은 논문 3.1절).
- 분산을 줄이려고 temperature를 낮추지 않는다. 같은 논문 3.3절은 그 설정의 행동을 연구하려는 게 아니면 하지 말라고 한다. 운영과 같은 설정으로 잰다.

## 4. Δ 측정: 같은 케이스, 짝지은 차이

1. 기준 버전 A(지금 운영 중인 프롬프트와 모델)와 후보 버전 B를 같은 케이스, 같은 k, 같은 judge 버전, 같은 설정으로 돌린다. 바뀌는 것은 시험하려는 변수 하나뿐이다.
2. 케이스마다 점수 차이 d_i = s_B,i - s_A,i를 구한다(k회 평균 점수 사용).
3. Δ = d_i의 평균. 짝지은 표준오차 SE = sqrt(d_i의 분산 / n).
4. 판정: Δ > 2 x SE면 "개선", Δ < -2 x SE면 "악화", 그 사이면 "차이 없음". 문항이 묶음(같은 문서에서 나온 질문 여러 개)이면 군집 표준오차를 쓴다.
5. 숫자 하나로 끝내지 않는다. A에서 통과하고 B에서 실패한 케이스 목록을 결과 파일에 그대로 적고 트랜스크립트를 읽는다.

예: 20개 중 17개 통과에서 18개 통과로 바뀌었고 나머지는 그대로라면 Δ = 0.05, 짝지은 SE = 0.05다. Δ가 2 x SE(0.10)보다 작으므로 "차이 없음"이다.

## 5. 승격 규칙 (기본값, `criteria.md`에서 프로젝트가 조정)

모두 만족해야 승격한다.

1. critical 케이스 100% 통과(사용자 대면이면 pass^3).
2. 회귀 셋에서 A는 통과, B는 실패인 케이스 0개.
3. 개선을 주장하는 변경이면 dev와 test 둘 다 Δ > 2 x SE. 비용이나 지연을 줄이는 변경이면 Δ가 -2 x SE보다 크고(악화가 아님) 1, 2를 만족.
4. 호출당 비용과 지연 p95가 `criteria.md` 예산 안.
5. 결과 파일에 프롬프트 버전, 고정된 모델 ID, judge 버전, n, k, 실행 비용이 있다.

판정은 "승격", "보류(이유)", "차이 없음" 중 하나로 결과 파일 첫 줄에 쓴다.

## 6. 기능이 있을 때와 없을 때 비교

- 새 AI 기능이나 스킬이 정말 결과를 바꾸는지 보려면 같은 케이스를 기능 없이 한 번, 기능과 함께 한 번 돌려 Δ를 본다. Claude Code의 `claude plugin eval`은 플러그인을 켠 실행과 끈 실행의 점수 차이를 Δ로 보고한다(https://code.claude.com/docs/en/plugin-evals.md). 같은 생각을 자기 기능에 쓴다.
- 운영 트래픽이 충분하면 큰 변경은 A/B 테스트로 확인한다. Anthropic은 자동 eval은 출시 전과 CI의 첫 방어선, 운영 모니터링은 실제 분포 확인, A/B 테스트는 트래픽이 충분할 때의 큰 변경 확인으로 역할을 나눈다(`Demystifying evals for AI agents`).

## 7. 결과를 읽는 순서

1. 실행이 정상인가(오류, 시간 초과, 비용 초과 수).
2. critical 실패 목록과 트랜스크립트.
3. 새로 실패한 케이스 목록.
4. Δ와 SE.
5. 비용과 지연.
6. dev와 test 격차(10%p 넘으면 과적합 의심).

# 사고 대응

사고 모드에서 연다. 지금 사용자가 영향을 받고 있으면 이 파일의 1~5절만 순서대로 한다.

## 1. 선언 (1분)

Google SRE 책(Managing Incidents)의 기준이다. 하나라도 맞으면 사고로 선언한다.

- 사용자가 볼 수 있는 장애다.
- 혼자 못 고친다. 다른 사람이나 다른 팀(호스팅 지원 포함)이 필요하다.
- 집중해서 1시간을 봤는데 못 풀었다.

애매하면 선언한다. 일찍 선언하고 간단히 고쳐 닫는 편이, 몇 시간 뒤에 틀을 꺼내는 것보다 낫다.

### 심각도

PagerDuty Incident Response 문서의 5단계를 작은 서비스에 맞게 옮겼다. 두 등급 사이에서 망설이면 **높은 쪽**으로 정하고, 등급 논쟁은 포스트모템에서 한다.

| 등급 | 뜻 | 대응 |
|---|---|---|
| SEV-1 | 공개 공지가 필요한 치명 장애(전체 다운, 데이터 유출이나 손실) | 사고 대응 전체, 상태 공지 필수 |
| SEV-2 | 많은 사용자가 핵심 기능을 못 씀 | 사고 대응 전체, 상태 공지 필수 |
| SEV-3 | 일부 사용자 영향, 서비스 담당자가 바로 봐야 함 | 즉시 호출, 공지는 판단 |
| SEV-4 | 사용자는 쓸 수 있지만 조치가 필요함 | 업무 시간 처리 |
| SEV-5 | 겉모양 문제 | 이슈 등록 |

SEV-2 이상은 "중대 사고"다.

## 2. 역할 (2분)

| 역할 | 하는 일 | 1인 서비스에서 |
|---|---|---|
| 지휘(IC) | 전체 상태를 쥐고, 일을 나누고, 결정한다. 직접 고치지 않는다 | 사람 |
| 고치기(Ops) | 시스템을 바꾸는 유일한 사람. 지휘와 상의하며 고친다 | 사람(지휘와 겸할 때는 15분마다 손을 멈추고 지휘로 돌아온다) |
| 공지(Comms) | 사용자와 이해관계자에게 정해진 간격으로 알린다 | 에이전트가 초안, 사람이 승인하고 올림 |
| 기록(Scribe) | 타임라인, 결정, 실행한 명령을 기록한다 | 에이전트 |

- 시스템을 바꾸는 사람은 고치기 역할뿐이다. 여러 사람이 동시에 설정을 바꾸면 무엇이 효과였는지 모른다.
- 지휘를 넘길 때는 말로 분명히 넘기고, 받는 사람이 "제가 지휘합니다"라고 확인한 뒤에 떠난다.

## 3. 복구 먼저 (5~15분)

원인 분석은 나중이다. 먼저 사용자 영향을 멈춘다.

1. **직전 변경 확인.** 마지막 배포, 설정 변경, 플래그 변경 시각과 증상 시작 시각을 나란히 적는다. 10분 안에 붙어 있으면 그 변경을 되돌린다. 롤백 런북(`docs/operations/runbooks/rollback.md`)의 명령을 사용자에게 제시하고, 사용자가 실행하거나 실행을 지시한다.
2. **기능 플래그.** 새 기능이 플래그 뒤에 있으면 플래그를 끄는 것이 가장 빠른 롤백이다.
3. **데이터 문제(코드만 되돌릴 수 없음).** 쓰기 경로를 막고(읽기 전용 플래그), 백업이나 시점 복구 지점을 확인하고, 잃을 데이터 범위를 적은 뒤 복원 여부는 사용자가 정한다.
4. **외부 의존 장애.** 상대의 상태 페이지를 확인하고, 폴백이나 기능 축소로 버틴다. 오류 예산 정책의 "외부 원인" 예외에 해당하는지 기록한다.
5. **보안 사고 의심**(침입, 비밀 유출, 개인정보 노출): 증거를 지우지 않는다. 노출된 비밀을 폐기하고, `gotechy-security` 스킬로 조사를 넘기고, 신고 의무는 `gotechy-comply-kr` 스킬로 판단한다.

## 4. 공지

PagerDuty의 외부 공지 지침에서 가져온 간격이다.

| 시점 | 내용 |
|---|---|
| 선언 5분 안: 첫 공지 | 문제를 알고 조사 중이다. 범위는 최소로, 다음 공지 시각 |
| 첫 공지 5분 안: 범위 공지 | 사용자 영향, 영향받는 기능, 지역 |
| 처음 2시간: 20분마다 | 영향이나 범위의 변화, 복구가 시작됐는지, 다음 공지 시각 |
| 영향이 크게 바뀌면 | 간격과 무관하게 바로 |
| 2시간이 넘으면 | 간격을 늘릴 수 있다(첫 1시간 안에는 정하지 않는다). 다음 공지 시각은 계속 적는다 |
| 해결 | 완전 복구 확인, 데이터 손실이나 남은 손상(없으면 "없음"), 포스트모템 공개 여부 |

공지 문장 규칙:

- 사용자가 겪는 증상으로 쓴다("로그인이 안 됩니다"). 내부 용어("DB 커넥션 풀 고갈")는 쓰지 않는다.
- 확인되지 않은 원인을 쓰지 않는다. 남 탓(호스팅 회사, 외부 API)도 확인 전에는 쓰지 않는다.
- 내용 없는 공지("계속 조사 중")만 반복하지 않는다. 무엇을 해 봤고 다음에 무엇을 하는지 한 줄을 넣는다.
- 상태 페이지가 없으면 서비스 첫 화면 배너나 공식 SNS 계정 등 사용자가 실제로 보는 곳 한 곳을 정해 둔다.

첫 공지 예:

```
[조사 중] 10:42 KST부터 일부 사용자가 로그인할 수 없습니다. 원인을 조사하고 있으며 11:05까지 다음 소식을 올리겠습니다.
```

## 5. 기록

기록 역할은 아래 형식으로 쌓는다. 이것이 그대로 포스트모템의 타임라인이 된다.

```
YYYY-MM-DD HH:MM KST  [관찰] 오류율 12%, 결제 API만
YYYY-MM-DD HH:MM KST  [결정] 14:02 배포를 되돌린다 (지휘)
YYYY-MM-DD HH:MM KST  [실행] vercel rollback (사용자 실행)
YYYY-MM-DD HH:MM KST  [공지] 범위 공지 게시
```

## 6. 종료

- SLI가 SLO 수준으로 돌아온 뒤 30분 동안 다시 나빠지지 않으면 종료한다(하네스 기본값).
- 해결 공지를 올린다.
- 임시 조치(꺼 둔 플래그, 막아 둔 쓰기 경로, 늘린 자원)를 목록으로 적고 되돌릴 담당과 날짜를 정한다.
- 포스트모템 트리거에 해당하면 `references/postmortem.md`로 넘어간다.

# 렌즈: 운영 결과를 오너에게 설명하기

SLO, 알림, 사고, 포스트모템, 백업 결과를 오너(부모님과 AI 초심자도 읽는다)에게 설명할 때 연다.

## 대표 그림

- 오류 예산 막대: 4주 예산(분)을 가로 막대로 두고, 사고마다 깎인 만큼 칠한다. 남은 칸이 "아직 써도 되는 실수".
- 사고 타임라인: 가로축 시간에 감지, 선언, 첫 공지, 롤백, 복구를 점으로 찍고 사이 간격(분)을 적는다.
- 복원 리허설 기록표: 날짜, 걸린 시간, 목표(RTO) 선을 함께 그린 막대.

## 비유 후보

- 은행 번호표 대기 시간: "100명 중 99명은 5분 안에 창구에 간다"가 SLO다. 나머지 1명 몫이 오류 예산이고, 다 쓰면 새 서비스보다 창구 정비가 먼저다.
- 냉장고 정리와 유통기한: 백업은 냉동실에 넣어 둔 음식이다. 꺼내서 데워 먹어 봐야(복원 리허설) 먹을 수 있는 줄 안다.
- 지하철 안내 방송: 열차가 멈추면 원인을 다 알기 전에도 "지연 중, 10분 뒤 다시 안내"를 먼저 한다. 사고 공지가 그렇다.

## 꼭 풀어야 할 용어

| 용어 | 쉬운 설명 |
|---|---|
| SLI | 사용자가 겪은 일 중 "잘 된" 비율, 예: 2초 안에 뜬 화면 비율 |
| SLO | 그 비율의 목표, 예: 4주 동안 99.9% |
| 오류 예산 | 목표를 지키면서도 허용되는 실패의 양, 4주 99.9%면 약 40분 |
| burn rate | 오류 예산을 쓰는 속도, 1이면 기간 끝에 딱 다 쓴다 |
| 런북 | 장애 때 그대로 따라 하는 순서와 명령을 적은 문서 |
| 포스트모템 | 장애 뒤에 사람 탓 없이 원인과 재발 방지책을 적는 글 |
| RPO | 사고가 나면 최대 몇 분치 데이터를 잃어도 되나 |
| RTO | 멈춘 서비스를 최대 몇 분 안에 되살려야 하나 |
| 당번(on-call) | 정해진 시간 동안 알림을 받고 대응하는 사람 |

## 선택해 보기 후보

"밤에는 아무도 못 봐요. SLO를 99%(4주에 약 6시간 43분)로 낮출까요, 99.9%(약 40분)를 지키려고 밤에 자동으로 되돌리는 장치를 만들까요?" (정답 없음. 사용자 기대, 만드는 비용, 대응 가능 시간을 함께 보게 한다.)

## 면접 꼬리 질문

1. 오류 예산을 다 쓰면 팀은 무엇을 멈추고 무엇을 하나요? 그 규칙을 누가 정하나요?
2. CPU 사용률 알림 대신 burn-rate 알림을 쓰는 이유를 실제 장애 예로 설명해 보세요.
3. 백업이 있다는 것과 복원할 수 있다는 것의 차이를 어떻게 증명했나요? RTO를 잰 적이 있나요?

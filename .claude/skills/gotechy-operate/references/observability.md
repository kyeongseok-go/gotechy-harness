# 관측 (OpenTelemetry, 로그, 대시보드)

준비 모드 7단계에서 계측을 넣거나 점검할 때 연다.

## 1. 무엇을 보나

Google SRE 책의 4대 황금 신호를 핵심 서비스마다 한 화면에 둔다.

| 신호 | 뜻 | 웹 서비스 예 |
|---|---|---|
| 지연 | 요청을 처리하는 데 걸린 시간. 성공과 실패를 나눠 본다 | 응답 시간 히스토그램 |
| 트래픽 | 시스템에 걸린 수요 | 초당 요청 수 |
| 오류 | 실패한 요청 비율. 명시적 오류, 틀린 응답, 정책 위반(너무 느림)을 포함 | 5xx 비율, 시간 초과 비율 |
| 포화 | 가장 빠듯한 자원이 얼마나 찼나 | DB 연결 수, 메모리, 큐 길이 |

호출(사람 깨우기)은 사용자가 겪는 증상(오류, 지연)으로만 한다. 원인(CPU, 연결 수)은 대시보드에서 "왜"를 찾는 데 쓴다.

## 2. OpenTelemetry 현재 상태 (2026-10-16 확인)

명세 상태표(명세 v1.61.0) 기준:

| 신호 | API | SDK | 프로토콜(OTLP) |
|---|---|---|---|
| 트레이스 | Stable | Stable | Stable |
| 지표 | Stable | Mixed | Stable |
| 로그 | Stable(Bridge API) | Stable | Stable |
| Baggage | Stable | Stable | 해당 없음 |
| 프로파일 | 없음 | 없음 | Development |

- 트레이스, 지표, 로그는 운영에 써도 된다. 프로파일은 아직 개발 단계라 운영 필수 항목으로 두지 않는다.
- 언어별 SDK의 안정 여부는 언어마다 다르다. 쓰는 언어의 SDK 저장소에서 지표, 로그 SDK가 Stable인지 확인하고 HANDOFF 증거에 적는다.

## 3. semantic conventions

- 현재 판은 v1.44.0(2026-08-04)이다. HTTP 스팬과 DB 스팬 문서는 "Stable, 따로 표시한 것 제외"다. 일부 속성(`url.template`, `http.request.body.size` 등)은 아직 Development다.
- 속성 이름은 손으로 짓지 않고 conventions를 따른다(`http.request.method`, `http.response.status_code`, `db.system.name` 같은 이름). 그래야 대시보드와 알림 도구가 그대로 알아본다.
- 옛 실험판 이름에서 안정판으로 옮길 때는 계측 라이브러리가 `OTEL_SEMCONV_STABILITY_OPT_IN`을 지원하는지 본다. `http/dup` 값은 옛 이름과 새 이름을 함께 내보내 대시보드를 옮길 시간을 준다. 옮긴 뒤 `http`로 바꾼다.
- `service.name` 같은 `service.*` 리소스 속성은 바꾸지 않는다는 것이 명세의 약속이다. 서비스 이름을 처음에 잘 정한다.
- 생성형 AI 관련 conventions는 별도 저장소로 옮겨 갔다. LLM 호출 계측은 `gotechy-ai-eval` 스킬과 함께 정한다.

## 4. 최소 계측 (작은 서비스의 출발점)

1. 서버 진입점(HTTP 핸들러)마다 자동 계측 라이브러리로 스팬과 요청 지표를 만든다.
2. 외부 호출(DB, 외부 API, LLM)마다 스팬을 만들고 타임아웃 값을 속성으로 남긴다.
3. 로그는 한 줄 하나의 JSON이고, `trace_id`, `span_id`, 심각도, 이벤트 이름이 들어 있다. 콘솔에 사람용 문장만 찍지 않는다.
4. 비밀(토큰, 키, 비밀번호)과 개인정보(이메일, 전화번호, 주민번호)는 로그와 스팬 속성에 넣지 않는다. 넣어야 하면 마스킹한다. 로그 표본을 gitleaks로 검사해 0건을 확인한다.
5. 외부 합성 프로브 하나가 핵심 여정 URL을 밖에서 주기적으로 부른다. 무료 업타임 감시 서비스로 시작해도 된다.
6. 표본 추출을 쓰면 오류 요청은 항상 남긴다(꼬리 기반 표본 추출이나 오류 우선 규칙).

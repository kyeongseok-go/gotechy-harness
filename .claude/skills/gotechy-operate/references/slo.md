# SLO 문서 만들기

준비 모드 2~6단계, 9단계에서 연다. `docs/operations/slo.md`가 없으면 이 파일 맨 아래 틀로 만든다.

## 1. SLI 고르기

SLI는 "좋은 이벤트 수 / 유효 이벤트 수"로 쓴다. 0%는 아무것도 안 됨, 100%는 아무것도 안 깨짐이다(SRE Workbook, Implementing SLOs). 같은 꼴로 쓰면 알림, 보고, 분석 도구를 하나로 쓸 수 있다.

| 서비스 종류 | SLI 종류 | 예 |
|---|---|---|
| 요청-응답(웹, API) | 가용성 | 상태 코드 5xx가 아닌 응답 / 전체 유효 요청 |
| 요청-응답 | 지연 | 400ms 안에 끝난 응답 / 전체 유효 요청 |
| 요청-응답 | 품질 | 기능을 줄이지 않고(폴백 없이) 응답한 비율 |
| 파이프라인(배치, 동기화) | 신선도 | 10분 안에 갱신된 레코드 / 전체 레코드 |
| 파이프라인 | 정확성, 범위 | 검증을 통과한 출력 / 전체 출력 |
| 저장소 | 내구성 | 쓴 뒤 다시 읽을 수 있는 객체 비율 |

- **명세와 구현을 나눠 적는다.** 명세는 사용자 입장의 결과("첫 화면이 2초 안에 뜬 비율"), 구현은 재는 방법(로드밸런서 로그, 서버 계측, 외부 프로브, 브라우저 계측)이다. 구현마다 품질, 범위, 비용이 다르다.
- 유효 이벤트에서 빼는 것을 적는다: 헬스 체크, 봇, 부하 시험, 사용자의 잘못된 요청(4xx).
- 지연은 평균이 아니라 임계값 비율로 쓴다. "p95 500ms"보다 "500ms 안에 끝난 비율 95%"가 오류 예산 계산에 바로 들어간다.

## 2. 목표와 오류 예산

창은 4주 rolling을 기본으로 한다. 주말 수가 늘 같도록 주 단위로 맞춘 창이다. 주간 요약과 분기 보고를 곁들인다.

| SLO | 4주(40,320분) 오류 예산 | 쉽게 말하면 |
|---|---|---|
| 99% | 403.2분 | 4주에 약 6시간 43분 |
| 99.5% | 201.6분 | 약 3시간 22분 |
| 99.9% | 40.3분 | 약 40분 |
| 99.95% | 20.2분 | 약 20분 |
| 99.99% | 4.0분 | 약 4분 |

요청 기반이면 "100만 요청 중 99.9%"는 실패 1,000건이 예산이다.

정하는 순서:

1. 지난 4주 실제 값을 잰다(없으면 2주 재고 나서 정한다). 근거 칸에 "관찰" 또는 "추정"을 적는다.
2. 대응 가능 시간을 적는다. 예: "평일 9~22시는 30분 안, 그 밖은 다음 날 9시".
3. 4주 예산이 "최악 첫 대응 지연 + 롤백 5분"보다 커야 한다. 밤에 9시간 못 보는 서비스가 99.9%(40분)를 약속하면 장애 한 번에 예산을 넘는다. 그러면 99%로 낮추거나, 밤 동안 자동 롤백이나 자동 폴백을 만든다.
4. 100%는 목표로 쓰지 않는다.

## 3. 오류 예산 정책

SRE Workbook의 예시 정책을 줄였다. 정책의 목적은 벌이 아니라 "데이터가 신뢰성이 더 급하다고 말할 때 신뢰성에 집중해도 된다는 허락"이다.

- **예산 초과(지난 4주)**: 최우선 수정과 보안 수정 말고는 기능 변경과 배포를 멈추고, SLO 안으로 돌아올 때까지 신뢰성 작업을 한다.
- **예외**: 우리 쪽이 아닌 원인(호스팅 전체 장애, 외부 API 장애, 부하 시험 트래픽)으로 예산을 썼으면 기능 작업을 계속해도 된다. 그 대신 외부 의존을 줄이는 일을 부채로 적는다.
- **사고 하나가 4주 예산의 20%를 넘게 씀**: 포스트모템을 쓰고 최우선 조치를 1개 이상 둔다.
- **같은 종류의 사고가 분기 예산의 20%를 넘게 씀**: 다음 분기 계획에 최우선 항목으로 넣는다.
- **이견**: 오너가 정한다.

## 4. 알림 규칙

SRE Workbook의 multiwindow, multi-burn-rate 권장값(99.9% SLO 예시)이다. burn rate는 SLO 대비 예산을 쓰는 속도이고, 1이면 창 끝에 예산을 딱 다 쓴다.

| 알림 | 긴 창 | 짧은 창 | burn rate | 쓴 예산 |
|---|---|---|---|---|
| 호출 | 1시간 | 5분 | 14.4 | 2% |
| 호출 | 6시간 | 30분 | 6 | 5% |
| 티켓 | 3일 | 6시간 | 1 | 10% |

- 긴 창과 짧은 창이 **둘 다** 넘을 때 울린다. 짧은 창은 긴 창의 1/12이다. 짧은 창은 복구 뒤 알림이 빨리 꺼지게 한다.
- Workbook 표는 30일(720시간) 창으로 계산됐다(2% x 720시간 / 1시간 = 14.4). 4주 창에 같은 burn rate를 쓰면 쓴 예산은 약 2.1%, 5.4%, 10.7%로 거의 같다.
- 식: 오류율 임계값 = burn rate x (1 - SLO). 99.9%에서 14.4배면 1시간 오류율 1.44%다.
- 저트래픽 서비스(4주 허용 실패가 100건 미만)는 Workbook 권고대로 합성 트래픽을 더하거나, 작은 서비스를 묶거나, 재시도와 폴백을 넣거나, SLO를 낮추거나 창을 늘린다.
- 호출 알림마다 런북 링크를 주석으로 단다.

# plan 결과를 오너에게 설명하는 렌즈

언제 여는 파일인가: 실행 계획이나 진척을 오너나 비전공자에게 보고하거나 설명 문서를 만들 때.

## 대표 그림

- 마일스톤 지하철 노선도: 역마다 마일스톤 이름과 "증명 명령" 한 줄, 첫 역은 끝까지 가는 얇은 조각
- 언덕 그림: 마일스톤을 점으로, 오르막(모르는 것 푸는 중)과 내리막(아는 일 하는 중) 위치
- 위험 표 2x2: 가능성과 영향, 칸마다 조기 신호 한 줄

## 비유 후보

- **지하철 노선도**: 종점까지 한 번에 가는 노선을 먼저 깔고 역을 늘린다. 반쯤 깐 노선 열 개보다 끝까지 가는 노선 하나가 낫다(tracer bullet).
- **이사 계획표**: "이사가 망했다면 왜일까?"를 미리 적어 보면 엘리베이터 예약, 비 오는 날 같은 대비책이 나온다(pre-mortem).
- **요리 레시피**: 처음 보는 사람도 따라 하면 같은 맛이 나야 좋은 레시피다. 재료(파일), 순서(명령), 완성 사진(예상 출력)이 다 있어야 한다(혼자 읽히는 계획).

## 꼭 풀어야 할 용어

| 용어 | 쉬운 설명 |
|---|---|
| ExecPlan | 처음 보는 사람도 끝까지 따라 할 수 있게 쓴 살아 있는 작업 계획서 |
| 마일스톤 | 혼자 확인할 수 있는 중간 도착점 |
| tracer bullet | 처음부터 끝까지 일단 이어 놓은 가장 얇은 경로 |
| 증명 명령(proof) | 쳐 보면 "됐다"가 화면에 나오는 명령과 그 결과 |
| pre-mortem | 시작 전에 "이미 망했다"고 가정하고 이유를 적는 회의 |
| 조기 신호 | 위험이 터지기 전에 먼저 보이는 징조 |
| 멱등(idempotence) | 같은 작업을 두 번 해도 결과가 한 번 한 것과 같은 성질 |
| ADR | 중요한 기술 결정과 그 이유를 남기는 한 장짜리 기록 |
| 트렁크 기반 개발 | 작은 변경을 하루에도 여러 번 메인 줄기에 합치는 방식 |

## 선택해 보기

"가계부 앱에 은행 내역 가져오기를 만들 때 첫 2주를 어떻게 쓸까요?"
A. DB 설계, 로그인, 디자인 시스템을 다 만든다 B. 은행 한 곳의 파일 하나를 올리면 목록에 한 줄이 뜨게 끝까지 잇는다 (정답 B. 끝까지 가는 길을 먼저 보여야 방향이 맞는지 안다)

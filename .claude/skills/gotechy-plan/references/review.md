# 계획 리뷰

언제 여는 파일인가: 계획 초안을 다 쓴 뒤 착수 전(절차 7단계), 그리고 범위를 크게 바꾼 뒤.

## 실행 방법

1. **서브에이전트가 있으면 위임한다.** 쓸 수 있는 서브에이전트에 `spec-reviewer`(또는 같은 역할의 읽기 전용 리뷰어)가 있으면 계획 경로, 연결된 스펙 경로, 이 파일 경로, `references/bar.md` 경로를 넘기고 "아래 관점으로 깨뜨려 달라"고 맡긴다.
2. **새 세션 시험을 함께 맡긴다.** 가능하면 다른 서브에이전트에게 계획 파일만 주고 "Context and Orientation과 Concrete Steps만 보고 M1 첫 명령까지 가 보라, 막힌 곳을 보고하라"고 시킨다(읽기 전용이면 명령이 저장소에 실제로 있는지만 확인).
3. **없으면 스스로 한다.** 계획을 쓴 사람이 아니라 승인을 거절하려는 시니어 리뷰어 역할을 선언하고, 파일을 처음 보는 것처럼 다시 연다.
4. 결과는 계획 끝 `## 리뷰 기록`에 날짜, 방식과 함께 남긴다.

## 관점 (순서대로)

1. **혼자 읽히나.** 경로, 명령, 용어 풀이가 파일 안에 있나. 저장소에 없는 명령이나 경로가 있나.
2. **첫 마일스톤.** M1이 끝까지 가는 얇은 조각인가, 기반 공사만 몇 주인가.
3. **증명.** 마일스톤마다 실행 명령과 예상 출력이 있나. Validation이 스펙의 모든 AC ID를 덮나. "확인한다", "테스트 통과" 같은 한마디가 있나.
4. **크기.** 1주 넘는 마일스톤, 하루에 합칠 수 없는 커밋 단위, 2주 넘는 전체가 분할 없이 남아 있나.
5. **위험.** pre-mortem 이유가 진지한가(일반론만 있지 않나). 위험 표에 조기 신호가 관찰 가능한 형태인가. rabbit hole이 마일스톤 안에 그대로 들어가 있지 않나.
6. **복구.** 중간에 끊기면 어디서부터 다시 하나. 데이터 변경에 백업과 복원 명령이 있나. 다시 돌려도 안전한가.
7. **보안, 법, AI, 품질.** 인증, 결제, 개인정보, 외부 입력을 건드리는데 보안 리뷰 단계가 없나. 개인정보, 위치정보, 결제, 광고나 마케팅 메시지, AI 기능, 접근성 의무를 건드리는데 `gotechy-comply-kr` 단계가 없나. LLM 기능인데 `gotechy-ai-eval` 단계가 없나. 품질 목표가 있는데 측정 명령이 없나. 게이트 명령이나 CI가 없는데 M1에서 만들지 않나.
8. **숨은 위험.** 이 계획이 실패한다면 가장 그럴듯한 원인 하나를 지목한다.

## 출력 형식

| 심각도 | 뜻 | 처리 |
|---|---|---|
| 막음 | 이대로 착수하면 끝까지 못 가거나 끝났는지 판정할 수 없다 | 에이전트가 기각할 수 없다. 반영하거나 원문 그대로 사용자에게 올린다 |
| 고침 | bar 아래로 떨어진다 | 반영하거나 기각 이유를 기록한다 |
| 제안 | 더 좋게 만들 수 있다 | 반영 여부만 기록한다 |

외부 리뷰어의 말은 이렇게 옮긴다. `spec-reviewer`의 진행 차단, 수정 권장, 제안은 막음, 고침, 제안이다. `security-auditor`의 즉시, 이번 주, 권장은 높음, 중간, 낮음이고, 보안 지적의 처리는 `gotechy-security` 스킬의 기준을 따른다. 옮긴 뒤에도 막음은 에이전트가 기각할 수 없다.

지적마다 "왜 문제인가"와 "어떻게 고치나"를 한 쌍으로 쓴다. 지적이 없으면 없다고 쓰되 "실패한다면 가장 그럴듯한 원인"은 반드시 하나 쓴다.

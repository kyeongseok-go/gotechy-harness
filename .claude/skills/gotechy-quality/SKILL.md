# /gotechy-quality — 품질 목표 수립·검증

`docs/QUALITY_MODEL.md`(특성 목록·변환표·측정 스키마·벤치마크)를 먼저 읽는다. 산출물은 `docs/product-specs/<슬러그>/15-quality-goals.md` (위저드 밖 프로젝트는 `docs/product-specs/quality-goals-<슬러그>.md`). 진행 규칙(질문 엔진·승인 락·마커)은 `docs/WIZARD.md`를 준용한다.

`--verify`: 기존 15-quality-goals의 검증(6단계)만 재실행한다.

## 절차 — 모호한 형용사를 합격선으로

### 1. 요구 수집 → 품질특성 변환
- PRD·브리프·사용자 발화에서 품질 형용사를 수집한다 ("빠르게", "장애 없이", "보안", "쉽게"...).
- QUALITY_MODEL.md의 변환표로 25010 특성(부특성)에 매핑해 보여준다. 형용사 없이 시작해도 된다 — 프로젝트 유형별 추천 특성에서 출발.

### 2. 특성 선정 (상위 3~5개만)
- 9특성 전부를 관리하려 들지 않는다. 프로젝트 맥락(0절: 성격·규모·실패 비용)을 먼저 채우고, AskUserQuestion으로 상위 3~5개를 추천과 함께 확정한다. 나머지는 QUALITY_BAR 기본 체크로 커버됨을 명시.

### 3. 목표값 리서치 (표준은 측정법을 주고, 목표값은 우리가 정한다)
- 선정 특성×도메인별 통상 목표값을 조사한다: **QUALITY_MODEL.md의 벤치마크 표 우선** → 부족하면 웹 리서치(공식 문서·업계 표준 — Core Web Vitals, WCAG, OWASP, SLA 관행 등). **모든 목표값에 근거 출처를 붙인다.**
- 같은 측정 항목이라도 목표값은 시스템마다 다르다(증권 주문 ≠ 사내 게시판) — 실패 비용에 따라 엄격/보통/느슨 3안을 제시하고 선택받는다.

### 4. 목표 확정 — 조건 + 대상 + 지표 + 목표값
- 형식 강제: "**[조건(부하·환경)]에서 [대상(특정 API·페이지·여정)]의 [지표(p95·가용성·기록률)]가 [목표값]**". 넷 중 하나라도 빠지면 목표가 아니다.
- 평균보다 백분위(p95), "빠르다"보다 임계값, 기간 명시(월 가용성). 수치화 불가능하면 최소한 검증 가능한 기준(예: "감사 로그 기록률 100% — 행위·로그 1:1 대조")으로.
- 승인 락: 목표 표를 제시하고 명시적 승인 후 확정. 근거 없는 값은 `[NEEDS CLARIFICATION]`.

### 5. 설계 전략 (아키텍처 드라이버)
- 각 목표를 만족시킬 택틱을 도출한다 (성능→캐시·튜닝·스케일아웃 / 가용성→이중화·페일오버·백업 / 보안→감사로그·중앙수집·위변조 방지...).
- 설계에 큰 영향을 주는 목표는 **아키텍처 드라이버**로 표시하고 ADR 승격·ExecPlan 반영을 안내한다.
- §4의 "AI 작업 지시문"을 생성한다 — ExecPlan Validation에 그대로 들어가는 형식: "Q1: 50 VU에서 검색 API p95 ≤ 500ms를 만족할 것. 설계 전략과 부하 테스트 스크립트를 세우고 측정 결과를 보고할 것."

### 6. 검증 실행
- 목표별 검증 방법을 **실행 가능한 명령**으로 연결한다 (예: k6·autocannon 부하 / Lighthouse CI / @axe-core / npm audit / 로그 1:1 대조 스크립트 / 가동시간 집계). 도구가 없으면 최소 스크립트를 만들어 package.json에 등록한다 (명령 부재 = 게이트 실패).
- 실행 → §5 검증 기록에 측정값·X=A/B·합불 기록. **불합격은 실패가 아니라 루프다**: 설계 재검토 항목을 ExecPlan/부채로 라우팅하고 재측정 일정을 남긴다.
- `/gotechy-ship` 연결: 15-quality-goals가 존재하면 기능/릴리스 등급 게이트에서 미판정·불합격 목표가 걸린다.

## 완료 기준

- 목표 표(조건·대상·지표·목표값·근거·검증 방법 전부 채움, 마커 0) + 검증 1회 실행 기록 + 사용자 승인. 요약 3줄(선정 특성 / 합격선 / 판정 현황) 보고.

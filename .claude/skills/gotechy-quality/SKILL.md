# gotechy-quality: 모호한 품질 요구를 검증 가능한 합격선으로

"빠르게"는 요구사항이 아니다. 이 스킬은 품질 형용사를 표준 품질특성으로 옮기고, 측정 항목을 고르고, 조건과 대상과 목표값을 이 프로젝트의 근거로 정하고, 실행 가능한 명령으로 검증한다. 표준은 측정 방법까지만 주고 목표값은 우리가 정한다. 그래서 목표값마다 근거와 기준선 측정이 붙어야 한다. 테스트 전략은 커버리지 숫자가 아니라 "테스트가 결함을 잡는가"를 기준으로 세운다.

## 언제 쓰나, 쓰지 않나

- 쓴다: 스펙이나 대화에 "빠르게, 장애 없이, 보안 강화, 쓰기 쉽게" 같은 형용사가 나올 때. 기능 등급 이상 작업의 검증 기준을 세울 때. 테스트 전략(커버리지, mutation, flaky, 부하, 접근성)을 정하거나 점검할 때. `--verify`로 기존 목표의 측정만 다시 할 때.
- 쓰지 않는다: LLM 기능의 골든셋과 채점기(`gotechy-ai-eval`), 완료 게이트 판정(`gotechy-ship`), 보안 위협 모델과 리뷰(`gotechy-security`), 운영 SLO와 런북(`gotechy-operate`). 이 스킬은 목표와 검증 방법을 만들고, 판정은 그 스킬들이 가져다 쓴다.
- 패치(1시간 미만, 파일 1~2개, 동작 계약 불변)에는 목표 문서를 만들지 않는다. 대신 bar의 테스트 항목만 확인한다.

## 산출물과 저장 위치

| 상황 | 파일 (없으면 만든다) |
|---|---|
| 위저드 안 (스펙 폴더가 있음) | `docs/product-specs/<슬러그>/15-quality-goals.md` |
| 위저드 밖 | `docs/quality/goals-<슬러그>.md` |
| 미달 항목 | `docs/exec-plans/tech-debt-tracker.md`에 한 줄씩 추가 |
| 설계에 큰 영향을 주는 목표 | `docs/decisions/NNNN-<슬러그>.md` 초안 제안. ADR은 gotechy-plan이나 gotechy-retro의 틀로 쓴다 |

양식은 `references/templates/quality-goals.md`를 복사해 채운다.

## 절차

1. **맥락 수집.** 스펙(`docs/product-specs/`)과 PRD가 있으면 먼저 읽는다. 시스템 성격, 사용 규모 가정(DAU, 피크 동시 사용자), 실패 비용(장애, 오답, 유출 때 잃는 것)을 0절에 적는다. 모르는 값은 지어내지 않고 `[NEEDS CLARIFICATION: 질문]`을 남긴다. 산출물: 0절.
2. **형용사 수집과 특성 변환.** 요구에서 품질 형용사를 모아 `references/quality-model.md`의 변환표로 25010 특성과 부특성에 매핑한다. 형용사가 없으면 프로젝트 유형에서 출발한다. 산출물: 변환 표.
3. **특성 선정.** 9특성 전부를 관리하지 않는다. 실패 비용이 큰 순서로 3~5개를 추천과 함께 묻고 확정한다. 나머지는 "bar 기본 체크로 덮는다"고 적는다. 산출물: 1절 순위표.
4. **기준선 측정과 목표값 리서치.** 지금 값을 먼저 잰다(부하 도구, Lighthouse, 커버리지 리포트 등). 측정이 불가능하면 그 사실을 적는다. 그다음 공식 출처(`references/quality-model.md`의 기본 벤치마크 표)로 엄격, 보통, 느슨 3안을 만들고 실패 비용과 연결해 하나를 추천한다. 산출물: 목표 후보 3안과 근거.
5. **목표 확정.** 모든 목표를 "[조건]에서 [대상]의 [지표]가 [목표값]" 형식으로 쓴다. 넷 중 하나라도 빠지면 목표가 아니다. 지연은 백분위(API p95 또는 p99, 프론트 field 데이터는 p75)와 측정 창을 적고, 가용성은 기간과 허용 중단 시간을 같이 적는다. 수치화가 안 되면 검증 가능한 기준(예: 감사 로그 기록률 100%, 행위와 로그 1:1 대조)으로 쓴다. 표를 보여 주고 명시적 승인을 받은 뒤 확정한다. 산출물: 2절 목표 표.
6. **테스트 전략.** `references/test-strategy.md`를 열어 테스트 크기 구분, 커버리지 하한, mutation, 속성 기반 테스트, flaky 격리 규칙, 계약 테스트, 부하 테스트, 접근성 자동 검사 중 이 프로젝트에 해당하는 것을 고르고 합격선과 명령을 정한다. 산출물: 3절 테스트 전략 표.
7. **설계 전략과 AI 작업 지시문.** 목표마다 택틱(캐시, 이중화, 감사 로그 등)을 적고, 설계에 큰 영향을 주는 목표는 아키텍처 드라이버로 표시해 ADR 후보로 올린다. 목표 ID별로 ExecPlan에 그대로 넣을 지시문을 만든다. 예: "Q1: 정상 부하 50 VU에서 검색 API의 p95가 500ms 이하일 것. 설계 전략과 k6 스크립트를 세우고 측정값을 보고할 것." 산출물: 4절, 5절.
8. **검증 실행.** 목표마다 실행 가능한 명령을 연결한다(k6 thresholds, Lighthouse CI, axe, 커버리지 thresholds, Stryker break 값, 로그 대조 스크립트). 명령이 없으면 최소 스크립트를 만들어 프로젝트의 스크립트 목록(`package.json`, `Makefile` 등)에 등록한다. 명령이 없는 목표는 게이트 실패다. 실행 결과(측정값 A, 목표 B, X = A/B, 판정, 환경, 일시)를 6절에 적는다. 불합격은 끝이 아니라 설계 재검토로 돌아가는 루프다. 원인과 재측정 일정을 ExecPlan이나 부채 목록에 올린다. 산출물: 6절 검증 기록.
9. **보고.** 세 줄로 보고한다: 선정 특성, 합격선, 판정 현황(합격, 불합격, 미측정 개수). 위임 작업의 보고는 `owner-protocol` 스킬의 HANDOFF 형식을 따른다.

`--verify`일 때는 1~7단계를 건너뛰고 8단계만 다시 실행해 6절에 새 행을 추가한다. 이전 행은 지우지 않는다.

## 질문과 승인 규칙

- 한 번에 최대 5문항. 아키텍처, 데이터, 완료 판정에 영향이 큰 것만 묻는다. 사소한 취향은 묻지 않는다.
- 질문은 선택지 2~4개와 추천안, "왜 묻는지" 한 줄을 붙인다(가능하면 선택지 질문 도구를 쓴다). 모든 질문에 기본값을 붙여 "추천대로"만으로 진행되게 한다.
- 답을 받으면 해당 절을 바로 고치고 문서 끝 `## Q&A 로그`에 `- Q: ... A: ...` 한 줄을 남긴다.
- 확정은 명시적 승인("확정", "좋아")이 있을 때만 한다. 승인 날짜를 `## 확정 이력`에 적는다. 수정 요청은 전과 후를 보여 주고 다시 승인받는다.
- 위저드 순서에서 이 문서는 PRD(`10-prd.md`) 다음, 기능 명세(`20-features.md`) 전이다. PRD가 없으면 0절 맥락을 사용자에게 직접 묻는다.
- 확정 뒤 PRD가 바뀌면 영향받는 목표 행에 `[SYNC NEEDED: 무엇이 바뀌었나]`를 남긴다.

## 기준 요약 (전체와 등급 판정은 `references/bar.md`)

1. 목표 행마다 조건, 대상, 지표, 목표값, 근거, 검증 명령 6칸이 모두 차 있다. 마커(`[NEEDS CLARIFICATION]`, `[SYNC NEEDED]`)는 0개.
2. 지연 목표에 평균만 쓴 행이 0개다. 백분위와 측정 창이 있다.
3. 목표값마다 기준선 측정값이나 공식 출처가 있다. "업계 관행"만 적은 행은 0개.
4. 신규, 변경 코드 커버리지 80% 이상을 테스트 러너 thresholds로 강제한다. 커버리지는 하한이지 목표가 아니다.
5. 핵심 모듈(돈, 권한, 데이터 변환)은 변경 코드에 mutation testing을 돌리고 mutation score 60 미만이면 CI가 실패한다(하네스 기본값, A등급은 80). `gotechy-ship`과 `gotechy-build`도 같은 값을 쓴다.
6. 막는(blocking) 테스트 스위트에 flaky 테스트가 0개다. 격리된 테스트마다 담당자, 이슈, 7일 이내(하네스 기본값) 기한이 있다.
7. 버그 수정 PR은 고치기 전에 실패하는 재발 방지 테스트를 포함한다.
8. 성능, 접근성 목표는 도구 thresholds(k6, axe, Lighthouse CI)로 코드화되어 넘으면 명령이 0이 아닌 값으로 끝난다.

## 완료 기준

- 목표 표의 모든 행이 6칸을 채웠고 마커가 0개다.
- 모든 목표에 검증을 1회 이상 실행한 기록이 있다(불합격이어도 기록이 있으면 된다).
- 사용자가 목표 표를 승인했고 확정 이력에 날짜가 있다.
- 불합격, 미측정 목표가 ExecPlan이나 부채 목록에 담당자와 함께 올라가 있다.
- `references/bar.md` 기준으로 영역 등급(A~D)을 매겨 보고했다.

## 하지 않는 것

- 근거 없는 목표값을 만들지 않는다. 출처도 기준선도 없으면 `[NEEDS CLARIFICATION]`로 남긴다.
- "ISO 25010이 p95 200ms를 요구한다"처럼 표준에 없는 숫자를 표준 탓으로 돌리지 않는다. 표준은 특성과 측정 방법을 주고, 목표값은 이 프로젝트가 정한다.
- 커버리지 100%를 목표로 걸지 않는다. assertion 없는 테스트로 숫자만 채우는 길을 연다.
- flaky 테스트를 재실행으로 초록불로 만들고 끝내지 않는다. 격리하고 기한을 건다.
- 9특성 전부에 목표를 걸어 문서를 부풀리지 않는다.
- 승인 없이 목표를 확정하지 않고, 위저드 진행 중에 기능 코드를 만들지 않는다. 검증용 스크립트만 만든다.

## 필요할 때 여는 파일

- `references/quality-model.md`: 세 표준의 역할, 9특성과 부특성, 형용사 변환표, 목표 형식, 기본 벤치마크.
- `references/test-strategy.md`: 테스트 크기, 포트폴리오, 커버리지, mutation, 속성 기반, flaky, 계약, 부하, 접근성의 합격선과 명령.
- `references/bar.md`: 전체 체크리스트, 원천 표, 등급 판정, 흔한 실패.
- `references/lens.md`: 결과를 오너에게 설명할 때.
- `references/templates/quality-goals.md`: 산출물 양식.

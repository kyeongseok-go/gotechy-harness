# 품질 모델: 특성, 측정, 목표값을 세우는 방법

언제 여는 파일인가: 절차 2~5단계(형용사 변환, 특성 선정, 목표값 리서치, 목표 형식)를 할 때.

기반: ISO/IEC SQuaRE(25000 계열) 표준과 코딩하는기술사 영상 「AI에게 검증가능한 품질목표 제시하기」(https://youtu.be/OTttvhEHncQ, 2026-10-16 확인). 한 문장 요약: 품질특성을 식별하고, 측정 항목을 고르고, 조건과 대상과 목표값을 우리가 정하고, 그 기준으로 검증한다.

## 1. 표준들의 역할 분담 (2026-10-16 확인)

| 표준 | 판과 상태 | 답하는 질문 | 가져오는 것 |
|---|---|---|---|
| ISO/IEC 25010:2023 제품 품질 모델 | 2판, 2023-11 발행, 2011판은 폐지 | 무엇을 품질로 보나 | 9개 특성과 부특성의 공용 어휘 |
| ISO/IEC 25023:2016 제품 품질 측정 | 1판, 2022 재확인. 후속 ISO/IEC DIS 25000-23(Part 23, 제품 품질 측정)이 2026-09-10 DIS 투표 시작, 대체 예정 | 특성을 무엇으로 재나 | 측정 항목과 측정 함수 |
| ISO/IEC 25030:2019 품질 요구사항 틀 | 2판, 2025 재확인 | 목표를 어떻게 요구사항으로 만드나 | 목표값은 표준이 아니라 우리 시스템의 요구사항이라는 원칙 |
| ISO/IEC 25019:2023 사용 품질 모델 | 1판, 2023-11 | 사용 결과가 좋은가 | 출시 뒤 실사용 지표의 틀(특성 3개) |
| ISO/IEC 25002:2024 품질 모델 개요와 사용법 | 1판, 2024-03 | 품질 모델을 어떻게 쓰나 | 모델 구조와 측정, 요구사항, 평가의 관계 |
| ISO/IEC/IEEE 29148:2018 요구공학 | 2판, 2024 재확인, 후속 DIS 개정 중 | 좋은 요구사항의 조건 | 검증 가능성, 단일성, 추적 가능성 |

- 핵심: 표준은 측정 방법까지만 준다. 같은 측정 항목(응답 시간)이라도 증권 주문 시스템과 사내 게시판의 목표값은 다르다. 그래서 프로젝트마다 근거를 갖춰 목표값을 정한다.
- 25023은 개정 중이다. 측정 항목 이름을 인용할 때 판을 같이 적는다. 25023 원문의 측정 항목 ID와 식은 유료 원문이라 이번에 확인하지 못했다. 이 스킬의 판정식 X = A/B(실측 A, 목표 B)는 이 스킬의 약속이다.
- 출처: committee.iso.org의 각 표준 페이지(https://committee.iso.org/standard/78176.html, /35747.html, /89069.html, /72116.html, /78177.html, /78175.html, /72089.html).

## 2. 5단계 루프

1. 품질특성 식별: "빠르게"를 성능효율성(시간 효율성)으로.
2. 측정 항목 도출: 응답 시간 백분위, 처리량.
3. 조건, 대상, 목표값 설정: 기준선 측정과 리서치로 근거를 갖추고 우리가 정한다.
4. 설계 전략 결정: 캐시, 이중화, 감사 로그. 설계에 큰 영향을 주면 아키텍처 드라이버다.
5. 측정과 검증: 합격, 불합격 판정. 불합격이면 설계를 다시 보고 1~4로 돌아간다.

## 3. ISO/IEC 25010:2023 9개 특성과 부특성

특성과 부특성의 영어 이름은 iso25000.com 정리(https://iso25000.com/index.php/en/iso-25000-standards/iso-25010, 2026-10-16 확인)를 따랐다. 한국어 이름은 업계 통용어 기준이며 2023판 공식 국문 번역은 확인하지 못했다.

| # | 특성 | 뜻 | 부특성 |
|---|---|---|---|
| 1 | 기능적합성 (Functional Suitability) | 필요한 기능을 올바르게 주나 | 기능 완전성, 기능 정확성, 기능 적절성 |
| 2 | 성능효율성 (Performance Efficiency) | 자원 대비 빠르고 여유 있나 | 시간 효율성, 자원 활용성, 용량 |
| 3 | 호환성 (Compatibility) | 다른 시스템과 공존, 연동되나 | 공존성, 상호운용성 |
| 4 | 상호작용 능력 (Interaction Capability, 구 사용성) | 사람이 배우고 쓰기 쉬운가 | 적절성 인식성, 학습성, 운용성, 사용자 오류 방지, 사용자 몰입, 포용성, 사용자 지원, 자기 설명성 |
| 5 | 신뢰성 (Reliability) | 장애 없이 돌고 나도 복구되나 | 무결함성(Faultlessness, 구 성숙성), 가용성, 결함 허용성, 복구성 |
| 6 | 보안성 (Security) | 데이터와 행위가 보호되나 | 기밀성, 무결성, 부인 방지, 책임 추적성, 인증성, 저항성(Resistance) |
| 7 | 유지보수성 (Maintainability) | 고치기 쉬운 구조인가 | 모듈성, 재사용성, 분석성, 수정성, 시험성 |
| 8 | 유연성 (Flexibility, 구 이식성) | 환경 변화에 적응하나 | 적응성, 확장성(Scalability), 설치성, 대체성 |
| 9 | 안전성 (Safety, 2023 신설) | 사람과 자산에 해를 끼치지 않나 | 운영 제약, 위험 식별, 페일 세이프, 위험 경고, 안전한 통합 |

- 사용 품질은 별도 표준(25019:2023)이다. 제품이 아니라 "사용 결과"를 재는 축이라 출시 뒤 실사용 지표에 대응한다. 25019의 세 특성 이름은 이번에 원문으로 확인하지 못했다.

## 5. 목표 형식: 넷 다 있어야 목표다

"[조건]에서 [대상]의 [지표]가 [목표값]". 예: "정상 부하 500 TPS에서 주문 API의 p95 응답 시간이 500ms 이하, 오류율 0.1% 이하."

- 평균이 아니라 백분위를 쓴다. 평균은 꼬리 지연을 숨긴다. Google SRE book은 평균보다 백분위를 선호하고 99, 99.9번째 백분위가 그럴듯한 최악을 보여 준다고 쓴다(https://sre.google/sre-book/service-level-objectives/).
- 기간을 적는다. "가용성 99.95%"가 아니라 "월 가용성 99.95%(30일 기준 허용 중단 약 21.6분)". 계산: 30일 x 24시간 x 60분 x (1 - 목표). 99.9%는 약 43.2분, 99.5%는 약 3.6시간.
- 조건에는 부하(VU 또는 TPS), 데이터 크기, 환경(어느 서버 사양, 어느 네트워크)을 적는다. 개발 노트북에서 잰 값은 운영 조건 목표의 증거가 아니다.
- 수치화가 안 되면 검증 가능하게 쓴다. "관리자 개인정보 조회의 감사 기록률 100%, 행위와 로그를 1:1 대조".
- 좋은 요구사항의 조건(29148): 필요성, 명확성, 단일성, 실현 가능성, 검증 가능성, 추적 가능성. 개발 첫 단계에 적는다.
- AI에게 시킬 때도 같은 형식이다. "성능 좋게" 대신 "Q1을 만족할 것. 설계 전략과 검증 스크립트를 세우고 측정값을 보고할 것".

## 8. 엄격, 보통, 느슨 3안 만드는 법

1. 기준선을 잰다. 지금 p95가 900ms면 "200ms" 목표는 설계 변경 없이는 불가능하다는 사실부터 적는다.
2. 실패 비용을 한 줄로 쓴다. "주문 실패 1건 = 매출 손실과 고객 이탈" 같은 문장.
3. 3안을 만든다. 느슨 = 공식 출처의 "통과" 경계, 보통 = 기준선에서 현실적으로 개선 가능한 값, 엄격 = 실패 비용이 큰 경우 필요한 값. 3안마다 드는 비용(설계 변경, 인프라)을 적는다.
4. 하나를 추천하고 이유를 실패 비용과 연결해 쓴다. 사용자가 고른다.

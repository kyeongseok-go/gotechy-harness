# ADR (결정 기록) 쓰는 법

절차 6단계에서 Decision Log를 ADR로 올릴지 정하고, ADR을 쓰거나 대체할 때 연다.

## 1. 원천과 원칙

- Michael Nygard, Documenting Architecture Decisions (2011-11-15): 제목, 맥락, 결정, 상태, 결과 다섯 부분. 번호는 순서대로 붙이고 다시 쓰지 않는다. 뒤집힌 결정도 지우지 않고 "대체됨"으로 남긴다. 그때 그것이 결정이었다는 사실이 여전히 중요하기 때문이다. 문서 전체는 한두 쪽.
- MADR 4.0.0 (2024-09-17): 맥락과 문제, 결정 동인, 검토한 선택지, 결정 결과, 결과, 확인 방법, 선택지별 장단점, 더 알아볼 것. 앞의 넷(제목 포함) 말고는 선택 항목이다.

이 틀은 Nygard의 다섯 부분을 뼈대로, MADR의 선택지 비교와 확인 방법을 더했다.

## 2. ADR로 올리는 기준

Decision Log의 결정이 아래 중 하나에 해당하면 ADR로 올린다.

<!-- gotechy:adr-when:start -->
- 되돌리는 데 하루 이상(하네스 기본값) 걸린다: 데이터 모양, 저장소, 프레임워크, 공개 API 계약, 파괴적 마이그레이션.
- 새 런타임 의존성, 저장소, 큐, 외부 서비스를 들인다.
- 인증, 인가, 비밀 처리 방식을 바꾼다.
- 여러 모듈이나 바깥 사용자에게 영향이 간다.
- 진지하게 비교한 선택지가 2개 이상 있었고, 6개월 뒤 누군가 "왜 이렇게 했지?"라고 물을 만하다.
- 같은 논쟁이 두 번 이상 나왔다.
<!-- gotechy:adr-when:end -->

해당하지 않으면 Decision Log에 두고, 회고 문서 8절에 "ADR 아님, 이유"를 한 줄 적는다.

## 3. 쓰는 규칙

- 번호: `docs/decisions/`의 가장 큰 번호 다음. 4자리(`0007`). 지운 번호를 다시 쓰지 않는다. 폴더가 없으면 만들고 `0001`부터.
- 제목: 짧은 명사구. 문제와 해결이 보이게. 예: "0007. 메모 검색에 Postgres 복합 인덱스 사용".
- 맥락: 사실만, 가치 판단 없이. 기술, 일정, 사람, 비용의 힘이 서로 어떻게 당기는지.
- 결정: "우리는 ~한다"처럼 능동 문장으로 끝까지.
- 결과: 좋은 점, 나쁜 점, 중립 모두. 나쁜 점이 하나도 없으면 아직 덜 생각했다는 신호다.
- 확인 방법: 결정이 지켜지는지 무엇으로 확인하나(테스트, lint 규칙, 리뷰 항목).
- 상태: 제안됨, 승인됨, 폐기됨, 대체됨(NNNN). 결정은 오너만 한다. 에이전트가 쓴 ADR은 "제안됨"으로 두고 오너 결정으로 올린다.
- 대체: 새 ADR에 "대체: NNNN"을 적고, 옛 ADR은 상태만 "대체됨(새 번호)"으로 바꾼다. 옛 본문은 고치지 않는다.

- 나쁘다, 왜냐하면 <...>

## 5. 점검

- [ ] 번호가 연속이고 기존 번호와 겹치지 않는다: `ls docs/decisions | sort`
- [ ] 상태, 날짜, 맥락, 선택지 2개 이상, 결정, 결과(나쁜 점 1개 이상)가 있다.
- [ ] 대체했다면 옛 ADR의 상태가 "대체됨(새 번호)"이고 본문은 그대로다: `git diff docs/decisions/<옛 파일>`에 상태 줄만 바뀌었다.
- [ ] 한두 쪽(대략 120줄) 안이다.

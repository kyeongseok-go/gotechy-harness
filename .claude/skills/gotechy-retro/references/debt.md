# 부채 기록과 사분면

절차 7단계에서 부채 표에 적고 회고 문서에서 분류할 때 연다. 부채 표가 없으면 이 파일의 틀로 만든다. `gotechy-ship`, `gotechy-plan` 스킬과 같은 표를 쓴다.

## 1. 부채 표 `docs/exec-plans/tech-debt-tracker.md`

```markdown
# 기술 부채

부채는 고금리 대출이다. 매일 조금씩 갚는다. 기록 없는 부채가 가장 비싸다.

## 활성 부채

<!-- gotechy:debt-table:start -->
| ID | 등록일 | 내용 | 위치 | 심각도 | 이자(방치 시 비용) | 상환 계획 |
|---|---|---|---|---|---|---|

심각도: 구조(레이어 위반, 데이터 위험) / 기능(엣지 케이스, 성능) / 표면(이름, 중복)
보안 리뷰의 심각도를 옮길 때: 높음은 구조, 중간은 기능, 낮음은 표면으로 적는다.
<!-- gotechy:debt-table:end -->

## 상환 완료

| ID | 내용 | 상환일 | 증거 |
|---|---|---|---|
```

규칙:

- ID는 `TD-001`부터 이어 붙인다. 지운 번호를 다시 쓰지 않는다.
- 7칸을 모두 채운다. "이자"는 "이 부채가 커지면 무엇이 비싸지는가"를 한 문장으로 쓴다. 이자를 쓰지 못하면 부채가 맞는지 다시 본다.
- 상환 계획은 날짜나 계기("다음 결제 기능 작업 때")로 쓴다. "언젠가"는 계획이 아니다.
- 부채를 만들며 머지하는 것은 허용된다. 기록 없이 머지하는 것이 금지다.
- 구조나 기능 심각도 항목이 2주(하네스 기본값) 넘게 그대로면 `gotechy-plan` 스킬로 상환 계획을 세우자고 보고에 적는다.
- 보안 높음은 이 표로 미루지 않는다. 바로 처리하고, 못 하면 `gotechy-security` 스킬로 넘기고 오너에게 막는 결정으로 올린다. 기한 있는 중간과 낮음은 표 아래 대응대로 심각도를 옮겨 적는다.
- 갚으면 행을 "상환 완료" 표로 옮기고 증거(테스트 파일, 커밋, 측정치)를 적는다.

## 2. 사분면으로 나누기 (Fowler, 2009)

Martin Fowler의 Technical Debt Quadrant는 부채를 두 축으로 나눈다. 신중(prudent)과 무모(reckless), 의도(deliberate)와 무의식(inadvertent). Fowler는 "부채냐 아니냐"보다 "신중한 부채냐 무모한 부채냐"가 쓸모 있는 구분이라고 쓴다. 회고 문서 9절에 사분면을 적고, 사분면마다 처리 방향을 다르게 잡는다.

| 사분면 | 모습 | 회고에서 할 일 |
|---|---|---|
| 신중-의도 | 출시를 위해 알고서 지름길을 택하고 결과를 감수함 | 부채 표에 이자와 상환 시점을 적는다. 이자가 작으면 갚지 않는 선택도 기록한다(Fowler는 이자가 작으면 갚을 가치가 없을 수 있다고 쓴다) |
| 무모-의도 | 좋은 설계를 알면서 "일단 빨리"를 택함 | 같은 선택을 막는 과정 행동 항목을 만든다(예: 스펙 없이 구현 시작 금지 규칙) |
| 무모-무의식 | 설계 방법을 몰라서 생긴 빚 | 지식 공백을 메우는 행동 항목(학습, 리뷰어 추가)과 상환 계획 |
| 신중-무의식 | 잘 만들고 나서야 "이렇게 했어야 했다"를 알게 됨 | 정상으로 본다. Fowler는 뛰어난 설계자 팀에게도 흔하고 피할 수 없다고 쓴다. 배운 것을 ADR이나 문서로 남기고 리팩터링 시점을 정한다 |

사분면은 회고 문서에만 적는다. 부채 표의 7칸 형식은 바꾸지 않는다(다른 스킬과 같은 표를 쓰기 때문이다).

## 3. 회고에서 꼭 넣는 부채

- 이번 마일스톤에서 이월한 범위.
- 회고 행동 항목 가운데 이번 주기에 하지 못하는 것.
- 출시 2주나 4주 뒤 성공 기준 측정(아직 재지 않았으면). 심각도 표면, 상환 계획에 날짜.
- "반복"으로 표시한 문제의 구조 개선(규칙 파일, CI 검사, 템플릿).

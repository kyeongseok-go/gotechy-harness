# 렌즈: 게이트 결과를 오너에게 설명하기

완료 게이트나 출시 점검 결과를 오너(부모님과 AI 초심자도 읽는다)에게 설명할 때 연다.

## 대표 그림

- 점수판: 검사 항목을 한 줄씩 세우고 통과, 실패를 칸으로 칠한 표. 맨 위에 "7개 중 6개".
- 출시 단계 사다리: 1%, 10%, 100% 계단과 계단마다 "여기서 멈추는 조건".
- 세 번 나눈 공사 그림: 새 길 내기(expand), 차 옮기기(migrate), 옛 길 막기(contract).

## 비유 후보

- 택배 송장: "보냈어요"가 아니라 송장 번호(커밋 sha와 CI 결과)가 있어야 보낸 것이다. 번호가 다른 송장은 남의 택배다.
- 이사할 때 새 집 먼저: 새 집에 짐을 다 옮기고 확인한 뒤에 옛 집 계약을 끝낸다. 같은 날 하면 되돌아갈 곳이 없다.
- 가계부의 빚 칸: 빚을 져도 괜찮지만 가계부에 이자와 함께 적어야 한다. 안 적은 빚이 가장 비싸다.

## 꼭 풀어야 할 용어

| 용어 | 쉬운 설명 |
|---|---|
| 완료 게이트 | "끝났다"고 말하기 전에 통과해야 하는 검사 목록 |
| CI | 코드를 올릴 때마다 서버가 자동으로 검사를 돌려 주는 장치 |
| 커밋 sha | 코드의 한 시점을 가리키는 고유 번호, 송장 번호 같은 것 |
| 롤백 | 방금 내보낸 것을 직전 상태로 되돌리기 |
| 카나리 | 새 버전을 일부 사용자에게만 먼저 보내 문제를 살피는 방법 |
| 기능 플래그 | 코드를 내보낸 채로 기능만 켜고 끄는 스위치 |
| expand-contract | DB 구조를 새 것 추가, 옮기기, 옛 것 삭제의 세 번에 나눠 바꾸기 |
| SemVer | 버전 번호 세 자리로 "얼마나 크게 바뀌었나"를 알리는 약속 |
| 기술 부채 | 나중에 고치기로 하고 남긴 일, 미룰수록 비용이 붙는다 |

## 선택해 보기 후보

"테스트 하나가 가끔 실패해요. 오늘 출시를 미루고 원인을 찾을까요, 그 테스트를 부채로 적고 출시할까요?" (정답 없음. flaky 테스트의 위험, 출시 지연 비용, 부채 기록 여부를 함께 보게 한다.)

## 면접 꼬리 질문

1. "로컬에선 통과했는데 CI에서 실패"한 경험이 있나요? 무엇이 달랐고, 다시는 안 생기게 무엇을 바꿨나요?
2. 컬럼 이름을 바꾸는 배포를 무중단으로, 롤백 가능하게 하려면 몇 번에 나눠 배포하나요? 각 단계에서 롤백하면 어떻게 되나요?
3. 배포 빈도와 변경 실패율을 팀 목표로 걸면 어떤 부작용이 생길까요?

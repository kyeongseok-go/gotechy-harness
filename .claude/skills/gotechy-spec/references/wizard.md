# 기획 위저드 규칙

언제 여는 파일인가: 트랙 판정이 "위저드"(화면 여러 개인 제품이나 사이트, 신규 프로젝트)일 때, 첫 질문을 하기 전에.

## 1. 단계 사슬

```
gotechy-spec:   00-brief, 10-prd, (15-quality-goals), 20-features, 30-user-flow
gotechy-design: 40-sitemap, 50-wireframe, 60-style-guide
그다음:         gotechy-plan (ExecPlan)
```

- 산출물은 모두 `docs/product-specs/<슬러그>/` 한 폴더에 번호 순으로 쌓인다(없으면 만든다). 문서끼리 링크한다.
- 진행 표시는 7단계 기준이다: 00-brief 1/7, 10-prd 2/7, 20-features 3/7, 30-user-flow 4/7, 40~60은 `gotechy-design`의 5/7~7/7. 15-quality-goals는 번호 없는 선택 단계다.
- 화면이 없는 제품(CLI, 라이브러리)은 30-user-flow 뒤에 바로 `gotechy-plan`으로 간다.
- 기능 하나짜리 작은 일은 위저드가 아니라 미니나 풀 스펙으로 쓴다.

## 2. 제1원칙: 위 문서가 아래 문서의 입력이다

브리프의 한 줄이 PRD의 문제가 되고, 기능 명세의 기능이 유저 플로우의 노드가 된다. 그래서 고칠 일은 되도록 위에서 고친다. 글 한 줄 고치는 비용이 화면을 다시 만드는 비용보다 훨씬 싸다. 각 단계는 앞 단계가 확정되지 않으면 시작하지 않는다(하드 게이트). 특히 30-user-flow는 20-features에 확정된 기능이 1개 이상 있어야 시작한다.

## 3. 질문 엔진

1. 단계당 최대 5문항. 영향(설계, 데이터, 사용 경험, 완료 판정을 바꾸는가)과 불확실성이 모두 큰 것만 묻는다. 취향은 묻지 않는다.
2. 선택지가 기본이다. 2~4개 선택지, 추천안 하나, "왜 묻는지" 한 줄. 열린 질문은 00-brief 인터뷰에서만 쓰고, 그때도 짧게 답할 수 있게 좁힌다.
3. 한 질문은 한 축만 다룬다. 범위를 물을 때 일정을 같이 묻지 않는다.
4. 모든 질문에 기본값을 둔다. "추천대로"라고만 해도 진행되고, "나중에 바꿀 수 있어요"를 밝힌다.
5. 답은 바로 문서에 반영한다. 그 자리의 옛 문장 중 모순되는 것은 지우고, 문서 끝 `## Q&A 로그`에 `- Q: ... / A: ... (날짜)`를 남긴다.
6. 추측하지 않는다. 물을 만큼 중요하지 않지만 확실하지 않은 것은 `[NEEDS CLARIFICATION: 질문]`으로 남긴다. 단계 확정 조건은 표시 0개다.

## 4. 승인 잠금

- 단계 끝에 산출물 요약(5줄 이내)과 남은 표시 수를 보여 주고 명시적 승인("확정", "좋아", "다음")을 받기 전에는 다음 단계로 가지 않는다.
- 수정 요청을 받으면 바꿀 부분을 전과 후로 보여 주고, 승인받아 반영한 뒤 다시 승인을 받는다.
- 여러 단계를 한 턴에 합치지 않는다.
- 승인은 문서 끝 `## 확정 이력`에 날짜와 함께 적는다.
- 위저드 중에는 코드를 만들지 않는다. 구현은 ExecPlan부터다.
- 매 턴 첫 줄에 위치를 밝힌다: `[위저드 20-features, 3/7]`.

## 5. 되돌아가기

확정된 위 문서를 고치면, 영향받는 아래 문서의 해당 위치에 바로 `[SYNC NEEDED: 10-prd의 '관리자' 역할 삭제 반영]` 표시를 넣는다. 아래 문서를 다시 만드는 일은 자동으로 하지 않고 "이어서 고칠까요?"로 묻는다. 표시가 남아 있으면 스펙은 확정되지 않는다.

## 6. 탈출구

- `--quick`: 승인 없이 00~30을 한 번에 초안으로 쓴다(Kiro Quick Spec과 같은 방식). 표시는 그대로 남기고, 마지막에 표시 목록을 보여 준다. 확정하려면 결국 표시를 다 풀어야 한다.
- 단계 하나의 분량이 크면(기능 20개 이상) 첫 요구사항 하나만 먼저 써서 방향을 확인받고 이어 쓴다.

## 7. 단계별 할 일과 확정 기준

| 단계 | 틀 | 할 일 | 확정 기준 |
|---|---|---|---|
| 00-brief (1/7) | `templates/00-brief.md` | 열린 질문 3개(무엇, 누구, 핵심 행동 1개)를 이야기로 듣는다. 해결책보다 먼저 appetite와 no-gos를 정한다. discovery 문서가 있으면 결정과 증거를 가져온다 | 한 단락 브리프가 공식 칸을 다 채움, appetite와 no-gos 있음, 표시 0 |
| 10-prd (2/7) | `templates/spec.md` | 브리프에서 끌어낸다. 성공 기준은 여섯 칸, 문제는 이해관계자별로 나누고, 사용자 역할 표를 만든다(20의 입력). 내부 FAQ 3개 | bar 체크리스트 8, 9, 10, 12, 17 통과, 표시 0 |
| 15-quality-goals (선택) | `gotechy-quality` 스킬 | 성능, 보안, 접근성 같은 품질 목표를 수치로. 큰 기능과 제품이면 권장. 10-prd 확정 뒤, 20-features 전에 만든다 | 그 스킬의 기준 |
| 20-features (3/7) | `templates/20-features.md` | 요구사항, 기능, 수용 기준 세 층. 수용 기준은 EARS만. 상세 9칸 중 구현 전 7칸 이상 | bar 체크리스트 3~7, 11, 13~16 통과, 표시 0 |
| 30-user-flow (4/7) | `templates/30-user-flow.md` | 하드 게이트: 확정된 기능 1개 이상. 범위는 선택지로 묻는다(핵심 여정만이 기본). mermaid와 페이지 노드 표 | 모든 노드가 기능 ID에 연결, 페이지 노드 표 있음, 표시 0 |

전체 순서는 00-brief, 10-prd, 15-quality-goals, 20-features, 30-user-flow, 40-sitemap, 50-wireframe, 60-style-guide다. 30-user-flow를 확정하면, 화면이 있으면 `gotechy-design` 스킬로, 없으면 `gotechy-plan` 스킬로 이어 간다고 알린다. 법 의무(개인정보, 위치정보, 결제, 광고나 마케팅 메시지, AI 기능, 접근성)가 걸리면 `gotechy-comply-kr`, LLM 기능이 있으면 `gotechy-ai-eval`도 계획 전에 거치게 한다.

## 8. 적대적 리뷰 시점

10-prd와 20-features가 모두 초안이 되면 `references/review.md`로 리뷰를 한 번 돌린다. "막음" 지적이 남아 있으면 20-features를 확정하지 않는다.

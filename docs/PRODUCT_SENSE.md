# PRODUCT_SENSE.md — 제품 감각

> 에이전트가 기능을 설계·구현할 때 "무엇이 좋은 제품인가"를 판단하는 기준. 신규 팀원 온보딩 문서라고 생각하고 읽는다.

## 기본 대상 사용자 (프로젝트별 교체 가능, 기본값은 고텍이 표준)

1. **부모님 + AI를 잘 접하지 못하는 사람들** — 이들이 이해하고 쓸 수 있으면 완성이다.
   - 함의: 설명 없는 전문용어 금지, 첫인상 기준은 `docs/DESIGN.md` 경험 원칙 1(3초 규칙) 참조, 에러 메시지는 "다음에 뭘 하면 되는지"를 알려줌.
2. **커리어 접점** — 채용 담당자·동료 개발자가 이 제품을 보고 "이 사람과 일하고 싶다"고 느껴야 한다.
   - 함의: README·데모·아키텍처 문서가 제품의 일부다.

## 제품 판단 원칙

1. **불편함 해소가 출발점** — "멋진 기술"이 아니라 "실제 불편함"에서 시작한다. 스펙에는 반드시 "누가, 언제, 왜 불편한가"가 먼저 온다.
2. **가장 얇은 완결 경로 우선** — 반쪽 기능 10개보다 끝까지 동작하는 1개. (50% 증후군 방어는 제품 수준에서도 적용)
3. **기본값이 제품이다** — 사용자는 설정을 바꾸지 않는다. 기본 상태가 최선의 경험이어야 한다.
4. **되돌릴 수 있게** — 파괴적 동작(삭제·발행·결제)은 확인 + 취소 경로 필수.
5. **한국어 UX 우선** — 날짜·통화·존댓말 톤까지 한국 사용자 기준. 국제화는 그다음.

## 기능 추가 판단 체크

새 기능 요청이 오면 순서대로 묻는다:

1. 대상 사용자 1이 이걸 이해할 수 있는가? (아니면 단순화하거나 숨긴다)
2. 기존 기능의 완성도를 높이는 게 먼저 아닌가?
3. 이 기능이 없으면 사용자가 실제로 곤란한가, 아니면 "있으면 좋은" 수준인가?
4. 유지보수 비용(테스트·문서·부채)을 감안해도 남는 장사인가?

## career_signals 렌즈 (gotechy 고유)

모든 스펙(`product-specs/`)에는 `career_signals` 필드를 포함한다. **키워드·타겟사·증거 기준의 진실의 원천은 `~/.claude/gotechy-career.yaml`(개인) 또는 `docs/career.example.yaml`** (채용 시장 변화 시 그 파일만 갱신).
- 스펙 시점: `hypothesis` (증명하려는 역량 가설 + jd_keywords 매칭)
- ship 시점: `evidence` (제3자가 확인 가능한 링크·수치 — 없으면 게이트 미통과)

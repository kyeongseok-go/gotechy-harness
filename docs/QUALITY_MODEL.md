# QUALITY_MODEL.md — 표준 기반 품질 목표 방법론 (ISO/IEC 25010·25023·25030)

> `/gotechy-quality`의 헌법. 기반: SQuaRE(ISO/IEC 25000 계열) + 코딩하는기술사 「AI에게 검증가능한 목표 제시하기」(youtu.be/OTttvhEHncQ).
> 한 문장 요약: **"빠르게·안전하게"는 요구사항이 아니다 — 품질특성을 식별하고, 측정 항목을 고르고, 조건·대상·목표값을 우리가 정하고, 그 기준으로 검증한다.**
> "측정할 수 없으면 관리할 수 없고, 관리할 수 없으면 개선할 수 없다."

## 0. 세 표준의 역할 분담

| 표준 | 답하는 질문 | 우리가 가져오는 것 |
|---|---|---|
| **ISO/IEC 25010** (제품 품질 모델) | 무엇을 품질로 볼 것인가 | 9개 품질특성 + 부특성의 공용 어휘 |
| **ISO/IEC 25023** (제품 품질 측정) | 그 특성을 무엇으로 측정하나 | 측정 항목 + 측정 함수 (예: X = A/B) |
| **ISO/IEC 25030** (품질 요구사항) | 목표를 어떻게 요구사항으로 만드나 | **목표값은 표준이 아니라 우리 시스템의 요구사항** — 조건·대상·평가 기준을 우리가 정의 |

핵심: 표준은 측정 **방법**까지만 준다. 목표값 B는 시스템마다 다르다 — 증권 주문 시스템과 사내 게시판은 같은 측정 항목(응답시간 적정성)에 다른 목표값을 갖는다. 그래서 **프로젝트마다 리서치로 근거를 갖춰 목표값을 정한다.**

## 1. 5단계 루프

```
① 품질특성 식별 ("빠르게"→성능 효율성)
② 측정 항목 도출 (25023: 응답시간 적정성, X=A/B)
③ 조건·대상·목표값 설정 ← 리서치로 근거 확보, 우리가 정한다 (25030)
④ 설계 전략 결정 (캐시·이중화·감사로그… 설계에 큰 영향이면 = 아키텍처 드라이버)
⑤ 측정·검증 (합격/불합격 판정) ──불합격──▶ 설계 재검토 후 ①~④ 루프
```

|---|---|---|
| "빠르게 해주세요" | 성능 효율성 (시간 효율성) | 응답시간 적정성(X=A/B), 평균 응답시간(p95 권장), 처리량 |

| "다른 시스템과 연동" | 호환성 (상호운용성) | 연동 성공률 |

## 3. ISO/IEC 25010:2023 — 9개 품질특성

<!-- 2023 개정 기준. 상세 부특성·측정 항목 카탈로그는 references/research/iso-25010-quality-research.md -->

| # | 특성 (한/영) | 뜻 | 부특성 (전체) |
|---|---|---|---|
| 1 | 기능적합성 Functional Suitability | 필요한 기능을 올바르게 제공하나 | 기능 완전성 · 기능 정확성 · 기능 적절성 |
| 2 | 성능효율성 Performance Efficiency | 자원 대비 빠르고 여유 있나 | 시간 효율성 · 자원 활용성 · 용량성 |
| 3 | 호환성 Compatibility | 다른 시스템과 공존·연동되나 | 공존성 · 상호운용성 |
| 4 | 상호작용능력 Interaction Capability (구 사용성) | 사람이 배우고 쓰기 쉬운가 | 적절성 인식성 · 학습용이성 · 운용성 · 사용자 오류 방지 · 사용자 몰입 · **포용성** · 사용자 지원 · 자기설명성 (구 접근성은 포용성·사용자 지원으로 분리) |
| 5 | 신뢰성 Reliability | 장애 없이 돌고, 나도 복구되나 | 무결함성(구 성숙성) · **가용성** · 결함 허용성 · 복구성 |
| 6 | 보안성 Security | 데이터·행위가 보호되나 | 기밀성 · 무결성 · 부인방지 · **책임추적성** · 인증성 · 저항성(신규) |
| 7 | 유지보수성 Maintainability | 고치기 쉬운 구조인가 | 모듈성 · 재사용성 · 분석용이성 · 수정용이성 · 시험용이성 |
| 8 | 유연성 Flexibility (구 이식성) | 환경 변화에 적응하나 | 적응성 · **확장성**(신규) · 설치용이성 · 대체용이성 |
| 9 | 안전성 Safety (2023 신설) | 사람·자산에 해를 끼치지 않나 | 운영 제약 · 위험 식별 · 고장 안전(페일 세이프) · 위험 경고 · 안전 통합 |

- 한글 용어는 KS·TTA(2011판)·업계 통용어 기준 (2023판 공식 국문 번역은 미공표 — 원장 참조).
- **사용품질 모델은 별도 표준(ISO/IEC 25019:2023)**: 유익성(사용성·접근성·적합성) / 위험 회피성 / 수용성(경험·신뢰·준수성) — 제품이 아니라 "사용 결과"를 재는 축. 출시 후 측정(온라인 지표·UXR)에 대응.
- 25023의 측정 항목은 `ID(예: PTb-2-G)·이름·측정 함수(QME 결합식)` 구조다. 25023:2016은 2011 모델 기준이라 신설 특성(안전성 등)의 측정 항목은 자체 정의한다.

## 4. 목표의 형식 — 넷 다 있어야 목표다

> **[조건] 에서 [대상] 의 [지표] 가 [목표값]** — 예: "정상부하 500 TPS에서 · 주문 API의 · p95 응답시간이 · 500ms 이하 (오류율 0.1% 이하)"

- 평균이 아니라 **백분위(p95)** — 평균은 꼬리 지연을 숨긴다.
- 기간을 명시 — "가용성 99.95%"가 아니라 "**월** 가용성 99.95% (= 30일 중 허용 중단 약 22분)".
- 수치화가 안 되면 **최소한 검증 가능하게** — "감사 로그 기록률 100%: 행위와 로그를 1:1 대조".
- 좋은 품질 요구사항의 조건 (25030→ISO/IEC/IEEE 29148): 필요성 · 명확성 · 단일성 · 실현 가능성 · **검증 가능성** · 추적 가능성 — 그리고 **개발 최초 단계에 명세**할 것.
- AI에게 시킬 때도 같은 형식으로: "성능 좋게"❌ → "Q1을 만족할 것. 설계 전략과 검증 스크립트를 세우고 측정 결과를 보고할 것"⭕.

## 5. 실무 사례 3종 (영상 원본 — 목표 표의 본보기)

| 요구 | 특성 | 합격선 | 설계 전략 (드라이버) | 검증 |
|---|---|---|---|---|
| "빠르게" | 성능 효율성 | 정상부하 500 TPS에서 주문 API p95 ≤ 500ms, 오류율 ≤ 0.1% | 캐시·쿼리 튜닝·스케일아웃 | 부하 테스트 500 TPS |
| "장애 안 나게" | 신뢰성(가용성) | 월 가용성 ≥ 99.95% (허용 중단 22분/월), 핵심 주문 MTTR ≤ 10분 | 이중화·페일오버·백업·모니터링 | 가동시간 집계 + 복구 훈련 |
| "보안 강화" | 보안성(책임추적성) | 관리자 개인정보 조회의 감사 기록률 100% | 감사로그 설계·중앙 수집·위변조 방지·보관 정책 | 행위↔로그 1:1 대조 |

## 7. 기존 문서와의 관계

- **QUALITY_BAR.md** = 모든 작업의 상시 하한선 (체크리스트, A~D 등급). **QUALITY_MODEL** = 프로젝트별 상위 3~5개 특성에 **수치 합격선**을 세우는 방법론. BAR는 늘 지키고, MODEL은 중요한 곳에 조준한다.
- **RELIABILITY.md**의 수치 예산 = 신뢰성·성능 특성의 기본값 예시. 15-quality-goals가 확정되면 그 값이 우선한다.
- 산출물: `docs/product-specs/<슬러그>/15-quality-goals.md` → ExecPlan Validation·`/gotechy-ship` 게이트로 집행.

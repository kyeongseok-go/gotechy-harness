# RELIABILITY.md — 신뢰성 요구사항

> "빠르고 죽지 않는다"를 수치로 정의한다. 이 표의 기본 예산은 출발점이고, 프로젝트별 정식 목표는 `/gotechy-quality`로 세운다 (`docs/QUALITY_MODEL.md` — 조건+대상+지표+목표값). 에이전트는 이 수치를 어기는 변경을 만들면 스스로 지적해야 한다.

## 기본 예산 (프로젝트별 조정)

| 항목 | 기준 |
|---|---|
| 서버 콜드 스타트 | 1초 이내 |
| 핵심 API p95 응답 | 500ms 이내 |
| 핵심 사용자 여정 (첫 화면 → 핵심 액션 완료) | 3초 이내 |
| 클라이언트 첫 로드 (LCP) | 2.5초 이내 |
| 에러율 | 핵심 여정에서 1% 미만 |

## 원칙

1. **관측 없이는 신뢰성 없음** — 핵심 여정에 최소한의 로깅/타이밍 계측을 넣는다. 콘솔 로그가 아니라 구조화된 로그.
2. **실패는 설계의 일부** — 외부 API 호출은 타임아웃·재시도(지수 백오프)·폴백을 명시한다. "일단 호출"은 금지.
3. **데이터는 잃지 않는다** — 파괴적 마이그레이션 전 백업 확인. 사용자 입력은 저장 실패 시 복구 경로 제공.
4. **동시성 헬퍼는 계측과 함께** — 병렬 처리 유틸에는 타이밍·에러 계측을 내장한다 (불투명한 외부 p-limit류보다 자체 헬퍼 선호).

## 검증 방법

- ExecPlan의 Validation 섹션에 신뢰성 항목을 행동으로 기술. 측정 도구는 프로젝트별로 정의하고(예: autocannon 래퍼를 `bench:api` 스크립트로), **정의 전까지 신뢰성 게이트는 미통과**다.
- 성능 저하가 예상되는 변경은 전/후 측정치를 PR·ExecPlan에 기록한다.

## 백업 (복원 테스트 안 한 백업은 백업이 아니다)

1. 파괴적 마이그레이션 전: `db:backup` 스크립트(프로젝트별 정의 — pg_dump 등) 실행을 절차로 강제. 관리형 DB(Neon/Supabase)면 PITR 활성 확인으로 대체.
2. 보존: 배포 전 스냅샷 + 일일, 최소 7일.
3. **분기 1회 복원 리허설** (ROUTINES.md 루틴 표에 등재) — 복원 소요 시간을 기록한다.
4. 마이그레이션은 expand-contract (추가→마이그레이트→제거를 분리 배포) — 롤백 가능성 유지.

## 인시던트 런북 (새벽 2시의 나는 다른 사람이다)

0. **감지**: 핵심 여정 URL 1개를 외부 모니터(UptimeRobot 등 무료 티어)로 감시.
1. **복구 우선, 원인 분석은 나중**: 직전 배포가 원인이면 즉시 롤백 (`docs/DEPLOYMENT.md` 절차).
2. 롤백 불가(데이터 문제)면: 쓰기 경로 차단(read-only 플래그) → 백업 확인 → 복구.
3. **24시간 내 5줄 포스트모템** → `docs/decisions/` 또는 ExecPlan Surprises에 기록. 장애도 블로그 재료다 (3종 출력).

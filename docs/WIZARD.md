# WIZARD.md — 단계형 기획·디자인 위저드 헌법

> `/gotechy-spec`(기획)과 `/gotechy-design`(UI 설계)이 공유하는 진행 규칙.
> 기반: Relume(Brief→Sitemap→Wireframe→Style Guide), 매니페스트(PRD→기능→유저플로우→와이어프레임, 하드 게이트),
> GitHub Spec Kit(/clarify 질문 엔진, NEEDS CLARIFICATION 마커), AWS Kiro(명시적 승인 락), Lovable(계획/실행 모드 분리),
> Shape Up(Appetite·No-gos 선행), Looka(한 스텝 한 축). 원장: `references/research/planning-wizard-research.md`

## 스테이지 체인

```
 /gotechy-spec ──────────────────────────┐   /gotechy-design ──────────────────────┐
 00-brief → 10-prd → 20-features → 30-user-flow → 40-sitemap → 50-wireframe → 60-style-guide → ExecPlan
```

- 산출물은 전부 `docs/product-specs/<슬러그>/` 한 폴더에 번호 순으로 쌓인다 (서로 링크된 살아있는 문서).
- 템플릿: `docs/product-specs/_wizard-templates/`. 화면이 없는 제품(CLI·라이브러리)은 40~60을 건너뛴다.
- 기능 하나짜리 작은 작업은 위저드가 아니라 기존 미니 스펙 경로(`_template-prd.md`)로 — 위저드는 제품·사이트 단위다.

## 제1원칙 — 상위 산출물이 하위 생성의 프롬프트다

사이트맵의 섹션 한 줄이 와이어프레임 생성의 입력이고, 브리프의 톤 한 줄이 스타일가이드의 입력이다.
따라서 **수정은 최대한 상류에서** 한다 — 텍스트 한 줄 고치는 비용이 화면 재생성보다 압도적으로 싸다.
각 스테이지는 이전 산출물이 없으면 시작할 수 없다 (하드 게이트 — 매니페스트: "PRD와 기능 1개 없이는 유저플로우 생성 불가").

## 질문 엔진 (Spec Kit /clarify 이식)

1. **스테이지당 최대 5문항.** (Impact × Uncertainty)가 높은 것만 — 아키텍처·데이터·UX·완료 판정에 실질 영향을 주는 질문만 하고, 사소한 취향은 묻지 않는다.
2. **선택지가 기본, 열린 질문은 예외.** AskUserQuestion으로 2~4개 선택지 + **추천안 명시** + description에 "왜 묻는지" 한 줄. 열린 질문은 브리프 인터뷰에서만, 답은 5단어 수준으로 답할 수 있게 좁혀서.
3. **한 스텝 = 한 축.** 스타일을 물을 때 색을 같이 묻지 않는다 (Looka: "지금은 스타일만, 색은 다음에").
4. **모든 질문에 기본값 동봉.** "추천대로"라고만 답해도 진행된다. "나중에 바꿀 수 있어요"를 명시해 결정 부담을 낮춘다.
5. **답변 즉시 문서 반영.** 해당 섹션을 그 자리에서 갱신하고 모순된 옛 문장은 삭제. 문서 하단 `## Q&A 로그`에 `- Q: … → A: …` 한 줄씩 남긴다.
6. **추측 금지 — 마커를 남겨라.** 물어볼 만큼 중요하지 않지만 확실치 않은 것은 임의로 정하지 말고 본문에 `[NEEDS CLARIFICATION: 질문]`을 남긴다. **스테이지 확정 조건 = 마커 0개.**

## 락 (Kiro식 승인 게이트)

- 각 스테이지 끝에 산출물 요약을 제시하고 **명시적 승인("확정", "yes", "다음")을 받기 전에는 다음 스테이지로 진행하지 않는다.**
- 수정 요청을 받으면: 바꿀 부분을 **diff(전/후)로 제시 → 승인 → 반영 → 재승인 요청.** 여러 스테이지를 한 턴에 합치지 않는다.
- 승인은 문서 하단 `## 확정 이력`에 날짜와 함께 기록한다. 확정 후 변경은 해당 스테이지를 다시 열고 하류에 전파한다(아래).
- 위저드 진행 중에는 **코드를 만들지 않는다** (Lovable: "Plan mode is for decision-making"). 구현은 ExecPlan부터.
- 진행 상황은 매 턴 밝힌다: `[위저드 40-sitemap · 4/7단계]` 형식.

## 되돌아가기 (Kiro Sync Files의 md 버전)

상류 문서를 수정하면, 영향받는 모든 하류 문서의 해당 위치에 `[SYNC NEEDED: 40-sitemap의 '요금' 페이지 삭제 반영]` 마커를 즉시 삽입한다.
하류 재생성은 자동이 아니라 **명시적으로** 한다 ("이어서 갱신할까요?"). SYNC 마커가 남아 있으면 `/gotechy-ship` 게이트에서 걸린다.

## 탈출구

- `--quick`: 승인 게이트 없이 전 스테이지를 일괄 초안 생성 (Kiro Quick Spec). 마커는 그대로 남기므로 검토는 결국 해야 한다.
- 체크포인트 생성: 양이 많은 스테이지(사이트맵·와이어프레임)는 **첫 단위(홈 페이지 1장)만 먼저** 만들어 방향을 확인받고 계속한다 (Relume "continue generating").

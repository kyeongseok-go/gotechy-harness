# 0006. 오너 인증: Secure Enclave 키와 Touch ID로 결정에 서명

- 상태: 제안 (1b N1 구현 끝, 오너가 실제 Touch ID로 확인한 뒤 승인)
- 날짜: 2026-10-14
- 대체: [0005](0005-decision-signing.md)의 서명 방식(HMAC). 필수 게이트를 원천에서 계산하는 부분은 그대로다.
- 관련: [계약 6.3절, 6.4절](../references/contract.md), [1b ExecPlan](../exec-plans/active/2026-10-14-harness-v2-phase1b.md), [N0 실험](../references/evidence/2026-10-14-n0/README.md)

## 맥락

1a의 결정 서명은 `$GOTECHY_HOME/keys/`의 비밀 키 파일로 만든 HMAC이었다. 오너와 같은 OS 사용자로 도는 프로그램은 그 파일을 읽을 수 있다. 셸이 있는 Codex 워커도 읽을 수 있었다. 그래서 1a의 알려진 한계(같은 사용자 자가 승인, Codex 키 읽기, 장부 무서명, TTY 우회)는 모두 "키가 파일이다"에서 나왔다.

## 검토한 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. Secure Enclave P-256 키 + 서명마다 사람 확인(Touch ID나 Mac 암호), 공개 키로 검증 (선택) | 개인 키가 칩 밖으로 나오지 않는다. 같은 사용자 프로세스도 오너의 손가락 없이는 서명하지 못한다. 검증에 비밀이 필요 없다 | macOS 전용. 화면이 잠기면 서명할 수 없다. Swift 도구를 빌드해야 한다 |
| B. macOS 키체인에 HMAC 키를 두고 접근 제어 | 기존 코드 변경이 작다 | 키체인 항목은 같은 사용자 앱이 허용 창으로 꺼낼 수 있고, 서명마다 사람 확인을 강제하기 어렵다 |
| C. 하드웨어 보안 키(YubiKey) | 다른 OS에서도 된다 | 기기를 사야 하고 늘 꽂혀 있어야 한다 |

## 결정

A. 서명 도구 `native/ownerkey.swift`를 `gotechy keys init`이 빌드하고, 키를 만들 때 `userPresence`를 건다. 게이트 서명과 결정 장부 줄 서명을 한 번의 확인으로 받는다. 검증은 `$GOTECHY_HOME/owner/<key_id>.pub`의 공개 키로 한다. 1a의 HMAC 결정은 옮기지 않고 다시 결정하게 한다(실제로 쓰인 HMAC 결정이 없었다).

## 결과 (Consequences)

- 쉬워지는 것: 워커, 스크립트, `script`로 TTY를 흉내 낸 프로세스도 Touch ID 없이는 결정을 만들지 못한다. 장부의 줄을 바꾸거나 더하면 검증이 실패한다(끝줄을 지우는 것은 TD-014). 서명 도구는 한 번의 확인으로 결정 하나만 서명하고, 확인 창 문구를 서명 대상에서 직접 만든다(보안 감사 6차). 검증은 어디서나(리눅스 CI 포함) 된다.
- 어려워지는 것: 결정은 이 맥에서, 화면이 풀린 상태에서만 할 수 있다. Touch ID는 무엇에 서명하는지 보여 주지 않으므로, 오너는 자기가 decide를 실행한 직후의 창만 승인해야 한다. 같은 사용자 프로세스가 공개 키와 blob을 자기 키로 바꾸는 공격은 프로젝트에 공개 키 지문을 고정해야 막힌다(TD-013).
- 확인할 것: 실제 Touch ID 창이 뜨는지, 한 번의 확인으로 두 서명이 나오는지, 취소하면 아무것도 기록되지 않는지(오너가 직접).

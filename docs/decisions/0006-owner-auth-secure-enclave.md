# 0006. 오너 인증: Secure Enclave 키와 Touch ID로 결정에 서명

- 상태: 승인됨 (2026-10-16, 오너가 T-007의 추천안 "암호 확인으로 승인"을 골랐다. 이 맥의 확인은 맥 로그인 암호로 둔다. 약한 점은 TD-023)
- 날짜: 2026-10-14
- 대체: [0005](0005-decision-signing.md)의 서명 방식(HMAC). 필수 게이트를 원천에서 계산하는 부분은 그대로다.
- 관련: [계약 6.3절, 6.4절](../references/contract.md), [1b ExecPlan](../exec-plans/completed/2026-10-14-harness-v2-phase1b.md), [N0 실험](../references/evidence/2026-10-14-n0/README.md)

## 맥락

1a의 결정 서명은 `$GOTECHY_HOME/keys/`의 비밀 키 파일로 만든 HMAC이었다. 오너와 같은 OS 사용자로 도는 프로그램은 그 파일을 읽을 수 있다. 셸이 있는 Codex 워커도 읽을 수 있었다. 그래서 1a의 알려진 한계(같은 사용자 자가 승인, Codex 키 읽기, 장부 무서명, TTY 우회)는 모두 "키가 파일이다"에서 나왔다.

## 검토한 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. Secure Enclave P-256 키 + 서명마다 사람 확인(Touch ID나 Mac 암호), 공개 키로 검증 (선택) | 개인 키가 칩 밖으로 나오지 않는다. 같은 사용자 프로세스도 오너의 손가락 없이는 서명하지 못한다. 검증에 비밀이 필요 없다 | macOS 전용. 화면이 잠기면 서명할 수 없다. Swift 도구를 빌드해야 한다 |
| B. macOS 키체인에 HMAC 키를 두고 접근 제어 | 기존 코드 변경이 작다 | 키체인 항목은 같은 사용자 앱이 허용 창으로 꺼낼 수 있고, 서명마다 사람 확인을 강제하기 어렵다 |
| C. 하드웨어 보안 키(YubiKey) | 다른 OS에서도 된다 | 기기를 사야 하고 늘 꽂혀 있어야 한다 |

## 결정

A. 서명 도구 `native/ownerkey.swift`를 `gotechy keys init`이 빌드하고, 키를 만들 때 `userPresence`를 건다. 게이트 서명과 결정 장부 줄 서명을 한 번의 확인으로 받는다. 검증은 `$GOTECHY_HOME/owner/<key_id>.pub`의 공개 키로 한다. 1a의 HMAC 결정은 옮기지 않고 다시 결정하게 한다(실제로 쓰인 HMAC 결정이 없었다).

## 결과 (Consequences)

- 쉬워지는 것: 워커, 스크립트, `script`로 TTY를 흉내 낸 프로세스도 Touch ID 없이는 결정을 만들지 못한다. 장부의 줄을 바꾸거나 더하면 검증이 실패한다(끝줄을 지우는 것은 TD-014). 서명 도구는 한 번의 확인으로 결정 하나만 서명하고, 확인 창 문구를 서명 대상에서 직접 만든다(보안 감사 6차). 검증은 어디서나(리눅스 CI 포함) 된다.
- 어려워지는 것: 결정은 이 맥에서, 화면이 풀린 상태에서만 할 수 있다. Touch ID는 무엇에 서명하는지 보여 주지 않으므로, 오너는 자기가 decide를 실행한 직후의 창만 승인해야 한다. 같은 사용자 프로세스가 공개 키와 blob을 자기 키로 바꾸는 공격은 프로젝트에 공개 키 지문을 고정해야 막힌다(TD-013).
- 확인할 것: 실제 Touch ID 창이 뜨는지, 한 번의 확인으로 두 서명이 나오는지, 취소하면 아무것도 기록되지 않는지(오너가 직접).

## 실측 (2026-10-15, 오너의 맥 미니, 근거는 macOS 통합 로그와 임시 프로젝트)

- 이 맥에는 지문 장치와 Apple Watch가 없어 확인 창은 **맥 로그인 암호 창**이다(`MechanismPasscode`만 쓰임). "손가락 없이는"은 이 맥에서 "로그인 암호 없이는"이 된다.
- 결정마다 확인 창이 한 번만 떴고, 창 문구에 작업 번호와 터미널과 같은 확인 코드가 보였다(예: `gotechy G-002 T-001: 넣기 (확인 69A4)`). 한 번의 확인으로 게이트와 장부 줄 두 서명이 나왔다.
- 맞는 암호가 확인된 뒤에만 서명이 기록됐다(`PasscodeVerified` 뒤에 장부 기록). 첫 decide가 프로젝트에 키를 고정했다.
- 확인 시험에서 오너가 "이번엔 취소"인 G-002를 두 번 승인했다. 스크립트 안내와 decide 안내("코드가 같으면 승인")가 부딪혔고, 암호 창은 평소 시스템 창과 같아 습관처럼 승인하기 쉽다(TD-023). 안내는 고쳤다(3955ce0).
- 터미널의 y 질문에서 거절하면 서명 도구를 부르지 않고 아무것도 기록하지 않았다(13:51 실행, G-002 pending, 장부 1줄).
- 확인 창에서 "취소"를 누르는 경로는 실제 기기에서 아직 눌러 보지 않았다. 확인 없이는 칩이 서명하지 않으므로(키에 `userPresence`), 취소가 서명으로 이어질 길은 없다. 자동 테스트는 가짜 서명 도구의 취소(exit 4)로 이 경로를 본다.
- 승인 때 오너가 정할 것: 이 맥의 확인을 로그인 암호로 둘지, Touch ID 달린 키보드를 쓸지(TD-023).

## 승인 (2026-10-16)

- 오너가 오후 루프 보고 T-007의 막는 결정에 "추천안으로 진행"이라고 답했다(2026-10-16 00:07 KST). 추천안은 "암호 확인으로 승인"이다.
- 그래서 지문 장치가 없는 이 맥에서는 결정 확인이 맥 로그인 암호다. 로그인 암호를 아는 사람은 결정할 수 있고, 암호 창은 다른 시스템 창과 닮아 습관처럼 승인하기 쉽다. 이 약한 점은 TD-023으로 남기고, 창의 확인 코드(터미널과 같은 4자리)로 자기 결정의 창을 알아보게 한 것이 지금의 완화책이다.
- 확인 창의 "취소" 버튼을 실제 기기에서 누르는 시험은 여전히 하지 않았다. 키에 `userPresence`가 걸려 있어 확인 없이는 칩이 서명하지 않는다는 것이 근거다.

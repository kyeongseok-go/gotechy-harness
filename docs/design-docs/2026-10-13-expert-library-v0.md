# 전문가 라이브러리 + 오케스트레이션 설계 가설 v0

> 이 문서는 결정이 아니라 **가설**이다. 12절 결정 트리를 grill-me로 하나씩 잠그면서 갱신하고, 잠긴 결정은 Brief/PRD → ExecPlan으로 옮긴다.
> 근거와 출처는 전부 연결된 리서치 문서에 있다 (여기서는 절 번호로만 참조: 리서치 §N).

## 1. 요구사항 (2026-10-13 사용자 요청 요약)

| # | 요구 |
|---|---|
| R1 | 제품의 시작부터 끝까지 각 분야 전문가를 에이전트로 만들고 계속 키운다 (기획·디자인·설계·개발·검증·배포·마케팅) |
| R2 | 전문가마다 최신 데이터·기술을 가져오는 루틴으로 자동 업그레이드 |

## 2. 설계 원칙 (근거)

1. **오너 우선**: 모든 위임 작업은 오너가 3분 안에 이해하고 결정할 수 있는 handoff로 끝난다. 이해는 완료 조건의 일부다. (리서치 §1 Probe 3축, §7 Anthropic RCT)
2. **전문가 = 스킬 팩, 페르소나가 아니다**: 절차·체크리스트·예시·검증 기준으로 전문성을 만든다. 페르소나는 브랜드 보이스에만. (§6)
3. **적게 싣고 잘 고른다**: 한 세션 자동 트리거 스킬 ≤15개, 도메인 라우터 → 레벨3 참조의 2단 라우팅, 프로젝트별 프로필 설치. (§3, §4, §12)
4. **채택 → 래핑 → 제작**: 검증된 공개 스킬은 버전 고정해 채택, 개인·한국 레이어로 감싸고, 차별화 영역만 직접 만든다. (§1 [31:00], §5 SkillsBench)
5. **방법은 파일에, 변하는 사실은 실행 시점에**: 스킬은 방법을 담고, 버전·API 같은 사실은 공식 문서 MCP·웹에서 실행 중에 조회한다. (§5)
6. **역할이 아니라 컨텍스트로 나눈다**: 병렬은 독립 작업에만, 한 영역의 쓰기는 한 워커만, 검증자는 읽기 전용. (§6)
7. **재지 않으면 주장하지 않는다**: plugin eval의 기여도(Δ), harness-bench, `/skill-doctor`로 판정. 모델이 흡수한 스킬은 은퇴. (§3, §5, §11)
8. **원천 하나, 어댑터 여럿**: 스펙 6필드 SKILL.md + AGENTS.md를 정본으로, 도구별 차이는 생성된 어댑터로. (§12)

## 3. 아키텍처 가설

```
L0 오너 콘솔 (메인 세션: 사용자 + 리드 에이전트)
   grill · 결정 게이트 · HANDOFF 검토 · 이해 확인
        │ 작업 명세 (Target/Change/Constraints/Ownership/Acceptance)
L1 오케스트레이션 어댑터: Orca(주력) / herdr(폴백) / 스크립트(최후)
        │ 워커 = CLI(claude·codex·cursor...) + 팩 프로필
L2 전문가 팩 (Agent Skills)
   항상: owner-protocol · 라우터들      단계별: 9단계 루프 팩 + AX/FDE 오버레이
        │
L3 지식 최신화: 실행 시점 조회(공식 문서 MCP) + 주간 radar → delta PR → eval 게이트 → 사람 머지
L4 이해·증거: HANDOFF.md → 렌더 뷰 → explain-doc(마일스톤) · 용어 은행 → 위키·블로그·면접
```

## 6. 이해 계층 (R7·R9)

- **owner-protocol (항상 켜짐, ≤1.5KB)**: 결론 먼저 → 결정 필요 항목 → 요약 → 마지막 줄에 "건너뛴 것·확인 못 한 것·리스크"(ponytail 계약). 용어 은행에 없는 새 용어만 한 줄 풀이.
- **handoff 3계층**: T0 `HANDOFF.md`(모든 작업, 1쪽) → T1 렌더 뷰(스크립트가 HANDOFF + 용어 은행을 인터랙티브 HTML로 변환, LLM이 HTML을 쓰지 않음) → T2 풀 explain-doc(단계 종료·마일스톤·면접 준비 때만).
- **렌즈**: 팩마다 ≤40줄 — 대표 그림 종류, 비유 후보, 꼭 풀 용어, "선택해 보기" 후보, 면접 꼬리 질문. explain-doc 엔진은 하나만 유지(포크 금지).
- **이해 게이트**: 결정 게이트를 통과시키기 전에 오너가 "말해 보기" 2문항에 자기 말로 답한다 → 결정 기록에 남긴다. 핵심 로직은 학습 모드(사람이 일부 작성)로 선택 적용.
- **용어 은행**: 한 번 설명한 용어는 다시 풀지 않는다(토큰 절약 + 학습 누적) → 위키·블로그·면접 연습 재료.

**HANDOFF 한눈 보기** (D4 결정으로 오너의 주 검토 수단이 됨 — AI 요약은 요점을 묻고 사실과 추측을 섞기 쉽다):
1. **형식 강제**: `handoff-lint`가 스키마·길이를 검사, 통과 못 하면 워커가 고쳐 재제출. 한 줄 요약 ≤60자, 결정 ≤3개(옵션·추천·이유 1줄), 리스크 ≤3줄, 증거는 "명령 → 결과", 문장마다 [확인/추론/추정].
2. **3초 카드**: frontmatter → 상태 신호등 한 줄 (결정 필요 수 · 테스트 결과 · 리스크 수 · 비용 · 변경 파일 수).
3. **인박스 한 화면**: 모든 워커의 HANDOFF를 "결정 필요 → 실패 → 완료" 순으로 정렬. 터미널(`inbox` 명령)과 HTML 대시보드 둘 다.
4. **HANDOFF 감사관**(저비용): 싼 모델이 HANDOFF를 실제 diff·테스트 로그와 대조해 "요약과 실제가 다른 곳"만 지적.
5. **읽기 3단**: 3초(카드) → 30초(요약+결정) → 3분(증거·용어·말해 보기, 접힘).
6. **결정 분류와 넘침 규칙**: 결정은 ①막는 결정(답 없으면 진행 불가) ②기본값 결정(기본값으로 진행, 이의 제기 가능) ③알림(결정 아님)으로 나눈다. 카드에는 ①만 최대 3개. ①이 3개를 넘으면 버리지 않고 lint가 "작업을 쪼개거나 결정 세션으로 올리라"는 교정 메시지와 함께 실패 → 리드가 의존 순서대로 한 번에 하나씩 묻는 결정 세션(grill)으로 처리하고 ADR로 남긴다. ②는 접힌 목록으로 "기본값 적용 예정 n건".
7. **에러 메시지는 에이전트용**(shadcn/lint 방식): lint 실패 메시지에 무엇이 틀렸고 어떻게 고치는지 + 대안을 적는다 (core-beliefs #5).
8. **Claude Code mod 뷰(선택 어댑터)**: 사용자가 이미 만든 `apply-kit` mod(상태 파일 → 패널 + "내가 할 일" 토스트 + 푸시 알림)와 같은 패턴으로 HANDOFF 인박스 패널, 결정 발생 시 토스트·폰 푸시, `/decide` 명령을 제공. 원천은 파일이므로 다른 도구에서는 터미널 `inbox`·HTML로 같은 내용을 본다.
9. **교차 검증 감사관**: 작성 모델과 **다른 계열** 모델이 HANDOFF를 diff·테스트 로그와 대조(상관된 오류 감소). 기본은 Codex 저가 모델, 모델은 Codex 프로필(`~/.codex/<이름>.config.toml`)·커스텀 프로바이더(`[model_providers.*]`, OpenRouter 등)로 교체 가능 → `routing.yaml`의 `auditor:` 항목. 감사관 지적은 file:line 근거 필수, 권고만. 회사 모드에서는 데이터 경계에 맞춰 교체.

`HANDOFF.md` 스키마 (Orca `worker_done`·`ask`와 1:1):

```markdown
---
task: T-012
packs: [build-go]
status: needs-decision   # done | failed | needs-decision
evidence: ["go test ./... → 14 passed"]
new_terms: [connection pool]
---
## 결정 필요 (먼저) — 옵션, 추천, 이유 한 줄
## 한 줄 요약
## 한 일 · 산출물
## 증거 (명령 → 출력)
## 건너뛴 것 · 확인 못 한 것 · 리스크
## 새 용어 (용어 은행에 없는 것만)
## 말해 보기 (오너 이해 확인 2문항)
## 다음 단계 제안
```

## 7. 오케스트레이션 (R8)

- **주력 Orca**(이미 사용 중, MIT, CLI 40여 종, DAG·게이트·ask·worker_done, SSH). 오케스트레이션은 토글 없이 동작(1.4.209 확인), 잦은 릴리스 → 릴리스 파일로 버전 고정 + 오케스트레이션 스킬은 `orca skills get orchestration --full`로 앱 버전에 맞춰 락에 포함. **어댑터는 Orca 1 + native 1(백엔드 claude·codex)** — D7 결정, herdr는 반복 수요가 생길 때만.
- **전문가 호출 3형태** (같은 팩 원천에서 생성): 인라인(현재 세션에 스킬 로드) / 자문(격리 서브에이전트·읽기 전용 워커, HANDOFF만 회신) / 위임(Orca 워커가 worktree에서 산출물 생성 → 게이트). 기본값과 자동 조정 기준은 D4.
- **흐름**: 오너+리드가 grill → 스펙 → 작업 DAG(컨텍스트 단위) → 워커가 각자 worktree에서 팩 프로필로 실행 → 검증 워커(읽기 전용) → 게이트에서 오너 결정 → 영역별 단일 쓰기로 병합.
- **작업 명세** `orchestration/tasks/T-###.md`: frontmatter(id, pack, agent, model, deps, gate) + Orca 5요소. **결과** `orchestration/handoffs/T-###.md` = 6절 스키마. 게이트 결과는 `orchestration/gates/G-###.md`(서명, D8·1a ExecPlan), 구조 결정은 ADR(`docs/decisions/`).
- **원샷 세팅** `scripts/setup.sh --profile go-postgres,grow-kr --agents claude,codex [--company] [--dry-run]`: ①설치된 에이전트 감지 ②팩을 `.agents/skills` + `.claude/skills`에 배치(회사 모드는 복사) ③`gotechy.lock`·AGENTS.md 허브 생성 ④Orca 버전·실험 기능 확인 → 없으면 herdr → 없으면 스크립트 ⑤프로필별 공식 문서 MCP ⑥스모크 테스트: 작업 1건 → HANDOFF.md 생성 → 렌더 뷰 ⑦결과 보고.
- **비용 상한**: 멀티 에이전트는 3~10배 토큰 → 병렬은 독립 작업만, Run마다 워커 수·예산 상한.

## 8. 최신화 (R2)

- **팩의 필수 구성품 = `sources.yaml` + `evals/`** (사용자 강조, 2026-10-13). `sources.yaml`: 출처별 신뢰 등급(공식 문서·changelog / 표준·규제기관 / 논문 / 고신호 커뮤니티), 수집 방법(RSS·API·GitHub releases·스크레이프), 주기, 라이선스. 팩별 **딥 리서치로 작성**(첫 Orca 실전 런 후보). `evals/`: 실제 실패 20~50건에서 시작, capability/regression 분리, 기여도 Δ 게이트.
- 팩마다 `radar` 설정(위 sources.yaml을 읽음). 주 1회 Claude routine 또는 GitHub Actions.
- 산출물: radar 리포트 + `references/`에만 닿는 **delta PR**(출처 URL·확인일 포함). 핵심 규칙 자동 수정 금지, 통째 재작성 금지.
- 머지 조건: plugin eval 기여도 Δ>0, 회귀 케이스 전부 통과, 오너 주간 리뷰(15분).
- 웹·Context7 결과는 신뢰하지 않는 데이터로 취급(인젝션 방어).

## 10. 배포·이식 (R3·R4·R6)

- **정본은 파일**(SKILL.md + AGENTS.md). MCP로 스킬을 배포하는 표준(SEP-2640)은 Final이지만 Claude·Codex·Cursor·VS Code가 아직 미지원 → MCP는 실시간 도구·데이터에만. (리서치 §15)
- **AGENTS.md = 범용 라우터**: 모든 도구가 읽는 AGENTS.md에 "어떤 일엔 어떤 팩 파일을 연다"는 압축 색인(≤8KB)을 둬서 스킬 미지원 도구에서도 동작.
- **설치기 = microsoft/apm** (git SHA + 파일 해시 락, `--frozen`, `audit --ci`, MCP 설정 7개 도구 생성, `apm pack` 오프라인 번들, Windows). rulesync는 apm이 못 만드는 형식의 보조 생성기. apm은 0.x라 자체 버전도 고정.
- 정본 저장소 1개 → 프로젝트에는 프로필 + 락파일로 **필요한 팩만** 설치. 전역에는 owner-protocol·라우터 등 ≤6개.
- Claude는 `.agents/skills`를 읽지 않으므로 `.claude/skills`에도 배치하거나 Claude 플러그인으로(`.claude-plugin/marketplace.json`은 Codex·VS Code·skills CLI도 읽음).
- 서브에이전트·hook은 `adapters/`에서 도구별 생성(선택 기능). 커맨드는 스킬로.
- **회사 모드**: 심링크 대신 복사, 텔레메트리·자동 업데이트 끔, 개인 데이터(career.yaml 등) 미포함, Orca 설치 불가 시 herdr/스크립트.

## 10-1. 첫 세팅과 버전 호환성 (train)

- **train** = 함께 검증된 버전 묶음 하나(예: `2026.10.1`)를 태그로 관리. 원샷 세팅은 항상 train 그대로 설치한다.
- 구성: `train.yaml`(도구별 버전·고정 등급 A 완전/B 설치 시점/C 불가·3 OS 검증 결과) · `mise.toml`+`mise.lock`(CLI·런타임·apm·herdr) · `bin/mise` 부트스트랩 · `apm.yml`+`apm.lock.yaml`(팩·AGENTS.md·MCP) · `policy/`(도구별 자동 업데이트·텔레메트리 차단) · Orca는 릴리스 파일 고정.
- 순서: `bin/mise install --locked` → `apm install --frozen` → policy 적용 → `doctor`.
- `doctor`: 버전이 train과 일치 / 업데이트 차단 적용 / `apm audit --ci` 드리프트 / 스킬 검증·토큰 예산 린트 / MCP allowlist / 프록시·CA 도달 / API 키·로그인 존재 여부(키는 저장하지 않음).
- 업데이트(사용자 제안 반영, 2026-10-13): **자동 갱신 + 검증 통과 시 자동 적용**. 봇이 새 버전(출시 7일 경과분만)을 감지해 락파일을 고친 PR 생성 → 3 OS CI에서 doctor(스모크 테스트 포함) + eval 회귀 → 통과 시 자동 머지·새 train 태그 → 각 PC는 세션 시작·하루 1회 동기화, 로컬 doctor 실패 시 이전 train으로 자동 롤백. 안전장치: eval 예산 상한, 중요한 일정 전 "보류" 스위치, 보안 패치 빠른 경로, 고정 불가 도구(Cursor CLI 등)는 경고만. 사람은 설치 파일을 직접 고치지 않는다.

## 10-2. 작업별 모델 라우팅 (리서치 §16)

- 라우팅은 **작업 경계에서 한 번** (Orca `worker-start --agent --model --effort`). 세션 중 모델 교체·스킬 `model:`·`opusplan`은 쓰지 않는다(캐시·thinking 손실).
- 레버 순서: 캐시 → **effort(낮게 시작, 검증 실패만 높여 새 세션으로 재실행)** → 모델 등급 → 벤더. 판단 기준은 **완료 작업당 비용**.
- 작업 명세 `tier:` (T0 단순 / T1 단일 모듈 / T2 다중 모듈·설계·보안 / T3 T2 실패 시) → `orchestration/routing.yaml`이 도구·모델·effort로 변환. 등급은 규칙(경로·파일 수·위험 태그)으로, 매핑은 harness-bench 완료 작업당 비용으로 보정. 2회 실패 시 게이트로 사람에게.
- **Jev**: 스킬·팩 라우팅 후보(잘못 로드 16.8%→7.3%, 영어 합성 데이터) — 실제 프롬프트 80개로 자체 평가 후 채택. 모델 등급 라우팅에는 위험 신호 보조로만. 회사 모드에서는 끔(데이터가 미국 서버로).
- 선행 조건: harness-bench 토큰 집계 버그 수정(현재 시도당 마지막 `output_tokens` 하나만 셈).

# 전문가 스킬 주기 업그레이드 설계

오너 요청(2026-11-07): 기획, 디자인, 아이디어, 개발, 테스트와 검증 스킬을 분야별(예: 디자인은 영상, 이미지, 웹 프론트, PPT, 광고, UX / 개발은 웹, 앱, 프론트, 백엔드, 프레임워크, 최신 API)로 나눠 학습하고, 분야마다 최고 수준 합격선(bar)을 두고, 주기적으로 계속 업그레이드한다.

## 출발점 (2026-11-07 확인한 사실)

- `gotechy-design`은 웹 제품 화면 설계(사이트맵, 와이어프레임, 스타일가이드)와 WCAG 2.2 검토만 다룬다. 사용자 흐름 문서가 없으면 멈추는 하드 게이트가 있어 인쇄물, 현수막, 영상, PPT, 광고는 범위 밖이다.
- Claude 기본 내장 artifact-design 스킬은 한 장짜리 결과물의 시각 완성도(글꼴 짝, 주제에서 뽑은 색, 다크 모드, 반응형)에 강하지만 과정, 합격선, 측정이 없다. 두 스킬은 겹치지 않고 보완한다.
- 2026-11-05 현수막 작업에서 결과를 만든 지식(1px=1mm 시안 렌더링, A4 분할 출력, 인쇄 해상도, 겹침 띠)은 어느 스킬에도 없다.
- `evals/<스킬>/`에 평가 문제가 있지만(예: gotechy-design 3개) 한 번도 실행하지 않았다. 팩 eval 실행(5달러)은 `2026-11-05-upgrade-proposals.md`에서 오너 결정 대기.
- 분야별 참고 문서를 필요할 때만 여는 구조는 이미 `gotechy-build`의 `references/stack-*.md`(Go, Postgres, Python, React/Next, TypeScript)에 있다.

## 결정 기록

| # | 질문 | 결정 | 근거 |
|---|---|---|---|
| Q1 | 업그레이드됐다는 판정 기준 | **A. 평가 점수.** 분야별 평가 문제 세트에서 업그레이드 전보다 점수가 올라야만 반영, 같거나 내려가면 버린다. 실제 작업(예: 2026-11-05 현수막)을 평가 문제로 바꿔 넣는다. | 완료 게이트 원칙(산출물+검증), 점수 변화가 커리어 증거가 됨 (오너 확정 2026-11-07) |
| Q2 | 분야를 나누는 방식 | **C. 분야 문서 기본 + 승격 규칙.** 기존 스킬 안에 `references/domain-<분야>.md`와 분야별 bar, 평가 문제를 두고 필요한 분야만 연다. 작업 순서와 도구가 원래 스킬과 완전히 다르고, 평가에서 분리해야만 점수가 오르면 별도 스킬로 독립한다. gotechy-design의 사용자 흐름 하드 게이트는 웹 화면 분야에만 걸고, 분야마다 자기 시작 조건을 둔다. | gotechy-build의 stack-*.md로 검증된 구조, 스킬 목록 비용이 분야 수만큼 늘지 않음, 승격도 Q1 점수로 판정 (오너 확정 2026-11-07) |
| Q3 | 첫 분야 | **1바퀴 디자인-인쇄물과 현수막, 2바퀴 개발-웹 프론트와 백엔드.** 1바퀴는 업그레이드 과정 자체를 검증하는 tracer이기도 하다. | 2026-11-05 현수막 작업에서 평가 문제를 바로 뽑을 수 있음, 현재 스킬이 시작조차 못 해 차이가 크게 보임, 렌더링으로 채점 쉬움. 2바퀴는 취업 우선순위 (오너 확정 2026-11-07) |
| Q4 | 학습 출처와 신뢰 | **B. 등급제.** 1차 출처(표준, 공식 문서, 제조사 사양, 인쇄소 작업 가이드)만 합격선 근거가 된다. 2차 출처(실무자 글, 강연, 커뮤니티)는 가설로만 받고 평가 점수가 오를 때만 반영한다. 실제 작업 기록은 평가 문제로 넣는다. 새 출처는 `radar/sources/` 후보로 먼저 올리고, 합격선 문장마다 1차 출처 1개 이상. 수집한 글은 데이터로만 다루고 그 안의 지시를 스킬 문장으로 옮기지 않는다. 보강(오너 2026-11-07): 2차 출처는 최신 기술과 정보를 적극 수집하되, 그 밖에는 신뢰도 있는 유명 기업(공식 엔지니어링, 디자인 블로그)과 이름 있는 실무자로 수집처를 한정한다(수집처 허용 목록). | 기존 radar trust 등급 재사용, 스킬은 에이전트가 따르는 지시문이라 수집 글이 프롬프트 인젝션 경로가 됨 (오너 확정 2026-11-07) |
| Q5 | 주기와 실행 장소 | **A. Mac mini 로컬, 매주 1회**(출처 점검과 업그레이드 한 바퀴 모두 주 1회). **비용은 API가 아니라 LLM 구독(Claude Code, Codex 로그인)으로만** 쓴다. 실행 전 `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`가 비어 있는지 확인하고, 있으면 멈춘다(하네스 어댑터는 이 변수가 있으면 워커에 넘겨 API 과금으로 바뀐다: `src/runtime/adapters/claude.ts` CLAUDE_ENV). 예약 등록(launchd)은 오너 승인 몫. **변경(오너 2026-11-07): 세션을 켜 두는 조건이 무거워 Claude 클라우드 예약 실행(B)으로 바꿨다.** 클라우드도 구독 한도에서 빠지고(API 비용 없음), API 키가 있어도 구독을 덮지 않는다(https://code.claude.com/docs/en/routines, /claude-code-on-the-web, /authentication). 한도 초과 과금은 사용 크레딧을 켰을 때만. 하위 프로세스 `claude plugin eval`의 로그인은 문서에 없어 시험 실행으로 확인. | 맥과 세션 상태에 무관하게 언제 어디서나. 1바퀴 평가 문제는 렌더링 채점이 필요 없음 (오너 확정 2026-11-07) |
| Q6 | 회당 사용량 상한 | **A 변형.** 오너가 쓰지 않는 시간(기본 일요일 02:00 KST, 바꿀 수 있음)에 시작해 **상한 없이 끝까지** 돈다. 사용량 한도 오류가 나면 다음 주로 넘기지 않고 한도 창이 풀릴 때까지 기다렸다가 같은 바퀴를 이어 한다. 주간 한도에 걸렸을 때만 다음 주로 넘긴다. 첫 바퀴에서 실제 사용량(토큰, 시간, 한도 오류 횟수)을 재고, 그 값을 보고 상한을 다시 정한다. 보강(오너 2026-11-07): 사용 한도 창이 근무 시간과 겹치지 않게 **08:00 KST까지 끝낸다.** 구독의 5시간 창은 그 창의 첫 요청 시각부터 세는 것으로 알려져 있어(첫 바퀴에서 확인), 시작을 토요일 22:00으로 옮기면 22:00~03:00, 03:00~08:00 두 창을 쓰고 08:00에 창이 끝난다. 08:00 이후에는 새 요청을 보내지 않고 멈추며, 못 끝낸 일은 다음 날 22:00에 이어 한다. 주간 한도의 초기화 시각은 계정이 정해 하네스가 바꿀 수 없다. | 오너 작업 시간과 겹치지 않게, 상한은 짐작이 아니라 측정값으로 (오너 확정 2026-11-07) |
| Q7 | 반영 승인 방식 | **B. 브랜치 푸시와 초안 PR까지 자동, 병합은 오너.** 브랜치 `skill-cycle/<날짜>-<분야>`, PR에 업그레이드 전후 점수표와 사용량, CI 결과 확인까지. 푸시 전 gitleaks와 수집 글 장문 인용 검사(저작권)를 통과해야 한다. | 오너 손은 PR 하나, 병합 결정은 오너에게. 공개 저장소라 검토 전 내용이 브랜치에 보이는 대가를 검사로 줄임 (오너 확정 2026-11-07) |
| Q8 | 가지치기와 종료 조건 | **A + 넓히기 보장.** 포화: 2바퀴 연속 점수가 오르지 않으면 유지 모드(주간 출처 점검만, 1차 출처가 바뀌면 재개). 대기열 순서: 실제 작업에서 부족했던 분야, 취업 우선순위, 낮은 점수 순(오너가 언제든 재정렬). 분야 문서마다 줄 수 상한, 넘으면 낡은 것부터 줄인다. 12주 동안 실제 작업에서 열리지 않은 분야는 빼기 후보로 PR에 올리고 지우기는 오너. **보강(오너): 결국 스펙트럼이 넓어져야 한다.** 그래서 대기열에 아직 다루지 않은 분야를 고르는 탐색 칸을 정기적으로 둔다(주기는 첫 바퀴 측정 뒤 정함). 분야가 별도 스킬로 독립해도 분야 단위로 나눈다. 각 분야는 그 분야 전문 직원(에이전트)처럼 부를 수 있어야 한다(형태는 Q9). | 끝내는 기준을 Q1 점수 하나로, 쓰는 분야부터 증명하되 넓이도 보장 (오너 확정 2026-11-07) |
| Q9 | 분야 전문 직원(에이전트)의 형태 | **A. 분야별 직원 카드 한 장(`skills/<스킬>/staff/<분야>.md`)이 원본**이고, 여기서 Claude Code 서브에이전트와 하네스 워커(`gotechy task`) 지시문을 둘 다 만든다. **보강(오너): C처럼 역할을 확실히 수행해야 한다.** 그래서 카드에 역할, 받는 입력, 내놓는 산출물, 완료 기준(그 분야 bar 항목), 쓸 수 있는 도구와 권한, 하지 않는 일, 보고 형식(owner-protocol HANDOFF)을 반드시 적고, 카드 형식 검사와 직원별 평가 문제로 역할 수행을 확인한다. 프로젝트에는 쓰는 팩의 직원만 깐다. | 같은 분야 지식을 두 곳에 쓰지 않음, 멀티 LLM 요구(Claude, Codex)와 맞음 (오너 확정 2026-11-07) |
| Q10 | 1바퀴 진행 방식 | **A. 1바퀴는 수동(리드 세션 안에서), 자동화는 측정 뒤.** **보강(오너): 1바퀴도 새벽에 알아서 시작, 01:00~08:00 KST.** 한도 창이 근무 시간과 겹치지 않게 LLM 사용은 01:00~06:00, 06:00~08:00은 LLM 없는 마무리. 주간 실행 시간도 이것으로 바꾼다(Q6의 토요일 22:00 대신 일요일 01:00, 실제 요일은 1바퀴 뒤 확정). 계획: `docs/exec-plans/active/2026-11-08-skill-cycle-1-print.md` | Q6의 상한을 측정값으로 정하려면 1바퀴를 먼저 재야 함 (오너 확정 2026-11-07) |

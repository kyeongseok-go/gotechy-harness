# evals/ — LLM 기능 골든셋과 실행 규약

> "채점기를 산출물보다 먼저 만든다." LLM 기능이 있는 프로젝트는 이 폴더에 골든셋을 체크인하고, `npm run eval`로 실행한다.
> 실행 불가능한 게이트는 게이트가 아니다 — 러너를 연결하기 전까지 AI 기능의 /gotechy-ship 게이트는 미통과다.

## 케이스 형식 (JSONL — 1줄 1케이스)

```json
{"id": "onboard-001", "input": "사용자 입력 또는 시나리오", "expected_behavior": "관찰 가능한 기대 동작 서술", "rubric": ["사실 정확성", "형식 준수", "다음 행동 안내 포함"], "must_refuse": false, "severity": "critical"}
```

- `id`: 안정적 식별자 (기능-번호)
- `expected_behavior`: 전문가 2명이 독립적으로 같은 판정에 도달할 수준으로 명확하게
- `must_refuse: true`: 거절해야 성공인 케이스 (균형 세트 — 반드시 포함)
- `severity`: `critical`(1건이라도 실패 시 게이트 실패) / `normal`

## 시작 규칙

1. **20개로 시작한다** — 완벽한 셋을 기다리지 않는다. 출처: 실제 실패 사례 > 수동 테스트 절차 > 상상 시나리오.
2. 파일명: `<기능-슬러그>.golden.jsonl` (예: `search-answer.golden.jsonl`)
3. 실사용 실패가 발견될 때마다 케이스로 추가한다 (사고 → 골든셋).

## 통과 기준 (기본값 — 프로젝트별 조정 가능)

- `critical` 케이스 100% 통과
- 전체 루브릭 평균 ≥ 0.85 (LLM-judge 0.0~1.0)
- 직전 실행 대비 회귀 0건
- 신뢰성이 중요한 사용자 대면 기능은 pass^k (k=3 연속 전부 통과), 탐색 도구는 pass@k

## 그레이더 3종

| 그레이더 | 대상 | 주의 |
|---|---|---|
| 코드 기반 | 형식·스키마·금지어·상태 검증 | 빠르고 객관적 — 가능하면 최우선 |
| LLM-judge | 루브릭 항목별 0.0~1.0 | critique 먼저 쓰고 판정. 제작 세션과 격리. 주기적으로 사람과 캘리브레이션 |
| 사람 | 주 1회 트랜스크립트 직접 읽기 | 0% 통과는 대개 태스크/그레이더 결함 신호 |

## 운영

- eval은 **프롬프트·모델·하네스 변경의 게이트** — 통과 없이 승격 금지.
- 통과율 100% 근접 시 회귀 스위트로 졸업시키고 새 난제를 추가한다 (포화 관리).
- 결과 리포트는 `docs/generated/eval-report.md`로 재생성한다 (러너 연결 후 생성되는 파일 — 초기에는 존재하지 않음).

## 러너 연결

`package.json`의 `eval` 스크립트를 실제 러너로 교체한다. 자체 스크립트(judge 호출 + JSONL 집계)나 promptfoo 등 도구 모두 가능 — 도구 선택은 ADR 1건으로 기록.

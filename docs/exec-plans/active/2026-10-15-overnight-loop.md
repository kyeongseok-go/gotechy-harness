# 밤샘 자율 실행 루프 2

오너(고텍이)가 자는 동안 리드(Claude Code, Opus 5.5 xhigh)가 혼자 진행한다. 방식은 첫 밤샘 루프(`2026-10-14-overnight-loop.md`)와 낮 루프(`2026-10-14-day-loop.md`)와 같다. 시작 시각은 이 파일의 커밋 시각이다.

## 목표

1a를 마감할 수 있는 상태로 만들고(apm 전환, 전체 보안 리뷰, 완료 게이트 검사), 1b 중 오너 없이 할 수 있는 마일스톤을 진행한다. 오너가 일어나면 인터랙티브 설명 문서 한 건과 루브릭 문서 한 건으로 "원했던 것, 결정한 것, 만든 것, 지금 되는 것, 확인할 것"을 한 번에 파악할 수 있게 한다.

오너의 요청 "내가 원했던 과정을 인터랙티브한 문서와 루브릭 문서로"는 이렇게 해석했다(오너 확인 필요). 설명 문서는 요구사항(R1~R10)에서 결정(D1~D14, ADR), 구현(1a, 1b), 지금 되는 것까지의 전 과정이다. 루브릭은 요구사항과 스펙 성공 기준마다 단계별 판정 기준, 현재 판정, 근거를 적은 표다.

## 작업 대기열 (위에서부터)

| 순서 | 일 | 완료 판정 |
|---|---|---|
| E1 | `init`의 apm 전환(TD-011, M3 작업 5). 격리 HOME에서 실험 먼저 | 격리 환경에서 `init`이 apm으로 팩을 깔고 `doctor`의 `apm audit --ci` 검사가 통과, 변조하면 실패 |
| E2 | 1a 전체 보안 리뷰(`docs/SECURITY.md` 체크리스트와 security-auditor 7차). 지적 수정 | 높음 0건 남음, 나머지는 부채 |
| E3 | 1a 완료 게이트 검사(`/gotechy-ship` 기능 등급 항목을 손으로) | 부분 점수 보고. 모두 통과하면 1a ExecPlan을 `completed/`로 |
| E4 | 1b N2 `gotechy serve`(가짜 서명 도구로 테스트) | 1b Validation 4, 5와 6의 자동 테스트 |
| E5 | TD-013(프로젝트 공개 키 고정), TD-014(장부 끝줄 방어) | 각 부채의 공격 시나리오가 테스트로 거부됨 |

**문서 시작 규칙:** 마일스톤 하나가 끝날 때마다 `date`를 본다. 05:30이 지났으면 대기열이 남아 있어도 E8로 넘어간다. 대기열을 먼저 끝내면 바로 E8.

## 마일스톤마다 도는 루프

계약 먼저, 실패하는 수용 테스트, 구현, `bun run check`, mutation check, 적대적 리뷰, 기록(ExecPlan, HANDOFF), 커밋과 harness-v2 푸시, CI 확인.

## 멈춤 규칙

- 같은 문제로 3번 실패하면 그 일을 멈추고 HANDOFF를 `failed`로 쓴 뒤, 의존하지 않는 다음 일로 넘어간다.
- 오너만 정할 수 있는 결정은 되돌릴 수 있는 기본값으로 진행하고 커밋을 따로 나눈다. 설명 문서의 "확인 필수"에 올린다.
- CI가 실패하면 다음 일로 가기 전에 고친다.

## 하지 않는 것

- `~/.claude`, `~/.codex` 설정 수정, `gotechy setup` 실제 적용, 실제 `~/.gotechy` 아래 생성이나 수정(지금 있는 `backup/`은 건드리지 않는다)
- force push, 외부 발행, 위키 적재, 배포
- 실제 Claude나 Codex 워커를 부르는 유료 실행, 실제 Orca 워커 실행
- Touch ID 창 띄우기, 실제 오너 키 만들기. 테스트 스위트의 보안 칩 테스트는 화면이 잠겨 있지 않으면 사람 확인 없는 테스트용 키를 임시 폴더에만 만든다(인증 창 없음, 키체인 저장 없음, 낮 루프 규칙과 같음). 처음에 "키 만들기"로 적었다가 01:33에 이 뜻으로 바로잡았다
- 서브에이전트가 `bin/gotechy`나 설치 명령을 실제 HOME으로 실행하는 것. 서브에이전트 지시에 금지 목록과 격리 경로를 반드시 적는다(2026-10-14 비평 에이전트의 실제 `~/.gotechy/bin` 다운로드 사고 재발 방지)

## Validation and Acceptance

1. E1~E7의 각 항목은 완료 판정을 통과했거나, HANDOFF에 멈춘 이유와 다음 단계가 있다.
2. 끝낸 마일스톤마다 `bun run check`가 통과한 커밋이 harness-v2에 있고, 그 커밋의 CI가 성공이다.
3. 보고 폴더에서 HANDOFF가 모두 lint를 통과한다.
4. 설명 문서에 요구사항부터 지금 되는 것까지의 과정, 오늘 밤 한 일, 결정(내린 것, 기본값으로 진행한 것, 남은 것), 오너가 확인할 것이 있다. explain-doc 자체 검사 실패 0건.
5. 루브릭 문서에 요구사항마다 판정 단계, 현재 판정, 근거 파일, 다시 재는 방법이 있다.
6. "하지 않는 것"에 적은 일이 하나도 일어나지 않았다. 끝날 때 `~/.gotechy`의 목록과 두 전역 설정 파일의 해시를 다시 확인한다.

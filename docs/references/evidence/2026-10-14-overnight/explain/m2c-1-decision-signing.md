# 오너 결정에 서명하기 (M2c-1)

## 한 줄로

에이전트가 "오너가 승인했다"고 거짓으로 적거나, 낡은 결과를 보고 내린 결정이 그대로 쓰이는 일을 막으려고, 오너의 결정마다 서명을 붙이고 실행 전에 그 서명을 확인하게 했어요.

## 왜 필요한가

하네스에서 사람의 역할은 결정이에요. 워커가 "캐시 만료를 5분으로 할까요, 1분으로 할까요?"를 HANDOFF에 올리면 오너가 고르고, 다음 실행은 그 결정을 따라요. 그런데 결정이 그냥 텍스트 파일이면 세 가지가 깨져요.

1. 누가 결정 파일을 손으로 고쳐도 알 수 없어요. "5분"을 "1분"으로 바꿔도 그대로 실행돼요.
2. 오너가 본 HANDOFF와 나중의 HANDOFF가 달라도 알 수 없어요. 워커가 결과를 바꾼 뒤에도 옛 결정이 새 결과를 승인한 것처럼 쓰여요.
3. 다른 프로젝트의 결정 파일을 복사해 와도 알 수 없어요.

## 어떻게 동작하나

1. 게이트 열기: `run`이 끝났을 때 HANDOFF에 막는 결정이 있으면, 리드가 결정마다 `orchestration/gates/G-001.md` 같은 게이트 파일을 열어요. `gate: before` 작업은 시작 전에, `gate: after` 작업은 끝난 뒤에 승인 게이트가 열려요.
2. 결정하기: 오너가 터미널에서 `gotechy decide G-001 5분`을 실행해요. 대화형 터미널이 아니면 거부해요. 에이전트가 이 명령을 대신 돌리지 못하게 하려는 장치예요. 질문과 요약을 보여 주고 `y`를 받아야 기록해요.
3. 서명하기: 결정 순간의 내용, 즉 프로젝트 id, 게이트 번호, 질문, 선택지, 고른 것, 작업 명세의 요약값, HANDOFF 파일의 해시, 시각, 일회용 난수(nonce)를 한 줄의 JSON으로 만들고 비밀 키로 HMAC 서명을 계산해 게이트 파일에 같이 적어요.
4. 확인하기: `gotechy gate verify`와 `run`은 게이트 파일에서 같은 JSON을 다시 만들어 서명을 다시 계산해요. 한 글자라도 다르면 서명이 맞지 않아요. 작업 명세나 HANDOFF가 결정 뒤에 바뀌었는지도 해시로 확인해요.
5. 실행 막기: 확인에 실패한 게이트가 걸린 작업은 `run`이 시작하지 않고, 어떤 게이트를 어떻게 다시 결정하면 되는지 알려 줘요.

## 비유

결재 서류에 도장을 찍는 것과 같아요. 도장(서명)은 서류 내용 전체에 걸쳐 찍혀서, 결재 뒤에 금액 한 칸만 고쳐도 도장이 안 맞아요. 서류에는 "어느 회사, 몇 번 결재, 어떤 첨부 문서를 보고 결재했는지"가 같이 적혀 있어서, 다른 회사 서류에 옮겨 붙이거나 첨부 문서를 바꿔치기하면 바로 드러나요. 도장(키)은 오너 서랍(`~/.gotechy/keys`, 다른 사람은 못 읽게 권한 600)에만 있어요.

## 무엇을 막고, 무엇은 못 막나

막는 것 (모두 테스트로 확인했어요):

- 결정 파일을 손으로 고침, 결정 뒤에 질문을 고침
- 같은 판본의 HANDOFF 내용 바꿔치기, 결정 뒤 작업 명세 변경
- 다른 프로젝트의 결정 파일 재사용, 다른 게이트의 nonce 재사용
- 같은 키로 서명한 옛 결정을 되살리기 (nonce가 그 게이트의 마지막 기록이 아니라서 실패)
- 키를 바꾼(`keys rotate`) 뒤 이전 키로 한 결정
- 같은 게이트에 동시에 두 번 결정, 대화형 터미널이 아닌 곳에서 결정
- 다른 사용자가 읽을 수 있는 권한의 키 파일

못 막는 것 (정직하게 적어 둔 한계):

- 오너와 같은 OS 사용자로 도는 악의적인 프로그램은 키 파일을 읽고 스스로 서명할 수 있어요. 같은 사용자 안에서 쓰는 대칭 키 방식의 본질적인 한계라서 1b에서 다뤄요.
- Codex 워커는 샌드박스가 읽기를 막지 않아서 키 파일을 읽을 수 있어요. 키 값이 든 파일을 만들면 리드가 되돌리고 실패로 처리하지만, 근본 해결(키를 보안 칩에 넣기)은 1b예요.
- 보안 감사 두 바퀴의 자세한 내용은 `security-review-rounds.md`에 있어요.

## 직접 해 보기

```text
export GOTECHY_HOME=$(mktemp -d)   # 실제 ~/.gotechy를 건드리지 않는 연습용
gotechy keys init
gotechy run T-001 --adapter fake --fixture tests/fixtures/fake/needs-decision
gotechy inbox
gotechy decide G-001 5분
gotechy gate verify
```

## 면접에서 이렇게 말할 수 있어요

"에이전트에게 일을 맡기면 사람의 결정이 텍스트 파일 하나로 남는데, 그 파일을 누가 고쳐도, 결과물이 결정 뒤에 바뀌어도 알 수 없었습니다. 그래서 결정 순간의 맥락(작업 명세 요약값, 결과물 해시, 프로젝트 id, nonce)을 묶어 HMAC으로 서명하고, 실행 전에 검증하게 했습니다. 위협 모델을 먼저 정해서, 같은 OS 사용자의 악의적 프로세스는 막지 못한다는 한계를 문서에 명시했습니다. 공격 시나리오를 실패하는 테스트로 먼저 고정했고(결정 서명 25개, 보안 감사 뒤 22개 추가), 방어 코드를 하나씩 빼 보는 mutation check 30종으로 테스트가 실제로 잡는지 확인했습니다."

## 새 용어

- HMAC: 비밀 키와 내용을 섞어 만든 지문이에요. 키가 없으면 같은 지문을 만들 수 없고, 내용이 한 글자만 달라도 지문이 달라져요.
- nonce: 한 번만 쓰는 난수예요. 옛 결정을 되살려 다시 쓰는 재사용 공격(replay)을 잡는 데 써요.
- canonical JSON: 키 순서와 공백을 정해진 규칙으로 맞춘 JSON이에요. 같은 내용이면 언제나 같은 글자가 나와야 서명을 다시 계산할 수 있어요.
- TOCTOU: 확인한 시점과 사용하는 시점 사이에 내용이 바뀌는 문제예요. 영어 `time of check to time of use`의 머리글자예요.
- 위협 모델: 무엇을 지키고, 누구로부터, 어디까지 막을지 먼저 정한 목록이에요.

# 이해 게이트와 병합 (M2c-2)

## 한 줄로

되돌리기 어려운 결정은 "말해 보기" 질문에 자기 말로 답해야 서명되고, 승인한 작업은 `gotechy accept`가 메인을 망가뜨리지 않는 방식으로 병합해요.

## 1. 이해 게이트

### 왜 필요한가

에이전트가 일을 잘할수록 사람은 읽지 않고 "y"만 누르게 돼요. 인증, 스키마, 배포처럼 되돌리기 어려운 변경에서 이런 일이 생기면 위험해요. 그래서 이런 결정만큼은 서명하기 전에 HANDOFF의 "말해 보기" 질문에 자기 말로 답하게 했어요.

### 어떻게 동작하나

- 대상: 작업 명세에 `irreversible: true`가 있거나, 바꾸는 경로에 `auth`, `schema`, `migration`, `security`, `deploy`, `.github/workflows/`가 들어간 작업이에요. 명세에 `false`라고 적혀 있어도 경로 규칙이 이겨요. 게이트 파일의 값을 손으로 꺼도, `decide`가 명세와 경로로 다시 계산해요.
- 질문: HANDOFF "말해 보기"의 질문을 하나씩 물어요. 빈 답도 받지만, 답하는 단계는 건너뛸 수 없어요.
- 채점: 워커가 HANDOFF에 `comprehension_keys`(질문마다 좋은 답에 들어갈 핵심어)를 적어 두면, 답에 그 핵심어가 몇 개 들어 있는지 세요. 이 핵심어는 인박스와 화면에 보이지 않아요. 보이면 시험지에 답이 적혀 있는 셈이에요.
- 기록: 답과 적중 수는 `orchestration/private/comprehension.jsonl`에만 남아요(공개 저장소에 올라가지 않는 폴더). 게이트 파일에는 "2문항, 핵심어 3개 중 2개 적중" 같은 요약만 남아요.

### 무엇을 재나

스펙의 성공 지표가 "HANDOFF 한 건을 3분 안에 이해하고 결정, 핵심어 적중률 60% 이상"이에요. 그래서 측정값도 같이 남겨요.

- `opened_at`: 인박스나 화면이 이 게이트를 처음 보여 준 시각
- `active_seconds`: 확인 질문을 보여 준 때부터 답할 때까지 걸린 초
- 핵심어 적중 수

## 2. `gotechy accept`

### 왜 필요한가

워커는 자기 작업 브랜치(worktree)에서 일해요. 결과가 좋아도 그 변경은 아직 메인에 없어요. 그래서 승인한 결과를 메인에 합치는 단계가 필요했어요. 이 단계를 설계하다가 원래 규칙의 버그도 하나 찾았어요. 선행 작업이 done이기만 하면 뒤 작업이 시작했는데, 그러면 뒤 작업은 선행 작업의 결과가 없는 메인에서 일하게 돼요. 그래서 선행 조건을 "accepted(메인에 병합됨)"로 바꿨어요.

### 어떻게 동작하나

1. 조건 확인: 작업이 done이고, 리드 verify를 통과했고, 필요한 게이트가 모두 검증을 통과했고, 승인 게이트가 있으면 "승인"이어야 해요.
2. 임시 작업대: 메인의 현재 커밋으로 임시 worktree를 하나 더 만들고, 거기서 작업 브랜치를 병합해요. 메인은 아직 건드리지 않아요.
3. 기록 빼기: 병합 결과에서 `orchestration/` 변경은 빼요. 작업 명세, HANDOFF, 게이트는 리드의 기록이라 메인 체크아웃에만 두고, 병합하는 것은 워커가 바꾼 파일뿐이에요.
4. 다시 검증: 병합한 결과에서 작업의 verify를 다시 돌려요. 따로는 잘 되던 두 작업이 합쳐지며 깨지는 경우를 여기서 잡아요. 이 verify도 샌드박스 안에서 돌아요.
5. 반영: 모두 통과하면 메인을 그 병합 커밋으로 앞으로 옮겨요(fast-forward). 충돌이나 verify 실패면 메인은 그대로 두고, 작업을 needs-decision으로 바꾸고 사유를 남겨요.
6. 정리: 작업 worktree를 지우고, 작업 상태를 accepted로 바꾸고, HANDOFF "새 용어"의 풀이 중 은행에 없는 것을 프로젝트 용어 은행에 더해요.

### 비유

공사 현장 옆에 가설 작업대를 세우고, 거기서 새 부품을 끼워 시운전까지 한 다음에야 본 건물에 옮기는 것과 같아요. 시운전에서 문제가 나면 본 건물은 손대지 않은 채로 남아요.

## 3. 인박스에서 바로 보이게

- 결정 줄에 게이트 번호가 붙어요: `결정 G-001: 캐시 만료를 얼마로 할까요? (추천 5분)`
- HANDOFF가 아직 없는, 시작 승인만 기다리는 작업도 카드로 보여요.
- 승인을 기다리는 done 작업은 "결정 필요" 묶음으로 올라와요.
- 병합이 끝난 작업은 인박스에서 빠져요.

## 아직 안 되는 것

- 병합이 충돌로 멈춘 작업을 새 메인 위에서 다시 하는 명령이 없어요(TD-006).
- 무시 파일(.gitignore 대상)의 변경은 허용 범위 검사에 잡히지 않아요(TD-007).

## 새 용어

- fast-forward: 메인에 새 커밋이 없을 때, 메인의 위치만 앞으로 옮기는 병합이에요. 새 병합 커밋을 만들지 않아요.
- worktree: 한 저장소를 여러 폴더에 동시에 펼쳐 두는 git 기능이에요.
- fail-closed: 판단할 수 없으면 막는 쪽을 택하는 설계예요. 반대는 fail-open이에요.

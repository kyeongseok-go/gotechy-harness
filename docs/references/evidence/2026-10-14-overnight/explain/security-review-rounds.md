# 보안 감사 두 바퀴에서 배운 것 (M2c)

## 한 줄로

결정 서명은 처음부터 튼튼했는데, 뚫린 곳은 그 둘레였어요. 워커가 쓴 코드를 리드가 대신 실행하는 순간(verify)이 가장 큰 구멍이었고, 첫 수정도 두 번째 감사에서 다시 뚫렸어요.

## 어떻게 진행했나

1. 결정 서명(M2c-1)을 테스트와 함께 만들었어요. 테스트 30개가 처음 구현에서 한 번에 통과했어요.
2. 읽기 전용 감사 에이전트에게 "적대적으로" 검토를 맡겼어요(1차). 높음 3, 중간 3, 낮음 4건이 나왔어요.
3. 지적마다 공격을 실제로 해 보는 테스트를 먼저 쓰고(13개 모두 실패), 고쳤어요.
4. 고친 코드를 다시 감사에 맡겼어요(2차). 1차 수정의 빈틈에서 높음 3건이 또 나왔어요.
5. 같은 방식으로 테스트 9개를 먼저 쓰고(모두 실패) 고쳤어요.
6. 방어 코드를 한 줄씩 일부러 빼 보는 mutation check를 30종 돌려, 테스트가 정말 그 방어를 검사하는지 확인했어요. 두 번 살아남은 결함이 있었고, 그때마다 테스트를 보강했어요.

## 1차 감사: 무엇이 뚫렸나

| 등급 | 문제 | 비유 | 고친 방법 |
|---|---|---|---|
| 높음 | verify가 워커가 쓴 테스트 코드를 오너 권한으로 실행했어요. 그 코드가 서명 키를 읽고 결정을 위조할 수 있었어요 | 수리공이 두고 간 "점검용 리모컨"을 집주인이 눌렀더니 금고가 열린 것 | verify를 macOS 샌드박스에 가둬요 |
| 높음 | HANDOFF 자리에 심볼릭 링크를 두면, 리드가 링크를 따라가 게이트 파일을 덮어썼어요 | 보고서함에 "이 보고서는 금고 안 서류다"라는 쪽지를 넣었더니 비서가 금고 서류를 덮어쓴 것 | 워커가 만든 링크는 모두 되돌리고 실패로 처리해요 |
| 높음 | 필요한 게이트를 "지금 있는 게이트 파일"에서 정해서, 파일을 지우면 검사도 사라졌어요(fail-open) | 결재 서류가 없으니 결재할 것도 없다고 판단한 것 | 필요한 게이트를 작업 명세와 HANDOFF에서 계산하고, 빠지면 다시 열어요(fail-closed) |

## 2차 감사: 첫 수정이 왜 부족했나

첫 샌드박스는 "기본은 다 허용, 프로젝트 쓰기와 키 읽기만 금지"였어요. 감사는 이렇게 짚었어요.

- verify가 홈 폴더의 git 설정 파일을 고쳐 두면, 리드가 나중에 샌드박스 밖에서 git을 돌릴 때 그 설정이 오너 권한으로 실행돼요. 막은 곳 옆으로 돌아 들어온 거예요.
- 변경 범위 검사가 verify보다 먼저 끝나서, verify가 만든 파일(보호 경로 포함)은 검사 없이 브랜치에 커밋됐어요.
- worktree의 `.git` 파일을 verify가 바꾸면 리드의 git이 엉뚱한 곳을 봐요.

그래서 원칙을 뒤집었어요. 쓰기는 기본 거부하고 작업 폴더만 허용해요. 네트워크는 끊고, 환경 변수는 허용 목록만 넘겨요. 순서도 바꿨어요. 워커 변경을 먼저 커밋하고, verify를 돌리고, verify가 남긴 것은 모두 지운 뒤, HANDOFF 하나만 커밋해요. 리드가 쓰는 git은 전역 설정과 훅을 읽지 않게 했어요.

## 3차 확인과 M3 리뷰

- 3차(2차 수정의 재검토): 파일 쓰기, 네트워크, 환경 변수, 산출물 커밋은 막혔다고 확인받았어요. 새로 나온 높음은 "워커가 worktree의 `.git` 연결 파일을 바꾸면 리드의 git이 워커가 준비한 설정을 따른다"였어요. 그래서 워커가 끝나면 git을 부르기 전에 연결 파일과 설정 목록(포함 파일까지)을 실행 전과 비교하고, 바뀌었으면 되돌린 뒤 그 실행은 git 없이 실패로 끝내요.
- M3 리뷰: 전역 설정을 바꾸는 코드라 따로 받았어요. 가장 큰 문제는 hook 경로였어요. 저장소 안 폴더를 hook 경로로 쓰면, 남이 만든 저장소에 숨겨 둔 hook이 다음 checkout 때 실행돼요. hook을 저장소 밖으로 옮겼어요.

## 배운 것

- 허용 목록이 금지 목록보다 안전해요. "이것만 막자"는 늘 옆길이 있어요. 첫 샌드박스가 그랬어요.
- 검사는 "마지막으로 바뀐 뒤"에 해야 해요. 검사 뒤에 실행되는 코드가 있으면 검사가 무효가 돼요(높음 B).
- 없는 것을 "문제없음"으로 읽으면 안 돼요(fail-closed). 인박스의 "리스크 기록 없음"과 같은 원칙이에요.
- 테스트가 한 번에 통과하면 오히려 의심해야 해요. mutation check로 확인하니 두 군데는 테스트가 실제로 방어를 검사하지 않고 있었어요.
- 고친 코드도 다시 감사받아야 해요. 2차에서 높음이 다시 나왔고, 3차에서도 하나가 더 나왔어요. 감사는 "막혔다"고 확인해 주는 역할도 해요.
- 남이 만든 저장소는 신뢰하지 않는 입력이에요. 그 안의 설정 파일(hook, gitleaks 설정)을 그대로 쓰면 검사를 끄거나 코드를 실행하게 돼요.

## 아직 못 막는 것 (정직하게)

계약 6.3절 "알려진 한계"에 적었어요. 핵심은 하나예요. 키가 파일이라서, 오너와 같은 OS 사용자로 도는 프로그램(특히 디스크를 읽을 수 있는 Codex 워커)은 키를 읽을 수 있어요. 리드가 키 값이 든 파일은 되돌리지만, 근본 해결은 키를 맥 보안 칩(Secure Enclave)에 넣고 서명마다 Touch ID를 받는 것이고, 1b ExecPlan의 첫 마일스톤으로 잡았어요.

## 면접에서 이렇게 말할 수 있어요

"에이전트 하네스에 사람 결정 서명을 넣고, 읽기 전용 감사 에이전트로 두 바퀴 적대적 리뷰를 돌렸습니다. 1차에서 '워커가 쓴 테스트를 리드가 오너 권한으로 실행한다'는 구멍이 나와 샌드박스로 막았는데, 2차에서 그 샌드박스가 금지 목록 방식이라 홈 설정 파일로 우회할 수 있다는 지적이 나왔습니다. 그래서 쓰기 기본 거부, 네트워크 차단, 환경 변수 허용 목록으로 바꾸고, 검사와 실행 순서도 고쳤습니다. 모든 지적을 실패하는 공격 테스트로 먼저 고정했고, 방어 코드를 하나씩 빼는 mutation check 53종으로 테스트의 실효성을 확인했습니다."

## 새 용어

- fail-open, fail-closed: 판단할 수 없을 때 통과시키면 fail-open, 막으면 fail-closed예요. 보안 장치는 닫히는 쪽이어야 해요.
- 샌드박스(sandbox): 프로그램이 할 수 있는 일(파일, 네트워크)을 정해진 범위로 가두는 장치예요.
- 허용 목록(allowlist): 정해진 것만 허용하고 나머지는 모두 막는 방식이에요. 반대는 금지 목록(denylist)이에요.
- 하드 링크: 같은 파일 내용에 이름을 하나 더 붙이는 것이에요. 심볼릭 링크와 달리 링크인지 겉으로 잘 드러나지 않아요.

## 말해 보기

- verify 뒤에 부산물을 지우는 것이 왜 필요한가요? 이번 실행이 아니라 다음 실행에서 무슨 일이 생기나요?

# 보안 감사 11차

대상은 밤 계획 E5의 미커밋 변경이었어요. 프로젝트 고정 키(TD-013), 장부 끝 기록(TD-014), `gotechy keys pin`이에요. 감사는 읽기 전용 security-auditor 서브에이전트가 했고, 리드가 지적을 고친 뒤 테스트와 mutation check로 확인했어요.

결과는 높음 0, 중간 2, 낮음 6, 계약과 코드 어긋남 6건이에요.

## 지적과 처리

| 등급 | 지적 | 처리 |
|---|---|---|
| 중간 1 | 끝 기록의 위치가 환경 변수(`GOTECHY_HOME`, `HOME`)를 따라서, 프로젝트만 쓰는 쪽이 가짜 끝 기록으로 검사를 통과할 수 있음 | 프로젝트 명령은 그 위치가 프로젝트 안이면 exit 2. 프로젝트 밖(`/tmp` 등)을 가리키는 경우는 못 막아 TD-019로 남김 |
| 중간 2 | 고정 파일의 임시 파일 이름이 예측 가능하고 링크를 따라가, 미리 심은 링크로 저장소 밖 파일을 덮어씀 | 임시 이름에 난수, `wx`로 만듦. 같은 패턴의 게이트 파일 쓰기 두 곳도 함께 고침 |
| 낮음 1 | `keys pin`이 보여 준 장부와 실제로 믿는 장부가 다를 수 있음(TOCTOU) | 잠금 안에서 보여 준 장부와 해시를 대조하고, 다르면 아무것도 바꾸지 않음. Touch ID를 거는 보강은 TD-021 |
| 낮음 2 | `keys pin` 요약에 장부 줄의 줄바꿈으로 가짜 줄을 끼울 수 있음 | 게이트 번호와 시각은 형식을 본 값만 보여 줌. 장부 서명 상태 줄을 더함 |
| 낮음 3 | 장부 줄을 쓴 뒤 단계가 실패하면 잘못된 상태와 안내가 남음 | 끝 기록을 못 쓰면 장부를 되돌림. 잠금 해제 실패는 기록을 실패로 바꾸지 않음. serve는 장부 줄만 남은 경우를 "결정을 끝내지 못했어요"로 구분 |
| 낮음 4 | 장부와 끝 기록을 따로 읽어 동시 결정 중 거짓 경보가 날 수 있음 | 끝 기록, 장부, 끝 기록 순서로 읽고 바뀌었으면 다시 읽음. decide는 기대 내용(읽은 장부와 새 줄)으로 끝 기록을 씀 |
| 낮음 5 | 고정 파일이 커밋됐는지 아무도 보지 않고, serve의 첫 결정은 커밋 안내가 없음 | serve도 안내. `gate verify`가 고정 파일이 커밋되지 않았거나 커밋과 다르면 경고 |
| 낮음 6 | 보호 경로를 대소문자 구분으로 비교(확인 필요) | 실험이 필요해 TD-020으로 남김 |

계약 어긋남 6건은 `contract.md` 6.3, 6.4, 8.3절에서 고쳤어요. 고친 내용은 이렇게 셋이에요.
- 끝 기록이 잡는 범위를 "프로젝트 폴더만 되돌리는 쪽"으로 좁혔어요.
- "검증은 어디서나 된다"를 "결정한 맥과 그 폴더에서만 `ok`"로 바꿨어요.
- 여러 맥을 오가는 결정은 지원하지 않는다고 적었어요.

## 실험: Bun의 계정 홈 조회

중간 1을 고치려고 홈을 계정 정보(`os.userInfo().homedir`)에서 읽게 바꿨어요. 하지만 다른 프로세스로 `HOME`을 바꿔 띄운 실험에서 그 값도 바뀐 `HOME`을 돌려줬어요. 효과가 없어서 이 변경은 되돌렸고 TD-019로 남겼어요. 처음 쓴 테스트는 같은 프로세스 안에서 `process.env.HOME`만 바꿔서 이 사실을 놓쳤어요. 별도 프로세스 테스트로 바꾼 뒤에 드러났어요.

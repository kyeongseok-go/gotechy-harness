# 오류 분석과 골든셋

언제 여는 파일인가: 절차 2단계(오류 분석)와 3단계(골든셋)를 할 때, 케이스 형식이나 크기, 분할을 정할 때.

## 1. 오류 분석: 채점기보다 먼저 데이터를 읽는다

근거: Hamel Husain과 Shreya Shankar의 evals FAQ(https://hamel.dev/blog/posts/evals-faq/, 2026-09-18 발행, 2026-09-21 수정)는 오류 분석을 eval의 출발점으로 둔다. 그들이 일한 프로젝트에서는 개발 시간의 60~80%가 오류 분석과 평가에 들었다. Shankar 외의 EvalGen 연구(arXiv 2404.12272)는 "출력을 채점하려면 기준이 필요하지만, 출력을 채점해 봐야 기준이 정해진다"는 기준 표류(criteria drift)를 보고했다. 기준을 출력을 보기 전에 다 정할 수 없다는 뜻이다.

### 순서

1. **트레이스 모으기.** 트레이스는 사용자 첫 입력부터 최종 응답까지의 모든 메시지, 도구 호출, 검색 결과 기록이다. 운영 로그가 있으면 사용자 유형과 작업 흐름이 고르게 섞이도록 100개 안팎을 뽑는다. 출시 전이면 차원(사용자 유형, 의도, 난이도, 입력 길이)을 정하고 조합마다 입력을 만들어 직접 돌린다.
2. **직접 읽고 메모.** 품질 결정권자 1명(오너나 도메인 전문가)이 처음 30개 이상을 직접 읽는다. 트레이스마다 통과, 실패 하나와 "사용자 입장에서 무엇이 이상한가"를 자유 메모로 쓴다. 원인 분석은 미룬다. 모델 탓이 아닌 문제(기능 누락, 링크 없음)도 적는다.
3. **묶기.** 메모를 비슷한 것끼리 묶어 실패 유형 이름을 붙이고 유형별 개수를 센다. 이 표가 실패 분류표다. AI에게 묶기를 맡겨도 되지만 유형의 정의와 최종 판정은 사람이 한다.
4. **포화까지 반복.** 새 트레이스를 읽어도 새 유형이 안 나오고 기존 유형의 정의도 안 바뀌면 멈춘다(이론적 포화). 대개 100개 안팎이다.
5. **고칠 것과 잴 것 나누기.** 프롬프트 한 줄, 코드 수정으로 고칠 수 있는 실패는 바로 고친다. 고친 뒤에도 남거나 다시 나올 위험이 큰 실패만 자동 채점기 후보로 올린다. 채점기를 만들 때마다 비용 대비 효과를 따진다.

### 실패 분류표 양식 (`error-analysis.md`)

| 실패 유형 | 정의 (통과와 실패를 가르는 한 문장) | 개수 / 읽은 수 | 예시 트레이스 ID | 조치 (고침, 채점기, 보류) |
|---|---|---|---|---|
| 없는 정책 지어내기 | 정책 문서에 없는 환불 조건을 사실처럼 말하면 실패 | 7 / 60 | t-014, t-031 | 채점기 (judge) |

## 2. 골든셋 케이스 형식 (JSONL, 1줄 1케이스)

```json
{"id": "refund-001", "input": "사용자 입력 또는 대화", "context": "필요하면 검색 결과나 상태", "expected_behavior": "관찰 가능한 기대 동작", "failure_modes": ["없는 정책 지어내기"], "must_refuse": false, "severity": "critical", "split": "dev", "source": "prod", "reference": "통과하는 기준 답 또는 판정 근거", "tags": ["security"]}
```

- `id`: 기능-번호. 바꾸지 않는다.
- `expected_behavior`: 도메인 전문가 2명이 따로 봐도 같은 판정이 나올 만큼 구체적으로. Anthropic은 좋은 과제의 조건을 "두 전문가가 독립적으로 같은 통과, 실패 판정에 이르는 것"으로 든다.
- `must_refuse`: 거절하거나 행동하지 않아야 성공인 케이스.
- `severity`: `critical`(1건이라도 실패하면 승격 불가) 또는 `normal`.
- `split`: `dev`(프롬프트 수정에 써도 됨) 또는 `test`(승격 판정 때만 연다).
- `source`: `prod`(운영 실패), `manual`(수동 테스트 절차), `synthetic`(만든 것).
- `reference`: 통과하는 기준 답. 과제가 풀 수 있는 것인지, 채점기가 맞게 설정됐는지 확인하는 데 쓴다(Anthropic 권장).
- 개인정보는 가린 뒤 넣는다.

## 3. 크기

| 단계 | 크기 | 근거 |
|---|---|---|
| 첫 골든셋 | 20개 | Anthropic: 실제 실패에서 뽑은 20~50개 단순 과제면 좋은 출발. 초기에는 변경 효과가 커서 작은 표본으로 충분하다 |
| 오류 분석 | 처음 30개 이상 직접 라벨, 100개 안팎에서 포화 확인 | Husain, Shankar FAQ |
| judge 검증용 사람 라벨 | 실패 유형마다 100~200개 권장. 최소선은 50개(하네스 기본값) | Husain, Shankar FAQ |
| 반복 실행 셋 | 중요한 흐름과 확인된 실패가 쌓여 100개 이상으로 자란다 | Husain, Shankar FAQ |

작은 셋으로 작은 차이를 판정하지 않는다. 20개 셋에서 1개 차이는 5%p지만 그 크기는 표준오차와 비슷해 잡음과 구별되지 않는다(계산은 `references/run-and-compare.md`).

## 4. 균형

- 행동해야 하는 케이스와 하지 말아야 하는 케이스를 둘 다 넣는다. Anthropic은 한쪽만 시험하면 한쪽으로만 최적화된다고 경고한다. 예: "검색해야 할 때 검색하는가"만 시험하면 거의 모든 질문에 검색하는 에이전트가 나온다.
- 하지 말아야 할 행동(거절, 도구 호출 안 하기, "모른다"고 말하기) 케이스가 전체의 20% 이상(하네스 기본값).
- 모르는 것을 아는지 재려면 답할 수 있는 질문과 답할 수 없는 질문을 비슷한 비율로 섞는다(Husain, Shankar FAQ).

## 5. 과적합 막기

1. **분할.** 케이스의 20% 이상을 `test`로 둔다(하네스 기본값). 프롬프트를 고칠 때는 `dev`만 본다. dev 결과로 프롬프트나 모델을 고를 때마다 dev 정보가 시스템에 스며든다. 그래서 dev에서는 좋은데 새 입력에서는 나쁜 상태가 프롬프트에 dev 예시를 직접 넣지 않아도 생긴다(Husain, Shankar FAQ).
2. **격차 감시.** dev 통과율과 test 통과율의 차이가 10%p를 넘으면 과적합을 의심하고 원인을 적는다(하네스 기본값).
3. **few-shot 금지.** 골든셋 케이스를 프롬프트 예시로 옮기지 않는다. 옮겼다면 그 케이스를 셋에서 빼고 새 케이스로 바꾼다.
4. **새 피 넣기.** 운영 실패를 7일 안에 케이스로 옮기고, 한 달에 한 번 운영 트레이스에서 새 케이스를 뽑는다. 오래돼 현재 사용과 맞지 않는 케이스는 이유를 적고 뺀다.
5. **통과율 100%를 쫓지 않는다.** FAQ는 100% 통과면 시스템을 충분히 시험하지 않는 것이고 70%가 더 의미 있을 수 있다고 쓴다. capability 셋이 2회 연속 95% 이상이면 회귀 스위트로 옮기고 더 어려운 케이스를 넣는다(하네스 기본값).

## 6. capability 셋과 회귀 셋

- capability(품질) 셋은 "이 에이전트가 무엇을 잘하나"를 묻고 낮은 통과율에서 시작해 올라갈 언덕을 준다. 회귀 셋은 "전에 되던 것이 아직 되나"를 묻고 거의 100% 통과해야 한다. capability 셋의 통과율이 높아지면 회귀 셋으로 졸업한다(Anthropic, `Demystifying evals for AI agents`, 2026-01-09).
- 파일에서는 `tags`에 `capability` 또는 `regression`을 붙여 나눈다.

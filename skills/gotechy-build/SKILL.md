# gotechy-build: 계획을 작고 검증된 변경으로 바꾼다

최고 수준의 엔지니어는 코드를 많이 쓰는 사람이 아니라, 리뷰어가 한 번에 이해하고 되돌릴 수 있는 작은 변경을 테스트로 증명하며 쌓는 사람이다. 이 스킬은 어떤 스택에서든 그 습관을 강제한다. 스택마다 다른 버전, 엄격 설정, 도구, 함정은 `references/stack-*.md`에 있고, 프로젝트가 쓰는 스택의 파일만 연다. 그래서 Go와 PostgreSQL만 쓰는 프로젝트는 TypeScript 문서를 읽지 않는다.

## 언제 쓰나, 쓰지 않나

- 쓴다: 승인된 스펙(`docs/product-specs/<슬러그>.md`)이나 ExecPlan(`docs/exec-plans/active/<날짜>-<슬러그>.md`)의 마일스톤을 코드로 옮길 때, 버그 수정, 리팩터링, 의존성 추가, DB 마이그레이션.
- 쓰지 않는다: 아이디어 단계(`gotechy-spec`), 큰 기능이나 제품인데 ExecPlan이 없는 작업(`gotechy-plan`), 화면 설계(`gotechy-design`), 완료 판정(`gotechy-ship`), 보안 리뷰 자체(`gotechy-security`).
- 수용 기준이 없으면 구현하지 않는다. 수용 기준 초안 3개 이상을 만들어 "결정 필요"로 올린다.

## 작업 크기 (`gotechy-spec`, `gotechy-plan`, `gotechy-ship`과 같은 표)

| 크기 | 기준 | 스펙 | 계획 | 출시 게이트 |
|---|---|---|---|---|
| 패치 | 1시간 미만, 파일 1~2개, 동작 계약 불변 | 없음 | 없음 | 패치 등급 |

| 큰 기능 | 1일 이상, 또는 사용자 데이터, 인증, 결제, 외부 발행을 건드림 | 풀 스펙 | ExecPlan | 기능 등급 |
| 제품 | 화면 여러 개나 새 프로젝트 | 위저드 | ExecPlan | 기능 또는 출시 등급 |

## 절차

1. **크기 판정.** 위 크기 표로 패치, 작은 기능, 큰 기능, 제품 중 하나를 먼저 알린다. 작은 기능은 미니 스펙의 수용 기준 목록을, 큰 기능과 제품은 ExecPlan을 입력으로 삼는다. 애매하면 큰 쪽으로 잡는다. 산출물: 판정 한 줄.
2. **스택 판별.** 저장소 루트와 변경할 폴더에서 아래 단서를 찾고, 맞는 reference만 연다. 산출물: "판별: Go, PostgreSQL. 연 파일: stack-go, stack-postgres" 한 줄.

   | 단서 파일 | 여는 파일 |
   |---|---|
   | `tsconfig.json`, `package.json`에 `typescript` | `references/stack-typescript.md` |
   | `package.json`에 `react` 또는 `next`, `next.config.*` | `references/stack-react-next.md` (TS면 위 파일도) |
   | `pyproject.toml`, `uv.lock`, `requirements*.txt` | `references/stack-python.md` |
   | `go.mod` | `references/stack-go.md` |
   | `migrations/*.sql`, `schema.prisma`의 `postgresql`, compose 파일의 `postgres` 이미지, `.env.example`의 `postgres://` | `references/stack-postgres.md` |

   - 비밀 파일(`.env`, 키 파일)은 단서로도 열지 않는다. 예시 파일만 본다.
   - 모노레포는 이번 변경이 닿는 패키지의 단서만 본다.
   - 표에 없는 스택이면 `references/bar.md`의 일반 기준만 쓰고, 그 스택의 공식 문서에서 현재 안정 버전, 린터, 테스트 러너를 확인해 HANDOFF 증거에 적는다.
   - 프로젝트에 이미 정한 도구(린터, 포매터, 러너, 버전)가 reference 권장보다 우선한다. 다르면 바꾸지 않고 차이를 "결정 필요"의 `[알림]`으로 남긴다.
3. **변경 쪼개기.** 수용 기준을 변경 단위로 나눈다. 한 변경은 관심사 하나이고, 리팩터링과 동작 변경을 섞지 않는다(구조를 먼저 바꾸고 동작을 나중에 바꾼다). 목표는 변경 하나에 100줄 안팎이고, 400줄(생성 코드, lockfile 제외)을 넘으면 다시 쪼갠다. 산출물: 변경 목록, 각 줄에 "무엇을, 어떤 테스트로".
4. **실패하는 테스트 먼저(RED).** 수용 기준이나 버그 재현을 테스트로 옮기고, 실행해서 기대한 이유로 실패하는 것을 본다. 산출물: 실패 출력의 핵심 한 줄(HANDOFF 증거에 넣는다).
   - 예외 1, 동작을 모르는 외부 경계(외부 API, CLI, OS 기능): 작은 실험으로 실제 동작을 먼저 확인하고, 결과를 ExecPlan의 Surprises에 적은 뒤, 확인한 동작을 테스트(녹화 응답 재생)로 고정한다.
   - 예외 2, 테스트할 동작이 없는 변경(문서, 설정값 이동, 순수 이름 바꾸기): 기존 테스트 전체 통과로 대신한다.
   - 예외를 쓰면 이유를 HANDOFF "한 일"에 적는다. 예외 없이 구현부터 쓰지 않는다.
5. **최소 구현(GREEN), 그다음 정리(REFACTOR).** 테스트를 통과시키는 가장 단순한 코드를 쓰고, 통과 상태를 유지하며 중복과 이름을 정리한다. 테스트의 기대값을 구현에 맞춰 고치지 않는다. 산출물: 통과 출력.
6. **경계에서 파싱.** HTTP 요청, 폼, URL 파라미터, 환경변수, 파일, 외부 API 응답, DB 행, LLM 출력은 들어오는 지점에서 한 번 스키마로 파싱해 내부 타입으로 바꾼다. 안쪽 코드는 검증된 타입만 받는다. 실패는 그 지점에서 명확한 오류로 끝낸다.
7. **의존성은 규칙대로.** 표준 라이브러리나 이미 있는 의존성으로 되면 넣지 않는다. 넣을 때는 레지스트리와 소스 저장소에서 진짜 패키지인지(비슷한 이름, AI가 지어낸 이름) 확인하고, 정확한 버전을 고정하고, lockfile을 같은 변경에 넣고, 유지보수, 라이선스, 알려진 취약점, OpenSSF Scorecard를 확인한다. 런타임 의존성 추가는 ADR 한 건과 "결정 필요" `[기본값]`으로 올린다. 산출물: 의존성 표 한 줄(이름, 버전, 라이선스, 마지막 릴리스, 취약점 수, Scorecard). 판정 기준은 `references/bar.md`의 의존성 절.
8. **자기 리뷰.** diff 전체를 처음부터 끝까지 다시 읽고 `references/code-review.md` 체크리스트를 돈다. 디버그 출력, 주석 처리한 코드, 추적 번호 없는 TODO, 비밀, 사유 없는 검사 끄기(`@ts-ignore`, `# type: ignore`, `//nolint`)를 지운다. 산출물: 체크리스트 결과(통과 수/전체).
9. **게이트 명령 실행.** 포맷 검사, 린트, 타입 검사, 테스트(커버리지 포함), 빌드를 프로젝트에 정의된 명령으로 돌린다. 명령이 없으면 "없음"이 아니라 실패로 보고한다. 산출물: 명령과 종료 코드.
10. **기록과 보고.** ExecPlan이 있으면 Progress와 Surprises를 갱신한다. 남긴 부채는 `docs/exec-plans/tech-debt-tracker.md`(없으면 만든다)에 적는다. 보고는 `owner-protocol` 스킬의 HANDOFF 형식을 따른다.

## ADR을 쓰는 때

ADR은 gotechy-plan이나 gotechy-retro의 틀로 쓴다. 파일은 `docs/decisions/NNNN-<슬러그>.md`(폴더가 없으면 만든다)이고, 상태는 "제안됨"으로 두고 오너 결정으로 올린다. 아래 중 하나면 쓴다.

<!-- gotechy:adr-when:start -->
- 되돌리는 데 하루 이상(하네스 기본값) 걸린다: 데이터 모양, 저장소, 프레임워크, 공개 API 계약, 파괴적 마이그레이션.
- 새 런타임 의존성, 저장소, 큐, 외부 서비스를 들인다.
- 인증, 인가, 비밀 처리 방식을 바꾼다.
- 여러 모듈이나 바깥 사용자에게 영향이 간다.
- 진지하게 비교한 선택지가 2개 이상 있었고, 6개월 뒤 누군가 "왜 이렇게 했지?"라고 물을 만하다.
- 같은 논쟁이 두 번 이상 나왔다.
<!-- gotechy:adr-when:end -->

## 기준 요약 (전체와 판정 등급은 `references/bar.md`)

1. 동작을 바꾸는 변경은 실패를 먼저 확인한 테스트와 함께 온다. 버그 수정은 재현 테스트가 먼저다.
2. 변경 하나는 관심사 하나다. 리뷰어가 한 번에 읽고 되돌릴 수 있는 크기다.
3. 외부 입력은 경계에서 파싱한다. 안쪽에서 같은 검증을 반복하지 않는다.
4. 에러는 삼키지 않는다. 처리하거나, 맥락을 붙여 올리거나, 기록하고 다시 던진다.
5. 타입 검사와 린터는 엄격 설정에서 경고 0이다. 끄려면 줄 단위로 사유를 단다.
6. 의존성은 정확한 버전과 lockfile로 고정하고, 추가 근거를 남긴다.
7. 비밀은 코드, 로그, 테스트 고정값에 없다. 설정은 환경에서 읽는다.
8. 코드와 문서는 한 몸이다. 동작이 바뀌면 스펙, README, ADR을 같은 변경에서 고친다.

## 산출물과 저장 위치

| 산출물 | 위치 |
|---|---|
| 코드와 테스트 | 프로젝트 구조를 따른다 |
| 진행 기록 | `docs/exec-plans/active/YYYY-MM-DD-<슬러그>.md`의 Progress, Surprises (있을 때) |
| ADR | `docs/decisions/NNNN-<슬러그>.md` (없으면 만든다) |
| 부채 | `docs/exec-plans/tech-debt-tracker.md` (없으면 만든다) |
| 보고 | `owner-protocol` 스킬의 HANDOFF |

HANDOFF에는 이렇게 채운다. "한 일"은 변경 단위마다 한 줄(`[확인]` 표지). "증거"는 RED 실패 한 줄, GREEN 통과, 린트, 타입 검사, 커버리지 수치를 `` `명령`: 결과`` 형식으로. "결정 필요"는 의존성 추가, 스펙과 코드의 모순, 기존 도구와 reference의 차이. 리스크 절에는 예외로 처리한 테스트와 확인 못 한 경계를 적는다.

## 완료 기준

- 수용 기준마다 테스트가 하나 이상 있고, 전부 통과한 출력이 증거에 있다.
- 게이트 명령(포맷, 린트, 타입, 테스트, 빌드)이 모두 종료 코드 0이다.
- `references/code-review.md` 체크리스트를 자기 리뷰에서 전부 통과했거나, 미달 항목이 부채로 기록됐다.
- 인증, 인가, API, DB, 개인정보를 건드렸으면 `gotechy-security` 스킬로 리뷰를 넘겼다고 "다음 단계"에 적었다. 크기와 무관하다.
- 완료 판정 자체는 `gotechy-ship` 스킬이 한다. 이 스킬은 "구현 완료, 게이트 대기"까지 책임진다.

## 하지 않는 것

- 실패하는 테스트를 보기 전에 구현부터 쓰지 않는다(4단계 예외 제외).
- 테스트를 지우거나 기대값을 바꿔서 통과시키지 않는다. 스펙이 틀렸다고 보이면 `[막는]` 결정으로 올린다.
- `latest`, `*`, 범위 지정(`^`, `~`, `>=`)으로 새 의존성을 넣지 않는다. lockfile 없이 설치하지 않는다.
- 요청하지 않은 기능, 추상화, 범위 밖 리팩터링을 더하지 않는다. 보이면 부채로 적는다.
- flaky 테스트를 주석 처리로 숨기지 않는다. skip하고 부채에 기록한다.
- 커밋, push, 배포, 마이그레이션의 운영 적용은 사용자가 명시적으로 지시했을 때만 한다.

결과를 오너에게 설명할 때는 `references/lens.md`를 연다. 다른 사람의 변경을 리뷰할 때도 `references/code-review.md`를 쓴다.

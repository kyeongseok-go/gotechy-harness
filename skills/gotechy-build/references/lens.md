# 렌즈: 구현 결과를 오너에게 설명하기

구현 결과를 오너(부모님과 AI 초심자도 읽는다)에게 설명할 때 연다.

## 대표 그림

- 신호등 순환: 빨강(실패하는 테스트), 초록(통과하는 최소 코드), 정리(같은 초록 유지). 변경마다 한 바퀴.
- 검문소 그림: 바깥(요청, 파일, 외부 API)에서 들어온 값이 입구 한 곳에서 검사받고, 안쪽에는 확인된 값만 다닌다.
- 변경 크기 막대: 변경 단위별 줄 수 막대와 400줄 선. 선을 넘는 막대가 없어야 한다.

## 비유 후보

- 식당 주문서: 요리(코드) 전에 주문서(실패하는 테스트)를 먼저 쓴다. 주문서와 다르게 나온 접시는 바로 보인다.
- 택배 송장: 접수 창구(경계)에서 주소를 한 번 확인하면, 배송 기사(안쪽 코드)는 주소를 다시 의심하지 않는다.
- 가계부와 영수증: lockfile은 "무엇을 몇 원에 샀는지" 영수증 그대로 적은 가계부다. 다음 달에도 같은 물건을 다시 산다.

## 꼭 풀어야 할 용어

| 용어 | 쉬운 설명 |
|---|---|
| TDD | 실패하는 테스트를 먼저 쓰고, 그걸 통과시키는 코드를 쓰는 순서 |
| diff | 이번 변경에서 바뀐 줄만 모아 보여 주는 비교표 |
| 경계에서 파싱 | 바깥에서 온 값을 입구에서 한 번 검사해 믿을 수 있는 모양으로 바꾸기 |
| lockfile | 설치한 라이브러리의 정확한 버전을 적어 둔 영수증 파일 |
| 리팩터링 | 겉동작은 그대로 두고 코드 속 정리만 하는 일 |
| 린터 | 실수하기 쉬운 코드 모양을 자동으로 찾아 주는 맞춤법 검사기 |
| ADR | 왜 이렇게 정했는지 남기는 한 장짜리 결정 기록 |
| 마이그레이션 | 이미 데이터가 든 DB의 구조를 순서대로 바꾸는 작업 |

## 선택해 보기 후보

"새 라이브러리 하나면 30분 만에 끝나요. 직접 짜면 3시간이에요. 대신 라이브러리는 1년째 업데이트가 없어요. 어느 쪽을 고를까요?" (정답 없음. 유지보수 신호, 라이선스, 되돌리는 비용을 함께 보게 한다.)

## 면접 꼬리 질문

1. 테스트를 먼저 쓰면 무엇이 달라지나요? 나중에 쓴 테스트가 놓치는 버그 예를 하나 들어 보세요.
2. "경계에서 파싱"과 "곳곳에서 검증"의 차이를 실제 코드 예로 설명해 보세요.
3. 의존성을 하나 추가할 때 무엇을 확인했고, 그 판단을 어디에 남겼나요?

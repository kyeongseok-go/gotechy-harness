# 상태 매트릭스와 화면 문구

> 50-wireframe에서 데이터 섹션과 폼을 쓸 때, 검토 모드에서 상태와 문구를 판정할 때 연다.

해피 패스만 그린 화면은 절반이다. 데이터를 보여 주는 섹션(`Table`, `CardGrid`, `StackedList`, `StatCards`, `DetailView`, `ProductList`, `ReviewList`)과 폼 섹션은 아래 8가지 상태를 모두 적는다. 해당이 없으면 "해당 없음: 이유"를 쓴다. 빈 상태는 시스템 상태를 알리고, 배울 단서를 주고, 핵심 작업으로 가는 길을 바로 준다(NN/g 빈 상태 3지침).

## 상태 8종

| 상태 | 언제 | 설계 규칙 | 다음 행동 예 |
|---|---|---|---|
| 로딩 | 응답 대기 | 아래 로딩 규칙 | 기다림, 10초 넘으면 취소 |
| 첫 사용 빈 상태 | 아직 만든 것이 없음 | 여기에 무엇이 생기는지 한 줄과 시작 버튼 1개 | "첫 예약 만들기" |
| 결과 없음 | 검색, 필터 결과 0건 | 적용한 조건을 보여 주고 조건을 푸는 링크 | "필터 모두 해제" |
| 복구 가능 오류 | 일시 장애, 시간 초과 | 무엇이 안 됐는지와 다시 시도, 입력값 유지 | "다시 시도" |
| 복구 불가 오류 | 사용자가 고칠 수 없는 서비스 문제 | 사실과 대안 경로(연락처, 나중에 하기), 입력값 보존 | "고객센터에 문의" |
| 부분 실패 | 일부 항목만 실패 | 성공분은 그대로 보이고 실패분만 인라인 재시도 | "이 항목 다시 불러오기" |
| 오프라인 | 네트워크 끊김 | 상단 배너, 읽기는 마지막 데이터로, 쓰기는 비활성 또는 대기열과 그 표시 | "연결되면 자동으로 보내요" |
| 권한 없음 | 로그인 필요(401) 또는 권한 부족(403) | 401은 로그인 뒤 원래 화면으로 복귀, 403은 누구에게 권한을 요청하는지 안내 | "로그인하기", "관리자에게 권한 요청" |

함께 적을 것:

- 성공 피드백(저장됨, 보냄)과 그 위치.
- 낙관적 업데이트가 실패하면 원래 값으로 되돌리고 알리는 경로.
- 파괴적 행동(삭제, 해지)의 되돌리기 또는 확인 단계. 확인 버튼은 행동 이름으로 쓴다.

## 로딩 규칙

- 대부분 1초 안에 끝나는 요청은 로딩 UI를 따로 그리지 않는다. 1초 미만이면 skeleton과 spinner가 필요 없다(NN/g). 그래도 표시가 필요하면 400ms가 지나도 응답이 없을 때만 띄워 깜빡임을 막는다(Doherty 임계 400ms).
- 화면 전체를 불러올 때는 실제 배치와 같은 모양의 skeleton을 쓴다(대기 10초 미만). 머리글과 바닥글만 있는 빈 틀 skeleton은 쓰지 않는다.
- 카드 하나, 영상 하나 같은 부분 모듈의 2~10초 대기는 spinner로 충분하다.
- 10초를 넘는 작업(업로드, 변환)은 진행률 막대와 남은 시간을 보인다. 전체 양을 모르면 처리한 항목 수를 보인다.
- 진행, 성공, 오류 알림은 포커스를 옮기지 않고도 보조기기가 읽게 `role="status"`, 급한 오류는 `role="alert"`로 둔다(WCAG 4.1.3).

## 폼 규칙

- 라벨은 늘 보이게 입력란 밖에 둔다. placeholder는 형식 예시로만 쓰고 라벨 대신 쓰지 않는다(NN/g).
- 검증 시점의 기본은 제출 때다. 오류가 있으면 화면 위에 오류 요약을 띄우고 키보드 포커스를 그리로 옮기고, 페이지 제목 앞에 "오류: "를 붙인다(GOV.UK). 입력 중에는 검증하지 않는다.
- 실시간 검증은 형식이 까다로운 필드(카드 번호, 사업자 번호)에서 근거가 있을 때만 더한다. 그때는 사용자가 필드를 떠난 뒤에 검사하고, 오류가 뜬 뒤에는 키 입력마다 다시 검사해 고치는 즉시 오류를 지운다(Baymard). GOV.UK는 필드를 떠날 때 검증하지 말라고 하고 Baymard는 떠날 때 검사하라고 해서 두 출처가 갈린다. 이 bar는 제출 검증을 기본으로 두고 실시간 검증은 사용성 근거를 Q&A 로그에 남겼을 때만 쓴다.
- 오류가 나도 입력값을 지우지 않는다(GOV.UK, NN/g).
- 같은 과정에서 이미 받은 정보를 다시 입력하게 하지 않는다. 자동으로 채우거나 고를 수 있게 준다(WCAG 3.3.7).
- 로그인 단계에서 기억이나 퍼즐 풀기만 요구하지 않는다. 붙여넣기와 비밀번호 관리자를 막지 않는다(WCAG 3.3.8).
- 이름, 이메일, 전화, 주소 입력란에는 맞는 `autocomplete` 값을 둔다(WCAG 1.3.5).
- 오류를 색만으로 알리지 않는다. 텍스트로 무엇이 틀렸는지 쓰고 아이콘을 함께 둔다(WCAG 1.4.1, 3.3.1).

## 오류 문구 규칙

무엇이 잘못됐는지와 어떻게 고치는지를 쓴다. 쉬운 말로 쓰고 사용자를 탓하지 않는다(GOV.UK, NN/g). 상황마다 다른 문구를 쓴다. 뭉뚱그린 문구는 아무것도 돕지 않는다.

| 유형 | 문형 | 예 |
|---|---|---|
| 비었음 | 행동 지시 | "이름을 입력하세요" |
| 너무 김, 짧음 | 범위 설명 | "이름은 35자 이하로 입력하세요" |
| 형식 틀림 | 맞는 형식 설명 | "휴대폰 번호를 010-1234-5678 형식으로 입력하세요" |
| 범위 밖 | 허용 범위 | "날짜는 오늘부터 90일 안에서 고르세요" |
| 서비스 문제 | 사실과 대안 | "예약을 저장하지 못했어요. 입력한 내용은 그대로 있어요. 1분 뒤 다시 시도하세요" |

쓰지 않는 문구: `오류가 발생했습니다`, `잘못된 입력입니다`, `유효하지 않은 값`, `필수 항목입니다`, `앗`, `이런`, 기술 용어(`500 Internal Server Error`, `null`, `undefined`). 사과는 서비스 잘못일 때만 짧게 한다.

- 필드 오류 문구는 라벨과 힌트 다음에 둔다. 오류 요약과 필드 문구는 같은 문장을 쓴다(GOV.UK).
- 자격 미달, 권한, 서비스 장애처럼 사용자가 고칠 수 없는 문제는 필드 오류 형식을 쓰지 않는다. 서비스 문제 화면, 페이지 없음 화면으로 안내한다(GOV.UK).

## 그 밖의 문구 규칙

- 버튼은 동사와 목적어로 쓴다: "예약 취소하기". 확인 대화상자도 "예, 아니오" 대신 행동 이름을 쓴다: "삭제하기", "그대로 두기".
- 한 제품 안에서 말투는 하나다(예: 해요체). 같은 대상은 같은 낱말로 부른다(NN/g 휴리스틱 4, 일관성과 표준).
- 날짜와 금액은 한국어 관례를 따른다: "2026년 10월 16일", "12,000원". 상대 시각("3분 전")에는 정확한 시각을 보조 텍스트로 둔다.
- 빈 수식어(`혁신적인`, `강력한`, `차세대`, `원활한`)는 쓰지 않고 수치나 사례로 바꾼다.

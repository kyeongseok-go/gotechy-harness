# 위저드 진행 규칙 (설계 단계 40, 50, 60)

> 위저드를 시작할 때, 질문을 고를 때, 승인을 받을 때, 상류 문서를 고칠 때 연다.

## 스테이지 체인

`gotechy-spec` 스킬이 00~30을, 이 스킬이 40~60을 맡는다. 산출물은 모두 `docs/product-specs/<슬러그>/` 한 폴더에 번호 순으로 쌓이고 서로 링크된다.

```text
00-brief, 10-prd, (15-quality-goals), 20-features, 30-user-flow   gotechy-spec, gotechy-quality
40-sitemap, 50-wireframe, 60-style-guide                         gotechy-design
그다음 ExecPlan                                                   gotechy-plan
```

- 화면이 없는 제품(CLI, 라이브러리)은 40~60을 건너뛴다.
- 기능 하나짜리 작은 작업은 위저드가 아니라 미니 스펙 경로다. 위저드는 제품, 사이트 단위다.

## 제1원칙: 상위 산출물이 하위 생성의 입력이다

사이트맵의 섹션 한 줄이 와이어프레임의 입력이고, 브리프의 톤 한 줄이 스타일가이드의 입력이다. 그래서 수정은 되도록 상류에서 한다. 텍스트 한 줄을 고치는 비용이 화면을 다시 만드는 비용보다 훨씬 싸다. 각 스테이지는 이전 산출물이 확정되지 않으면 시작하지 않는다(하드 게이트).

## 질문 엔진

1. 스테이지당 질문은 5개 이하다. 영향과 불확실성이 모두 큰 것만 묻는다. 구조, 데이터, UX, 완료 판정을 바꾸는 질문만 하고 사소한 취향은 추천안으로 정한다.
2. 선택지가 기본이다. 선택지 2~4개, 추천안 표시, "왜 묻는지" 한 줄을 붙인다. Claude Code에서는 AskUserQuestion 도구를 쓰고, 그 도구가 없으면 번호 목록으로 묻는다. 열린 질문은 짧게 답할 수 있게 좁힌다.
3. 한 질문에 한 축만 묻는다. 스타일을 물을 때 색을 같이 묻지 않는다.
4. 모든 질문에 기본값을 붙인다. "추천대로"만 답해도 진행된다. "나중에 바꿀 수 있어요"를 적어 결정 부담을 낮춘다.
5. 답을 받으면 그 자리에서 문서를 고치고 모순되는 옛 문장은 지운다. 문서 하단 `## Q&A 로그`에 `- Q: 질문 / A: 답` 한 줄씩 남긴다.
6. 추측하지 않는다. 물을 만큼 중요하지 않지만 확실하지 않은 것은 본문에 `[NEEDS CLARIFICATION: 질문]` 마커를 남긴다. 스테이지 확정 조건은 마커 0개다.

## 승인 락

- 스테이지 끝에 산출물 요약을 보이고, 명시 승인("확정", "다음", "yes")을 받기 전에는 다음 스테이지로 가지 않는다.
- 수정 요청을 받으면 바꿀 부분을 전과 후로 보이고, 승인받고, 반영하고, 다시 승인을 청한다. 여러 스테이지를 한 턴에 합치지 않는다.
- 승인은 문서 하단 `## 확정 이력`에 `- YYYY-MM-DD 확정: 오너 승인 문구` 형식으로 남긴다.
- 확정 뒤 변경은 그 스테이지를 다시 열고 하류에 전파한다(아래 SYNC).
- 진행 위치를 매 턴 밝힌다: `[위저드 40-sitemap, 5/7]`.

## 되돌아가기 (SYNC 마커)

상류 문서를 고치면 영향받는 하류 문서의 해당 위치에 즉시 `[SYNC NEEDED: 40-sitemap에서 '요금' 페이지 삭제 반영]` 마커를 넣는다. 하류 재생성은 자동으로 하지 않고 "이어서 갱신할까요?"로 묻는다. SYNC 마커가 남아 있으면 완료 게이트(`gotechy-ship` 스킬)에서 걸린다.

## 탈출구

- `--quick`: 승인 없이 세 스테이지 초안을 한 번에 만든다. 질문 대신 추천안을 쓰고, 추천안을 적용한 자리마다 Q&A 로그에 "추천안 적용"을 남긴다. 확실하지 않은 것은 마커로 남기므로 검토는 결국 해야 한다. `--quick`이어도 하드 게이트(30-user-flow)는 그대로다.
- 체크포인트: 양이 많은 스테이지(사이트맵, 와이어프레임)는 Home 한 장만 먼저 만들어 방향을 확인받고 이어 간다.

## 스테이지별 확정 기준

| # | 산출물 | 입력 | 확정 기준 |
|---|---|---|---|
| 40 | sitemap | 30-user-flow의 페이지 노드 | 노드와 페이지 1:1, 마케팅 페이지 4~8섹션, 앱 화면 3~8섹션, 섹션마다 한 줄 설명, IA 트리, 마커 0 |
| 50 | wireframe | 40의 섹션 줄 | 어휘 안 타입과 변형축, 실제 카피, 데이터 섹션 상태 8종, 폼 필드 표, 375px 배치, 인터랙션과 흐름 엣지 연결, 마커 0 |
| 60 | style-guide | 브리프의 톤, 50의 카피 | 성격 축 4개와 미학 서술문, 라이트와 다크 역할 색 대비 값, 타입 스케일, 간격, radius 2단계, 모션, DTCG 토큰 블록, 마커 0 |

## 40-sitemap 진행

1. 30-user-flow의 페이지 노드 표를 뼈대로 페이지 트리를 만들고 브리프의 페이지 목록과 대조한다. 흐름에 없는 페이지를 넣으려면 이유를 Q&A 로그에 남긴다.
2. 페이지마다 목표 한 줄을 쓴다. 첫 화면은 "무엇이고 무엇을 하면 되는지"가 목표다.
3. 섹션 줄을 쓴다: `` `[타입]` 제목: 한 줄 설명 ``. Navbar, Footer는 `@global`로 한 번만 쓴다.
4. 내비 라벨은 사용자가 쓰는 말로 쓴다(NN/g 휴리스틱 2, 실제 세계와 맞추기). 1차 내비 항목이 7개를 넘으면 묶거나 이유를 남긴다(Hick의 법칙: 선택지가 많을수록 결정이 느려진다).
5. 페이지가 20개 이상이거나 내비 깊이가 3단 이상이면 레이아웃 전에 tree testing을 제안한다(NN/g: 콘텐츠와 레이아웃을 만들기 전에 구조를 검증).
6. 지금 다듬자고 안내한다. 섹션 한 줄이 와이어프레임의 입력이라 지금 고치는 비용이 가장 싸다.

## 50-wireframe 진행

1. 디바이스 기준(모바일 우선, 데스크톱 우선)을 선택지로 먼저 정한다. 대상 사용자 다수가 휴대폰을 쓰면 모바일 우선이 추천안이다.
2. 사이트맵 섹션 줄과 1:1로 섹션 스펙을 채운다. 표기는 `타입 · 변형축`(예: `Hero · Media · Split`)이고 요소마다 실제 카피를 쓴다.
3. 카피에 브리프의 톤과 출처 있는 수치를 녹인다. 확보하지 못한 실물(고객 로고, 후기)은 `[NEEDS CLARIFICATION]`으로 둔다.
4. 데이터 섹션은 상태 매트릭스를, 폼 섹션은 필드 표를 채운다(`references/states-and-content.md`).
5. 인터랙션 행은 30-user-flow의 엣지와 연결한다.
6. 섹션마다 375px 배치를 한 줄 적는다. 쌓는 순서를 정하고, 모바일이라고 정보를 숨기지 않는다.
7. 사이트맵을 고치게 되면 양쪽 문서에 SYNC 마커를 넣는다.

## 60-style-guide 진행 (한 스텝 한 축)

1. 성격 축 4개(Modern과 Classic, Playful과 Serious, Bold와 Soft, Calm과 Energetic, 각 5단계)를 묻고 미학 서술문 한 문장으로 묶는다. 이 문장은 이후 모든 화면 생성 지시에 넣는다.
2. 레퍼런스 2~4개를 받는다. 색 말고 스타일(여백, 글자 위계, 밀도)을 보고 가져올 것과 가져오지 않을 것을 적는다.
3. 색 계열(차분한, 선명한, 무채색과 포인트 하나, 어두운 바탕과 밝은 포인트)을 먼저 고르고 구체 색은 다음 스텝에서 정한다.
4. 역할 색(Text, Background, Primary, Secondary, Accent, 상태색)을 라이트와 다크 모두 정하고 대비를 계산해 적는다. 미달인 색은 후보에서 뺀다.
5. 타이포: 헤딩과 본문 폰트(한글 글리프와 폴백 스택 포함), 고른 이유 한 줄, 타입 스케일 프리셋.
6. 형태와 모션: radius 2단계, 간격 밀도, 그림자, 모션 수준. 성격 축과 맞는지 확인한다.
7. 확정하면 DTCG 토큰 블록을 붙이고 CSS 변수 2층으로 옮길 일을 ExecPlan에 넘긴다. 그 뒤 토큰의 진실의 원천은 코드이고 이 문서는 결정 근거 기록이 된다.

수치 규칙, 대비 합격선, 계산 스크립트는 `references/tokens.md`에 있다.

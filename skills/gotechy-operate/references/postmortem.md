# 포스트모템

사후 모드에서 연다. `docs/operations/postmortems/YYYY-MM-DD-<슬러그>.md`를 아래 틀로 만든다.

## 1. 언제 쓰나

Google SRE 책의 트리거다. 하나라도 맞으면 쓴다. 기준은 사고 전에 정해 두고, 누구든 요청할 수 있다.

- 사용자에게 보인 장애나 성능 저하가 정한 기준(예: 5분)을 넘었다.
- 데이터를 조금이라도 잃었다.
- 당번이 개입했다(롤백, 트래픽 돌리기, 플래그 끄기).
- 해결 시간이 정한 기준을 넘었다.
- 감시가 실패했다. 알림이 아니라 사람(사용자 신고 포함)이 먼저 발견했다.
- 사고 하나가 4주 오류 예산의 20%를 넘게 썼다(오류 예산 정책).

## 2. 원칙

- **blameless.** 모든 사람이 그때 가진 정보로 선의로 행동했다고 가정한다. "누가 실수했나"가 아니라 "무엇이 그 행동을 그럴듯하게 만들었나"를 쓴다.
- **빨리.** 초안은 24시간 안(하네스 기본값), 리뷰 완료는 7일 안이다. SRE Workbook의 좋은 예는 일주일 안에 돌렸고, 나쁜 예는 넉 달 뒤에 한 팀 안에서만 돌렸다.
- **리뷰받는다.** 리뷰받지 않은 포스트모템은 없던 것과 같다. 1인 개발이면 다른 모델의 에이전트나 동료 한 명에게 "영향 수치가 있나, 원인이 충분히 깊나, 조치가 원인을 막나"를 물어 리뷰로 삼는다.
- **조치가 있어야 한다.** 조치가 따르지 않는 포스트모템은 포스트모템이 없는 것과 구분되지 않는다(Workbook이 인용한 Ben Treynor Sloss의 말).
- **사람보다 시스템을 바꾼다.** "앞으로 조심한다"보다 "이 실수를 할 수 없게 검사를 넣는다"를 고른다.
- **공개 저장소 주의.** 최종 사용자를 알아볼 수 있는 정보, 내부 주소, 비밀을 넣지 않는다. 커밋 전에 gitleaks로 검사한다.

## 3. 틀

```markdown
# 포스트모템: <한 줄 제목, 증상 중심>

상태: 초안 | 리뷰 중 | 완료
사고 기간: YYYY-MM-DD HH:MM ~ HH:MM KST (N분)
심각도: SEV-N
작성: <이름> / 리뷰: <이름, 날짜>

## 요약
<3줄: 무엇이, 얼마나 오래, 누구에게, 어떻게 복구했나>

## 영향
- 영향받은 사용자: <수 또는 비율, 추정이면 추정 근거>
- 실패한 요청: <수>, 오류 예산 사용: <분, 4주 예산 대비 %>
- 데이터 손실: <없음 또는 범위>
- 매출, 지원 문의 등 다른 영향: <수치>

## 타임라인 (KST)
<사고 기록을 그대로 옮기고, 감지, 선언, 첫 공지, 완화, 복구 시각을 굵게>

## 감지
<무엇이 먼저 알려 줬나(알림, 사용자 신고). 알림이 늦었거나 없었다면 왜>

## 원인
- 직접 계기(trigger): <예: 14:02 배포의 설정 키 이름 변경>
- 근본 원인(root cause): <계기가 장애가 되게 한 시스템 조건. 예: 설정 키 누락을 배포 전에 잡는 검사가 없었다>
- 기여 요인: <장애를 키우거나 복구를 늦춘 것>

## 잘된 것, 아쉬운 것, 운이 좋았던 것
- 잘된 것:
- 아쉬운 것:
- 운이 좋았던 것:

## 조치 항목
| 조치 | 종류(예방/완화/감지) | 우선순위 | 담당(1명) | 추적 번호 | 끝 상태(확인 방법) |
|---|---|---|---|---|---|

## 배운 것
<한두 줄. 블로그 소재가 될 만하면 "소재:"로 시작하는 줄을 하나 더>
```

## 4. 조치 항목 쓰는 법

| 나쁜 예 | 좋은 예 |
|---|---|
| 모니터링 개선 | 결제 API 오류율이 1시간 창 burn rate 14.4배를 넘으면 호출하는 규칙 추가. 끝 상태: 규칙 파일에 있고 시험 알림이 울림 |
| 배포 시 주의 | 배포 전 `.env.example`과 배포 환경 키를 대조하는 CI 단계 추가. 끝 상태: 키를 하나 지운 PR에서 CI가 실패 |
| 테스트 보강 | 설정 키 이름 변경을 잡는 계약 테스트 1개. 끝 상태: 옛 키 이름으로 되돌리면 테스트 실패 |

- 담당은 한 명이다. 여러 명이면 아무도 안 한다.
- 사용자 영향이 있었으면 최우선 조치가 1개 이상이다.
- 조치마다 추적 번호(이슈나 `docs/exec-plans/tech-debt-tracker.md`의 ID)를 단다.
- 예방 조치(다시 안 생기게)를 최소 1개 넣는다. 완화(덜 아프게)와 감지(빨리 알게)만으로 끝내지 않는다.

## 5. 문장 검사

리뷰 전에 아래를 확인한다.

- 원인 절에 사람 이름이 없다. "실수", "부주의", "깜빡", "잘못 판단" 같은 말이 없다.
- 느낌표, 과장("최악의", "재앙")이 없다.
- 처음 보는 사람도 읽을 수 있게 내부 용어를 한 줄로 풀었다.
- 영향에 수치가 있다. 정확하지 않으면 "추정"과 근거를 단다. 잘 추정한 값이 아무 값도 없는 것보다 낫다.

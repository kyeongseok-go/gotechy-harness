# 런북과 백업, 복원 리허설

준비 모드 8~9단계, 점검 모드의 복원 리허설에서 연다. 런북은 `docs/operations/runbooks/<이름>.md`에 하나씩 둔다.

## 1. 왜 런북인가

Google SRE 책은 미리 생각해 적어 둔 플레이북이 즉흥 대응보다 MTTR(복구까지 걸리는 평균 시간)을 약 3배 줄인다고 쓴다. 새벽 2시의 나는 낮의 나와 다른 사람이다. 런북은 그 사람을 위한 글이다.

## 2. 런북 틀

```markdown
# 런북: <알림 이름 또는 작업 이름>

마지막 검토: YYYY-MM-DD (90일마다 다시 본다) / 마지막 사용: YYYY-MM-DD

## 언제
<이 런북을 여는 조건. 알림 이름, 증상>

## 사용자 영향
<이 알림이 울릴 때 사용자가 겪는 일. 심각도 기본값>

## 판단 (3분 안)
1. <가장 흔한 원인부터 확인하는 질문과 명령>
2. 직전 배포나 설정 변경이 10분 안에 있었나? 있으면 롤백 런북으로.

## 명령
    <복사해 붙이면 그대로 도는 명령. 값을 바꿔야 하는 자리는 <대괄호>로>

## 확인
    <복구됐는지 보는 명령이나 대시보드 링크, 기대 값>

## 넘길 곳
<혼자 못 풀 때 연락할 곳: 호스팅 지원, 외부 API 지원, 동료. 연락 방법>

## 기록
- YYYY-MM-DD: <사용하면서 틀렸던 곳과 고친 내용>
```

규칙:

- 호출 알림마다 런북이 있어야 하고, 알림 규칙의 주석에 런북 경로를 단다.
- 명령은 실제로 돌려 본 것만 적는다. 돌려 보지 못했으면 "(검증 전)"을 붙이고 다음 리허설에서 확인한다.
- 런북을 쓰다 막힌 곳은 그 자리에서 고치고 "기록"에 남긴다.
- 기본으로 갖출 런북: `rollback.md`(직전 배포 되돌리기, `gotechy-ship`과 같은 파일), `restore.md`(백업 복원), `secret-rotation.md`(비밀 회전), `read-only.md`(쓰기 경로 막기), 호출 알림마다 하나.

## 3. RPO와 RTO 정하기

AWS Well-Architected REL13-BP01의 정의다.

- **RPO**: 마지막 복구 지점에서 사고까지, 잃어도 되는 최대 시간. "최대 몇 분치 데이터를 잃어도 되나".
- **RTO**: 서비스가 멈춘 뒤 되살아날 때까지 견딜 수 있는 최대 지연.

정하는 질문:

1. 이 저장소가 몇 시간 멈추면 사용자와 사업에 무엇이 생기나? 돈, 신뢰, 운영, 법적 영향을 모두 본다.
2. 몇 분치 데이터를 잃으면 감당할 수 없나? 다른 원본에서 다시 만들 수 있는 데이터인가?
3. 이 서비스가 기대는 외부 서비스의 복구 능력보다 엄격한 목표는 아닌가?
4. 법이나 계약이 요구하는 보존과 무결성이 있나? 있으면 `gotechy-comply-kr` 스킬로 확인한다.

피하는 것(AWS가 꼽는 안티패턴): 목표를 안 정함, 근거 없이 정함, "0초, 손실 0"처럼 달성할 수 없게 정함, 사업 필요보다 지나치게 엄격하게 정해 비용만 키움.

## 4. 백업 기본값 (하네스 기본값)

- 배포 전 스냅샷과 일일 백업, 최소 7일 보존.
- 관리형 DB(Neon, Supabase, RDS 등)는 시점 복구(PITR)를 켜고, 보존 기간을 RPO에 맞춘다.
- 파괴적 마이그레이션 전에는 백업이 있는지 명령으로 확인하고, 그 출력을 ExecPlan이나 PR에 남긴다.
- 백업은 원본과 다른 계정이나 다른 지역에 한 벌 둔다. 같은 계정 안의 백업은 계정 사고 때 함께 사라진다.

## 5. 복원 리허설 (분기 1회, 90일 이내)

AWS REL09-BP04의 절차를 줄였다. "복원했다"로 끝내지 않고, 데이터를 조회해 검증하고, 시간을 잰다.

1. **새 위치에 복원한다.** 운영 DB를 덮어쓰지 않는다. 스테이징이나 임시 인스턴스에 복원한다.
2. **검증 기준을 미리 정한다.** 행 수, 체크섬, 가장 최근 레코드의 시각, 핵심 테이블 몇 개의 표본 조회.
3. **검증한다.** 가장 최근 레코드 시각과 백업 시각의 차이가 RPO 안인지 본다.
4. **시간을 잰다.** 복원 시작부터 검증 끝까지 걸린 시간을 RTO와 비교한다.
5. **기록한다.** `docs/operations/slo.md`의 백업 표에 날짜, 걸린 시간, 결과를 적는다. RTO를 넘었거나 검증이 실패하면 부채 표에 구조 심각도로 적는다.
6. **자동화한다.** 손으로 두 번 해 봤으면 세 번째는 스크립트로 만든다(A등급 조건).

리허설 기록 예:

```
2026-10-16 restore drill: neon 브랜치 복원 6분 40초 (RTO 30분), 최신 레코드 03:00 (RPO 24시간 안), orders 행 수 원본과 일치
```

# ADR과 부채 목록

언제 여는 파일인가: Decision Log의 결정을 ADR로 올릴 때, 그리고 완료 전에 남은 부채를 적을 때.

## 1. 언제 ADR로 올리나

Decision Log의 결정 중 하나라도 해당하면 ADR로 올린다.

<!-- gotechy:adr-when:start -->
- 되돌리는 데 하루 이상(하네스 기본값) 걸린다: 데이터 모양, 저장소, 프레임워크, 공개 API 계약, 파괴적 마이그레이션.
- 새 런타임 의존성, 저장소, 큐, 외부 서비스를 들인다.
- 인증, 인가, 비밀 처리 방식을 바꾼다.
- 여러 모듈이나 바깥 사용자에게 영향이 간다.
- 진지하게 비교한 선택지가 2개 이상 있었고, 6개월 뒤 누군가 "왜 이렇게 했지?"라고 물을 만하다.
- 같은 논쟁이 두 번 이상 나왔다.
<!-- gotechy:adr-when:end -->

## 2. ADR 틀 (Michael Nygard 2011을 뼈대로, MADR 4.0.0의 선택지 비교와 확인 방법을 더함)

파일: `docs/decisions/NNNN-<슬러그>.md`. 번호는 4자리로 이어 붙이고 다시 쓰지 않는다. 폴더가 없으면 만들고 `0001`부터. 이 틀은 `gotechy-retro` 스킬의 ADR 틀과 글자 하나까지 같다. 한쪽을 고치면 다른 쪽도 고친다.

<!-- gotechy:adr-template:start -->
```markdown
---
status: 제안됨          # 제안됨 | 승인됨 | 폐기됨 | 대체됨(NNNN)
date: YYYY-MM-DD
decision-makers: [오너]
consulted: []
informed: []
supersedes: ""          # 대체하는 옛 ADR 번호가 있으면
related: [docs/exec-plans/completed/<파일>.md, docs/retros/<파일>.md]
---

# NNNN. <짧은 명사구 제목>

## 맥락과 문제

<3~5문장. 어떤 상황과 제약에서 이 결정이 필요했나. 사실만.>

## 결정 동인

- <예: 쿼리 2종이 모두 user_id로 거르고 최신순 정렬>
- <예: 쓰기 지연 증가는 10% 이내여야 함>

## 검토한 선택지

1. <선택지 A>
2. <선택지 B>
3. <아무것도 하지 않기> (가능하면 늘 넣는다)

## 결정

우리는 <선택지>를 쓴다. 이유: <결정 동인에 비춘 근거>.

### 결과

- 좋은 점: <...>
- 나쁜 점: <...>
- 중립: <...>

### 확인 방법

<예: `tests/db/index-exists.test.ts`가 CI 필수 체크로 인덱스 존재를 검사한다>

## 선택지별 장단점

### <선택지 A>
- 좋다, 왜냐하면 <...>
- 나쁘다, 왜냐하면 <...>

### <선택지 B>
- 좋다, 왜냐하면 <...>
- 나쁘다, 왜냐하면 <...>

## 더 알아볼 것

<다시 볼 시점이나 조건. 예: 노트 10만 개를 넘으면 부분 인덱스를 다시 검토>
```
<!-- gotechy:adr-template:end -->

- 상태: 제안됨, 승인됨, 폐기됨, 대체됨(NNNN). 결정은 오너만 한다. 에이전트가 쓴 ADR은 "제안됨"으로 두고 오너 결정으로 올린다.
- 결정이 뒤집히면 옛 ADR을 고치거나 지우지 않는다. 옛 ADR 상태를 "대체됨(새 번호)"으로 바꾸고 새 ADR에 `supersedes`를 적는다. 한때 그것이 결정이었다는 사실도 기록이다.
- 결과에는 나쁜 점을 1개 이상 쓴다. 나쁜 점이 없으면 아직 덜 생각했다는 신호다.

## 3. 부채 목록

파일: `docs/exec-plans/tech-debt-tracker.md`. 없으면 아래로 만든다. `gotechy-ship`, `gotechy-retro` 스킬과 같은 표다(표 머리와 심각도 규칙이 글자 하나까지 같다).

```markdown
# 기술 부채

부채는 고금리 대출이다. 매일 조금씩 갚는다. 기록 없는 부채가 가장 비싸다.

## 활성 부채

<!-- gotechy:debt-table:start -->
| ID | 등록일 | 내용 | 위치 | 심각도 | 이자(방치 시 비용) | 상환 계획 |
|---|---|---|---|---|---|---|

심각도: 구조(레이어 위반, 데이터 위험) / 기능(엣지 케이스, 성능) / 표면(이름, 중복)
보안 리뷰의 심각도를 옮길 때: 높음은 구조, 중간은 기능, 낮음은 표면으로 적는다.
<!-- gotechy:debt-table:end -->

## 상환 완료

| ID | 내용 | 상환일 | 증거 |
|---|---|---|---|
```

- ID는 `TD-001`부터 이어 붙인다. 지운 번호를 다시 쓰지 않는다.
- 7칸을 모두 채운다. "이자"는 "이 부채가 커지면 무엇이 비싸지는가"를 한 문장으로 쓴다.
- 상환 계획은 날짜나 계기("다음 결제 기능 작업 때")로 쓴다. "언젠가"는 계획이 아니다.
- 심각도는 색 기호 대신 구조, 기능, 표면 중 하나로 쓴다.
- 구조나 기능 심각도 항목이 2주(하네스 기본값) 넘게 그대로면 갚는 일을 새 ExecPlan으로 올린다.
- 보안 높음은 이 표로 미루지 않는다. 바로 고치고, 못 고치면 `gotechy-security` 스킬의 리뷰 문서에 남기고 오너에게 막는 결정으로 올린다. 기한 있는 중간과 낮음은 위 대응대로 적는다.
- 완료 게이트(`gotechy-ship`)는 이번 계획에서 생긴 부채가 이 목록에 있는지 본다. 숨긴 부채가 가장 비싸다.

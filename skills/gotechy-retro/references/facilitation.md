# 회고 진행법

절차 1단계(시작 선언)와 3~5단계(자료, 인사이트, 행동)를 진행할 때, 그리고 비난 문장을 고칠 때 연다.

## 1. 시작 선언 (Prime Directive)

Norm Kerth가 『Project Retrospectives』(2001)에서 낸 회고 시작 선언을 우리말로 옮겼다. 회고 문서 맨 위에 두고, 함께 하는 회고면 소리 내어 읽는다.

> 무엇을 발견하든, 우리는 모두가 그때 알던 것, 가진 기술과 능력, 쓸 수 있던 자원, 놓인 상황 안에서 할 수 있는 최선을 다했다고 이해하고 진심으로 믿는다.

Kerth는 회고가 효과 있으려면 안전해야 한다고 쓰고, 보복에 대한 두려움을 없애고 서로 믿는 분위기를 만드는 도구로 이 선언을 둔다. 논의가 누구 탓으로 흐르면 이 선언으로 돌아온다.

## 2. 다섯 단계와 시간 상자

Derby, Larsen, Horowitz의 『Agile Retrospectives』 2판(2024)은 회고를 다섯 단계로 나눈다. 시간은 60분 회고 기준의 하네스 기본값이다.

| 단계 | 하는 일 | 시간 | 1인 회고에서 |
|---|---|---|---|
| 판 깔기 | 범위와 목표, 시작 선언 | 5분 | 범위와 질문 하나를 적는다 |
| 자료 모으기 | 계획 대비 실제, 타임라인, 이전 행동 항목 | 15분 | `git log`, PR, CI, ExecPlan, HANDOFF에서 뽑는다 |
| 인사이트 만들기 | 잘된 것과 막힌 것의 기여 요인 | 20분 | 4절 질문을 스스로 묻는다 |
| 할 일 정하기 | 행동 항목 3개 이하 | 15분 | 고르지 못한 것은 "다음 후보"로 |
| 마무리 | 회고의 회고, 감사 | 5분 | 유용도 1~5와 바꿀 것 하나 |

자료 모으기 전에 해석을 쓰지 않는다. 해석이 먼저 나오면 사실이 해석에 맞춰 골라진다.

## 3. 자료 모으기 명령

```bash
# 기간 안의 커밋 (해시, 날짜, 제목)
git log --since=2026-10-01 --until=2026-10-15 --pretty='%h %ad %s' --date=short

# 기간 안에 머지된 PR
gh pr list --state merged --search "merged:2026-10-01..2026-10-15" --json number,title,mergedAt

# 실패한 CI 실행
gh run list --status failure --created 2026-10-01..2026-10-15 --json databaseId,displayTitle,createdAt

# ExecPlan 진행 기록과 놀란 일
sed -n '/## Progress/,/## Decision Log/p' docs/exec-plans/completed/<파일>.md
```

명령이 없거나 실패하면 그 사실을 적고, 대신 쓴 출처(사람의 기억이면 [추정])를 표시한다.

## 4. 비난 없는 언어

Google SRE 책 15장은 비난 없는 포스트모템을 "어떤 개인이나 팀도 고발하지 않고 기여 요인을 찾는 것"으로 정의하고, 모두가 그때 가진 정보로 선의를 갖고 행동했다고 가정한다. 고칠 대상은 사람이 아니라 시스템과 과정이다. 이 스킬은 같은 원칙을 AI 에이전트에도 적용한다. 에이전트의 실수도 지시, 맥락, 검증 장치의 문제로 본다.

| 비난하는 문장 | 바꿔 쓴 문장 |
|---|---|
| 민수가 테스트를 안 돌리고 머지했다 | 필수 CI 체크가 없어 테스트 없이 머지할 수 있는 상태였다 |
| 내가 멍청했다 | 그 시점에는 X라는 정보가 없었다. X를 먼저 알려 주는 장치가 없었다 |
| AI가 멋대로 파일을 지웠다 | 작업 명세에 금지 범위가 없었고, 머지 전에 diff 범위를 검사하는 단계가 없었다 |
| 부주의했다 | 확인 단계가 손으로 하는 일이었고 체크리스트가 없었다 |
| 왜 그렇게 했어요? | 그때 무엇이 보였어요? 무엇을 기대했어요? |
| 다음엔 조심하자 | 다음엔 무엇이 먼저 알려 주면 좋을까? 그 장치를 만든다 |

사람 이름은 타임라인의 "누가 무엇을 했다" 사실 기록에만 쓰고, 원인과 행동 항목 칸에는 쓰지 않는다. 1인 회고에서도 "나" 대신 구조를 원인 칸에 쓴다.

## 5. 질문 묶음

- 사실: 무엇을 봤나? 언제? 어디에 기록이 있나?
- 기대와 실제: 무엇을 기대했고 실제로는 어땠나? 차이는 몇 시간, 몇 퍼센트인가?
- 놀란 것: 예상하지 못한 것은? 그걸 먼저 알 수 있었던 신호가 있었나?
- 잘된 것: 무엇이 잘 됐고, 그게 우연인가 구조 덕인가? 구조 덕이면 무엇을 지키면 되나?
- 다시 한다면: 같은 상황이 오면 무엇이 먼저 알려 주면 좋은가? 그 장치는 무엇인가?
- 반복: 이 문제가 이전 회고에도 있었나? 있었다면 그때의 행동 항목은 왜 막지 못했나?

## 6. 기여 요인 네 갈래

| 갈래 | 예 |
|---|---|
| 구조 | 레이어 경계가 없어 한 변경이 여러 모듈을 건드림, 필수 체크 미설정 |
| 과정 | 리뷰 단계 없음, 스펙 없이 구현 시작, 작업 단위가 너무 큼 |
| 도구 | 로컬과 CI 명령이 다름, 로그가 실패를 "skipped" 한 줄로만 남김 |
| 정보 | 문서가 낡음, 결정 이유가 기록되지 않음, 에이전트에게 맥락을 주지 않음 |

막힌 것마다 기여 요인을 1개 이상 연결한다. 하나뿐이면 "다른 갈래도 봤는가"를 한 번 더 묻는다. 단일 원인으로 끝내면 행동 항목이 좁아진다.

## 7. 리뷰

SRE 책은 리뷰하지 않은 포스트모템은 없었던 것과 같다고 쓴다. 회고 문서도 마찬가지다. 다음 회고의 2단계(이전 행동 항목 추적)가 이 리뷰 역할을 한다. 팀이면 회고 문서를 한 사람 이상이 읽고 행동 항목의 우선순위에 동의했는지 기록한다.

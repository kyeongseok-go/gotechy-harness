# 출시 준비 점검 (출시 등급)

출시 등급 게이트의 7단계에서 연다. 배포 명령은 실행하지 않고, 준비가 됐는지만 판정한다.

## 1. 출시 준비 질문 10개 영역

Google SRE 책 부록의 출시 조율 체크리스트(Launch Coordination Checklist)를 1인, 소규모 팀용으로 줄였다. 영역마다 답을 한두 줄로 쓰고, 답할 수 없으면 부채로 기록한다. 질문마다 "이 질문이 막는 사고"를 적어 둔 것은 원문의 원칙(모든 질문은 이전 사고로 중요성이 입증돼야 한다)을 따른 것이다.

| 영역 | 질문 | 막는 사고 |
|---|---|---|
| 구조 | 요청이 어떤 서버, 저장소, 외부 서비스를 거치나? 그림 한 장이 있나? | 장애 때 어디를 볼지 몰라 시간을 버림 |
| 용량 | 예상 트래픽과 최대치는? 부하 시험 결과가 있나? | 출시 첫날 몰린 사용자에 서버가 넘어짐 |
| 실패 대응 | 서버 하나, 외부 API 하나가 죽으면 어떻게 되나? 타임아웃, 재시도, 폴백이 있나? | 외부 API 하나가 느려져 전체가 멈춤 |
| 백업 | 데이터 백업과 복원 시험이 있나? | 지운 데이터를 되살리지 못함 |
| 관측 | 사용자가 겪는 증상(오류율, 지연)을 볼 수 있나? 알림이 누구에게 가나? | 사용자 신고로 장애를 처음 앎 |
| 보안 | `gotechy-security` 리뷰를 통과했나? 인증, 비밀 관리가 확인됐나? | 출시와 함께 취약점 공개 |
| 자동화 | 빌드가 재현 가능하고, 배포와 롤백이 명령 하나인가? | 손으로 하다 단계를 빠뜨림 |
| 성장 | 10배 사용자에서 먼저 터질 곳은? | 성공이 장애가 됨 |
| 외부 의존 | 제3자 서비스가 느려지거나 한도에 걸리면 기능을 줄여서라도 버티나? | 남의 장애가 내 장애가 됨 |
| 일정 | 출시일이 금요일 밤이나 연휴 전인가? 문제 생기면 누가 깨어 있나? | 아무도 없는 시간에 장애 |

같은 원천의 Production Readiness Review(PRR)는 구조와 의존, 계측과 모니터링, 긴급 대응, 용량, 변경 관리, 성능을 본다. 처음 출시하는 서비스면 위 표에 이 여섯 축이 다 들어갔는지 한 번 더 본다.

## 2. 버전 번호 (SemVer 2.0.0)

| 바뀐 것 | 올리는 자리 |
|---|---|
| 공개 API(사용자가 의존하는 동작, 설정 키, CLI 옵션, 응답 모양)를 깨는 변경 | MAJOR, MINOR와 PATCH는 0으로 |
| 하위 호환 기능 추가, 또는 기능을 deprecated로 표시 | MINOR, PATCH는 0으로 |
| 하위 호환 버그 수정 | PATCH |

- 0.y.z는 초기 개발이라 무엇이든 바뀔 수 있다. 사용자가 생기면 1.0.0을 낸다.
- 발행한 버전의 내용은 바꾸지 않는다(규칙 3). 잘못 낸 버전은 새 버전으로 고친다. 확인: `git tag -l "v<버전>"`이 비어 있어야 한다.
- 웹 서비스처럼 버전 번호를 쓰지 않는 프로젝트는 배포 sha와 날짜를 버전 대신 CHANGELOG 절 제목으로 쓴다.

## 3. CHANGELOG (Keep a Changelog 1.1.0)

`CHANGELOG.md`가 없으면 아래로 만든다.

```markdown
# Changelog

이 프로젝트의 눈에 띄는 변경을 모두 적는다. 형식은 Keep a Changelog 1.1.0, 버전은 Semantic Versioning 2.0.0을 따른다.

## [Unreleased]

## [1.2.0] - 2026-10-16
### Added
- 사용자가 볼 수 있는 새 기능 한 줄
### Fixed
- 고친 버그 한 줄 (이슈 링크)
```

- 분류는 `Added`, `Changed`, `Deprecated`, `Removed`, `Fixed`, `Security` 여섯 가지만 쓴다.
- 최신 버전이 맨 위, 날짜는 `YYYY-MM-DD`.
- 커밋 로그를 붓지 않는다. 사람이 읽고 "나에게 무엇이 바뀌나"를 알 수 있게 쓴다.
- 작업 중에는 `[Unreleased]`에 쌓고, 출시할 때 새 버전 절로 옮긴다.

## 4. 환경 변수와 비밀

- 진실의 원천은 `.env.example`이다. 키 이름과 주석(환경별 필수 여부)만 있고 값은 없다.
- 배포 전 대조: `.env.example`의 키 목록과 배포 환경(호스팅 대시보드나 CLI)의 키 목록을 비교한다. 누락 키가 하나라도 있으면 배포 중단이다. 값은 출력하지 않는다.
- 비밀 수명주기(OWASP Secrets Management Cheat Sheet): 만들 때 최소 권한, 가능하면 만료일을 둔다. 정기 회전은 자동화를 먼저 고려한다. 기본 주기는 90일(하네스 기본값)이고, 유출이 의심되면 즉시다. 회전은 배포 환경까지 새 값으로 바뀌고 옛 값을 폐기한 시점에 끝난다.
- 유출 대응 순서: 폐기(revoke), 새 비밀 발급(가능하면 자동), 노출 위치(코드, 로그)에서 삭제, 누가 언제 접근했는지 기록 보존. git 이력 다시 쓰기는 커밋 링크를 깨므로 마지막에 판단한다. 보안 부채는 부채 표에 미루지 않고 바로 처리한다.

## 5. 점진 출시 계획

사용자 영향이 큰 변경(결제, 로그인, 데이터 쓰기 경로, 첫 화면)은 아래 표를 채운다.

| 단계 | 노출 | 대기 | 판정 지표와 합격선 | 중단 조건 |
|---|---|---|---|---|
| 1 | 내부 사용자 또는 1% | 30분 이상, 트래픽 정점 포함 | 오류율 대조 집단 대비 +0.1%p 이하, p95 지연 +10% 이하 (예시) | 합격선 초과 즉시 플래그 끄기 |
| 2 | 10% | 1시간 | 같은 지표 | 같은 조건 |
| 3 | 100% | | | |

- 판정 지표는 SLI에서 고르고 12개 이하로 둔다. 지표 집계 간격은 카나리 기간 이하여야 한다(1시간 집계로 30분 카나리를 판정하면 신호가 흐려진다).
- 지표는 카나리 집단과 대조 집단을 나눠 본다. 전체 합계에서는 5% 카나리의 오류 20%가 1%로 보인다.
- 카나리는 한 번에 하나만 돌린다.
- 기능 플래그는 OpenFeature 명세(v0.9.0)를 따르는 SDK를 쓰면 공급자를 바꿔도 코드가 그대로다. 평가가 실패하면 SDK가 기본값을 돌려줘야 하므로(요구사항 1.4.10), 기본값은 항상 옛 동작으로 둔다.
- 플래그를 만들 때 제거 예정일을 부채 표에 넣는다.
- 위 표의 수치는 예시다. 프로젝트의 SLO(`docs/operations/slo.md`)가 있으면 그 오류 예산 안에서 정한다.

## 6. 산출물 provenance (패키지, 이미지, 바이너리를 배포할 때)

- SLSA v1.2 Build 트랙: L1은 빌드 플랫폼이 provenance(무엇을, 어디서, 어떻게 빌드했나)를 자동으로 만든다. L2는 호스팅된 빌드 플랫폼이 서명하고 소비자가 진위를 검증한다. L3는 빌드끼리 격리하고 서명 비밀을 사용자 빌드 단계에서 떼어 놓는다.
- GitHub Actions의 artifact attestations는 기본으로 SLSA Build L2이고, 재사용 워크플로로 빌드하면 L3를 충족할 수 있다고 GitHub 문서가 쓴다(문서는 SLSA v1.0의 등급 이름으로 적는다. v1.2는 v1.1과 하위 호환이라고 발표됐고, v1.1에서 v1.2 사이의 큰 변화는 Source 트랙 추가다). 검증은 `gh attestation verify`.
- 이 bar의 합격선은 L2 이상이다. 웹 서비스처럼 남이 산출물을 내려받지 않으면 이 항목은 검사 대상이 아니다.

## 7. 흐름 지표 기록 (DORA, 선택이지만 A등급 조건)

출시할 때마다 한 줄씩 쌓는다. 위치는 ExecPlan의 Artifacts and Notes나 `docs/quality/score.md` 아래 표다.

| 날짜 | 커밋 sha | 리드타임(첫 커밋에서 배포까지) | 즉시 조치 필요했나(롤백, 핫픽스) | 복구 시간 | 계획 밖 배포였나 |
|---|---|---|---|---|---|

이 표에서 배포 빈도, 변경 리드타임, 변경 실패율, 실패한 배포 복구 시간, 배포 재작업률이 나온다. 숫자를 목표로 걸지 않고 4주 추세만 본다.

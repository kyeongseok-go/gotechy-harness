# 롤백과 마이그레이션 안전

출시 등급에서 롤백 계획과 DB 마이그레이션을 점검할 때, 그리고 `docs/operations/runbooks/rollback.md`가 없어 처음 만들 때 연다.

## 1. 원칙

- **롤백은 5분 안에 끝나야 한다**(하네스 기본값). 장애 중에 처음 찾는 명령은 5분 안에 끝나지 않는다. 그래서 명령 한 줄을 미리 적고 리허설한다.
- Google SRE 책이 꼽는 변경 관리 세 가지는 점진 출시, 문제를 빠르고 정확하게 감지, 문제가 생기면 안전하게 되돌리기다. 이 파일은 세 번째를 다룬다.
- **코드 롤백이 안전하려면 데이터가 양쪽 코드와 맞아야 한다.** 그래서 마이그레이션은 expand-contract로 나눈다.
- 프로덕션 롤백은 사용자가 직접 실행하거나 CI가 실행한다. 에이전트는 명령을 준비해 제시하고, 사용자가 명시적으로 지시했을 때만 실행한다.

## 2. expand-contract (Parallel Change)

Danilo Sato의 Parallel Change(2014)는 깨지는 변경을 세 단계로 나눈다. 원문은 대부분의 DB 리팩터링이 이 패턴을 따른다고 쓴다.

| 단계 | 하는 일 | 예: `name`을 `full_name`으로 바꾸기 | 이 배포를 롤백하면 |
|---|---|---|---|
| expand | 새 것을 옛 것 옆에 더한다. 옛 코드는 그대로 돈다 | `full_name` 컬럼 추가(nullable), 코드는 두 컬럼에 모두 쓰고 옛 컬럼에서 읽음 | 안전. 새 컬럼은 무시된다 |
| migrate | 데이터를 옮기고 읽기를 새 것으로 바꾼다 | 기존 행 채우기(배치), 코드가 `full_name`에서 읽음 | 안전. 옛 컬럼도 계속 채워졌다 |
| contract | 아무도 옛 것을 쓰지 않음을 확인하고 지운다 | 옛 컬럼에 쓰기 중단, 다음 배포에서 `name` 삭제 | 옛 코드로는 돌아갈 수 없다. 그래서 마지막에, 따로 |

- 세 단계는 **서로 다른 배포**다. 한 배포에 expand와 contract를 같이 넣으면 롤백할 곳이 없다.
- contract를 건너뛰면 시작보다 나쁜 상태(두 컬럼을 영원히 같이 관리)가 된다고 원문이 경고한다. contract는 날짜를 박아 부채 표에 넣는다.
- 파괴적 변경 목록: 컬럼이나 테이블 삭제, 이름 바꾸기, 타입 바꾸기, NOT NULL이나 제약 추가, 기본값 없는 컬럼 추가(DB에 따라 테이블 잠금), 큰 테이블의 인덱스 생성(Postgres는 `CREATE INDEX CONCURRENTLY`).
- 기계 검사: Postgres면 squawk 같은 마이그레이션 린터를 CI에 둔다. 다른 DB는 그 생태계의 린터나 리뷰 체크리스트로 대신한다.
- 파괴적 마이그레이션 전에는 백업을 확인한다. 관리형 DB면 시점 복구(PITR)가 켜져 있는지 확인한다. 복원 리허설은 `gotechy-operate` 스킬의 범위다.

## 3. 롤백 런북 틀

`docs/operations/runbooks/rollback.md`가 없으면 아래로 만든다. `gotechy-operate` 스킬도 같은 파일을 쓴다.

```markdown
# 런북: 직전 배포 되돌리기

언제: 배포 직후 오류율이나 지연이 SLO를 넘을 때, 또는 기능이 깨졌다는 확인된 신고가 있을 때.
마지막 리허설: YYYY-MM-DD, 걸린 시간 N분 (목표 5분 이하)

## 판단 (1분)
- 직전 배포 시각과 증상 시작 시각이 10분 안에 붙어 있나? 그렇다면 원인 분석 전에 되돌린다.
- 이번 배포에 contract 단계 마이그레이션이 있었나? 있으면 3번으로 간다.

## 1. 코드 되돌리기 (명령 한 줄)
    <예: vercel rollback / fly releases rollback / kubectl rollout undo deploy/web>

## 2. 확인
    <예: curl -fsS https://<도메인>/health 가 200, 대시보드의 오류율이 배포 전 수준>

## 3. 데이터 문제가 있으면 (코드만 되돌릴 수 없을 때)
- 쓰기 경로를 막는다: <읽기 전용 플래그 이름과 켜는 명령>
- 백업이나 시점 복구 지점을 확인한다: <명령>
- 복원은 사용자가 결정한다. 복원 범위와 잃을 데이터(RPO)를 먼저 적는다.

## 4. 뒤처리
- 사고 기록을 연다(gotechy-operate 스킬의 포스트모템 틀).
- 되돌린 배포의 sha와 시각을 기록한다.
```

## 4. 리허설

- 분기에 한 번(90일 이내, 하네스 기본값), 스테이징이나 미리보기 환경에서 런북대로 되돌려 본다.
- 걸린 시간을 런북 머리의 "마지막 리허설"에 적는다. 5분을 넘으면 넘긴 단계를 자동화하는 일을 부채로 적는다.
- 리허설을 한 번도 안 한 롤백 명령은 이 bar에서 "롤백 계획 없음"과 같게 친다.

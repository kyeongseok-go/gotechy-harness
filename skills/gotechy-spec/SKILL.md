# gotechy-spec: 아이디어를 검증 가능한 스펙으로

스펙은 "무엇을 왜 만들고, 끝났는지 어떻게 아는가"를 다른 사람과 에이전트가 같은 뜻으로 읽게 만드는 문서다. 이 스킬은 문제와 증거를 해결책보다 먼저 쓰고, 요구사항마다 시험할 수 있는 수용 기준을 붙이고, 성공을 숫자로 정하고, 모르는 것은 추측 대신 표시로 남긴다. 확정된 스펙은 `gotechy-plan`의 입력이 된다.

## 언제 쓰나

- 새 기능이나 제품을 시작할 때, 또는 기존 스펙을 고치거나 확정할 때
- 사용자 말 예시: "이 기능 스펙 써줘", "PRD 만들어줘", "기획 위저드로 시작하자"
- 다른 스킬이 "스펙이 없다"며 넘겨 왔을 때

쓰지 않는 때: 문제가 진짜인지부터 모를 때(`gotechy-discover`), 화면 설계(`gotechy-design`), 품질 목표 수치화(`gotechy-quality`), 아래 크기 표의 패치.

## 작업 크기 (`gotechy-plan`, `gotechy-build`, `gotechy-ship`과 같은 표)

<!-- gotechy:size-table:start -->
| 크기 | 기준 | 스펙 | 계획 | 출시 게이트 |
|---|---|---|---|---|
| 패치 | 1시간 미만, 파일 1~2개, 동작 계약 불변 | 없음 | 없음 | 패치 등급 |
| 작은 기능 | 1일 미만 | 미니 스펙(수용 기준 목록) | 없음. 수용 기준 목록이 검증 목록을 대신한다 | 기능 등급(미니 스펙 경로) |
| 큰 기능 | 1일 이상, 또는 사용자 데이터, 인증, 결제, 외부 발행을 건드림 | 풀 스펙 | ExecPlan | 기능 등급 |
| 제품 | 화면 여러 개나 새 프로젝트 | 위저드 | ExecPlan | 기능 또는 출시 등급 |

## 절차

1. **착수 판정.** `docs/discovery/<슬러그>.md`가 있으면 링크하고 결정과 증거를 가져온다. 없으면 네 질문에 답한다. 대상 사용자가 이해하고 쓸 수 있는가, 기존 기능을 다듬는 일이 먼저 아닌가, 없으면 사용자가 실제로 곤란한가, 테스트와 문서와 유지 비용을 감안해도 남는가. 그리고 "지금 이것을 먼저 할 이유" 3줄을 쓴다. 답하지 못하면 `docs/product-specs/index.md`에 "아이디어" 상태로만 올리고 멈추며, 큰 일이면 `gotechy-discover`를 제안한다. 산출물: 스펙 0절.
2. **트랙 판정.** 위 크기 표로 고르고 결과를 먼저 알린다. 작은 기능은 미니, 큰 기능은 풀, 제품은 위저드다. 패치면 스펙을 쓰지 않는다. 애매하면 큰 쪽을 고르고 확인받는다.
3. **미니 스펙.** `references/templates/spec.md`의 0~4절(수용 기준 1개 이상, 성공 기준 1행 이상)만 채워 `docs/product-specs/<슬러그>.md`로 쓴다. 6단계 리뷰는 `references/review.md`로 스스로 훑는 것으로 대신할 수 있다.
4. **풀 스펙.** `references/templates/spec.md` 전체를 채운다. 불편함은 최대 3문항(누가, 언제, 없으면 얼마나 곤란한가)으로 묻는다. 요구사항, 수용 기준, 성공 기준, 상태 설계는 `references/requirements.md` 규칙을 따른다.
5. **위저드.** `references/wizard.md`를 먼저 연다. `docs/product-specs/<슬러그>/`에 00-brief, 10-prd, 20-features, 30-user-flow를 한 단계씩 만들고 단계마다 승인을 받는다. 10-prd와 20-features 사이의 15-quality-goals는 `gotechy-quality`가 만든다. 매 턴 `[위저드 00-brief, 1/7]`처럼 위치를 밝힌다. 위저드 중에는 코드를 만들지 않는다. `--quick`이면 승인 없이 네 문서 초안을 한 번에 쓰되 표시는 남긴다.
6. **적대적 리뷰.** `references/review.md`를 연다. 쓸 수 있는 서브에이전트에 `spec-reviewer`가 있으면 스펙 경로와 `references/review.md`를 넘겨 위임하고, 없으면 같은 체크리스트로 스스로 검토한다. 위저드는 10-prd와 20-features를 함께 본다. "막음" 지적은 에이전트가 기각하지 못한다. 반영하거나 원문 그대로 사용자에게 올린다. "고침"과 "제안"은 반영하거나 기각 이유를 남긴다.
7. **색인 갱신.** `docs/product-specs/index.md`(없으면 만든다)에 한 줄을 더한다. 형식은 `references/templates/index.md`.
8. **확정.** 확정 조건을 모두 만족하면 상태를 "확정"으로 바꾸고 `## 확정 이력`에 날짜와 승인자를 적는다. 확정 뒤 변경은 `## 변경 이력`에 적고, non-goals를 줄이는(범위를 넓히는) 변경은 사용자 승인을 받는다.
9. **넘기기.** 위저드 순서(00-brief, 10-prd, 15-quality-goals, 20-features, 30-user-flow, 40-sitemap, 50-wireframe, 60-style-guide)대로 이어 간다. 품질 특성(성능, 보안, 접근성 등)을 수치로 정할 일이 있으면 `gotechy-quality`, 화면이 있으면 그다음 `gotechy-design`, 마지막으로 `gotechy-plan`이다. 개인정보, 위치정보, 결제, 광고나 마케팅 메시지, AI 기능, 접근성 의무 중 하나라도 건드리면 `gotechy-comply-kr`로 법 요구사항 표를 만들게 하고, LLM 기능이 있으면 `gotechy-ai-eval`로 eval 기준을 세우게 한다. 인증, 결제, 개인정보를 건드리면 계획에 `gotechy-security` 리뷰를 넣으라고 적는다. 산출물: 스펙 끝에 다음 스킬 목록과 이유.

## 질문 엔진 (모든 트랙)

- 한 번에 묻는 질문은 단계당 최대 5개다. 영향과 불확실성이 모두 큰 것만 묻는다.
- 질문마다 선택지 2~4개, 추천안 하나, "왜 묻는지" 한 줄을 붙인다. "추천대로"라고만 답해도 진행된다.
- 답은 바로 문서에 반영하고 `## Q&A 로그`에 남긴다. 모순된 옛 문장은 지운다.
- 물을 만큼 중요하지 않지만 확실하지 않은 것은 정하지 말고 `[NEEDS CLARIFICATION: 질문]`을 남긴다.

## 기준 요약 (전체는 `references/bar.md`)

1. 문제와 증거가 해결책보다 먼저다. 1절에 누가, 언제, 얼마나 아픈가와 증거 링크가 있고, 증거가 없으면 `[가정]`으로 표시한다.
2. 수용 기준은 EARS 다섯 형식(무조건, 상태, 이벤트, 선택 기능, 원치 않는 동작)으로만 쓰고, 문장 하나에 동작 하나다.
3. 요구사항 본문에 모호어가 0개다(빠르게, 쉽게, 적절히, 충분히, 사용자 친화적, 가능한 한, 등등).
4. 성공 기준은 지표, 기준값, 목표값, 측정 방법, 측정 시점, 실패선 여섯 칸이 모두 찬다.
5. non-goals가 3개 이상이다(풀, 위저드). 미니는 1개 이상.
6. 상태 표에 8종(로딩, 첫 사용 빈 상태, 결과 없음, 복구 가능 오류, 복구 불가 오류, 부분 실패, 오프라인, 권한 없음)이 각각 동작 문장으로 있다(풀, 위저드). `gotechy-design`의 상태 8종과 같은 이름이다.
7. 확정 조건: 리뷰 "막음" 0건, `[NEEDS CLARIFICATION` 0개, `[SYNC NEEDED` 0개, `references/bar.md` 기계 검사 통과. "(풀, 위저드)" 항목은 미니 스펙에 적용하지 않으므로 미니 스펙도 확정할 수 있다.
8. 요구사항과 수용 기준에 ID가 있어 계획의 검증 항목까지 추적된다.

## 산출물과 저장 위치

| 트랙 | 파일 (없으면 만든다) |
|---|---|
| 미니, 풀 | `docs/product-specs/<슬러그>.md` |
| 위저드 | `docs/product-specs/<슬러그>/00-brief.md`, `10-prd.md`, `20-features.md`, `30-user-flow.md` |
| 공통 | `docs/product-specs/index.md` |

품질 목표(`15-quality-goals.md`, 10-prd 다음이고 20-features 전)는 `gotechy-quality`, 화면 문서(40~60)는 `gotechy-design`이 같은 폴더에 만든다.

## 완료 기준

- 트랙에 맞는 산출물, 색인 갱신, 리뷰 종결, 확정 조건 충족.
- 기계 검사 명령과 결과를 스펙 끝 `## 검사 기록`에 붙였다.
- 사용자에게 세 줄 요약, 남은 `[NEEDS CLARIFICATION]` 목록(확정 전이면), 다음 스킬을 보고했다.

위임받은 작업의 보고는 `owner-protocol` 스킬의 HANDOFF 형식을 따른다.

## 하지 않는 것

- 빈칸을 그럴듯한 추측으로 채우지 않는다. 표시를 남긴다.
- 위저드에서 여러 단계를 한 턴에 합치거나, 승인 전에 다음 단계로 가지 않는다(`--quick` 제외).
- "빠르게", "안정적으로" 같은 말을 숫자 없이 성공 기준으로 두지 않는다.
- 해결책 이름으로 문제를 쓰지 않는다("알림 기능이 없다"가 아니라 "마감을 놓친다").
- 코드를 쓰지 않는다. 구현은 계획 다음이다.
- 프로젝트에 개인 커리어 파일(예: `career.yaml`)이 있으면 `career_signals` 가설을 적고, 없으면 그 절을 지운다.

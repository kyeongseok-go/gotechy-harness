# 요구사항 쓰는 법

언제 여는 파일인가: 스펙 틀의 3~5절과 7절, 위저드 10-prd와 20-features를 쓸 때, 그리고 리뷰에서 "모호", "검증 불가" 지적을 고칠 때.

## 1. ID 규칙 (추적의 뼈대)

| 대상 | 형식 | 예 |
|---|---|---|
| 요구사항(왜) | `R<번호>` | R1 정기 결제 놓침 방지 |
| 기능(무엇) | `### F<요구사항>-<번호>` 제목 | `### F1-1 결제 전날 알림` |
| 수용 기준(어떻게 판정) | `- AC-<기능>.<번호>` 줄 | `- AC-1-1.2 WHEN ...` |
| 성공 기준 | 성공 기준 표의 첫 칸 `SC-<번호>` | SC-1 |

계획(`gotechy-plan`)의 검증 항목은 AC ID를 그대로 인용한다. 그래서 ID를 바꾸지 않는다. 지운 기준은 줄을 지우지 말고 `(폐기 YYYY-MM-DD: 이유)`를 붙인다.

## 2. EARS 수용 기준

EARS는 요구사항을 정해진 문형으로 써서 모호함을 줄이는 방법이다(Alistair Mavin, 2009). 키워드는 영어 대문자로 두어 기계 검사가 되게 하고, 나머지는 한국어로 쓴다. 주어는 항상 "시스템은"이다. "시스템"이 무엇을 가리키는지(예: 예약 웹앱과 서버)는 스펙 2절에 한 번 적는다.

| 문형 | 쓰는 때 | 꼴 |
|---|---|---|
| 무조건 | 항상 참이어야 하는 성질 | `시스템은 <응답>한다.` |
| 상태 (WHILE) | 어떤 상태가 이어지는 동안 | `WHILE <상태>, 시스템은 <응답>한다.` |
| 이벤트 (WHEN) | 사건이 일어났을 때 | `WHEN <트리거>, 시스템은 <응답>한다.` |
| 선택 기능 (WHERE) | 특정 기능이나 설정이 있을 때만 | `WHERE <기능이 켜진 경우>, 시스템은 <응답>한다.` |
| 원치 않는 동작 (IF THEN) | 오류, 실패, 잘못된 입력 | `IF <원치 않는 트리거>, THEN 시스템은 <응답>한다.` |
| 복합 | 상태와 사건이 겹칠 때 | `WHILE <상태>, WHEN <트리거>, 시스템은 <응답>한다.` |

규칙:

- 절 순서는 WHILE, WHEN 순이다. 트리거는 0~1개, 상태는 여러 개 가능, 응답은 1개 이상.
- IF THEN은 "원치 않는 동작" 전용이다. 정상 조건 분기는 WHILE이나 WHERE로 쓴다.
- 응답에는 판정할 수 있는 값을 넣는다. 시간(초), 개수, 문구, 상태 코드.
- 버그 수정 스펙은 회귀 방지 기준을 함께 쓴다: `WHEN <조건>, 시스템은 <기존 동작>을 유지한다.`

예:

```markdown
### F1-1 결제 전날 알림

- AC-1-1.1 WHEN 등록된 정기 결제일 하루 전 오전 9시(KST)가 되면, 시스템은 해당 사용자에게 결제 이름과 금액이 담긴 푸시 알림 1건을 보낸다.
- AC-1-1.2 WHERE 사용자가 알림 시간을 바꾼 경우, 시스템은 바꾼 시간에 보낸다.
- AC-1-1.3 IF 푸시 발송이 실패하면, THEN 시스템은 10분 간격으로 최대 3회 다시 보내고 실패를 기록한다.
- AC-1-1.4 WHILE 사용자가 알림을 끈 상태이면, 시스템은 알림을 보내지 않는다.
```

## 3. 모호어 사전 (본문에서 숫자로 바꾼다)

| 쓰지 않는 말 | 바꾸는 예 |
|---|---|
| 빠르게, 신속히 | 2초 안에(측정 조건 함께) |
| 쉽게, 간편하게, 직관적으로 | 처음 쓰는 사용자 5명 중 4명이 안내 없이 3분 안에 완료 |
| 적절히, 충분히, 원활히 | 최대 100건, 재시도 3회 |
| 가능한 한, 필요시, 필요한 경우 | 조건을 WHEN이나 WHERE로 적는다 |
| 등, 등등, 기타 | 목록을 끝까지 쓰거나 "다음 3가지만"으로 닫는다 |
| 사용자 친화적, 유연한 | 무엇이 어떻게 되면 친화적인지 행동으로 쓴다 |

성능, 신뢰성, 보안, 접근성 같은 품질 특성의 수치는 `gotechy-quality` 스킬로 정하고, 여기에는 그 목표 ID를 링크한다.

## 4. 사용자 스토리와 INVEST

스토리 꼴: `[역할]로서, [기능]을 원한다, 그래서 [효용]`. 스토리마다 여섯 성질을 본다.

| 성질 | 점검 질문 |
|---|---|
| 독립 | 다른 스토리 없이 순서를 바꿔 만들 수 있나 |
| 협상 가능 | 세부가 아니라 핵심만 적었나 |
| 가치 | 사용자가 느끼는 가치가 있나(층 하나만 만드는 스토리가 아닌가) |
| 추정 가능 | 팀이 크기를 가늠할 만큼 이해했나 |
| 작음 | 며칠 안에 끝나나. 넘으면 쪼갠다 |
| 시험 가능 | 수용 기준으로 테스트를 쓸 수 있나 |

## 5. Gherkin 예시 (선택)

규칙이 데이터 조합에 따라 갈리면(요금 계산, 권한 표) EARS 아래에 예시 표를 붙인다. Given은 초기 맥락, When은 행동, Then은 기대 결과다.

```gherkin
Scenario Outline: 결제 전날 알림 시간
  Given 사용자의 알림 시간이 "<설정>"이다
  When 결제일 하루 전이 된다
  Then 알림은 "<발송 시각>"에 간다
  Examples:
    | 설정   | 발송 시각 |
    | 기본값 | 09:00     |
    | 20:00  | 20:00     |
```

## 6. 성공 기준 (여섯 칸)

목표에서 지표를 끌어낸다. 목표(사용자가 이루려는 것), 신호(그것이 일어나면 보이는 행동), 지표(신호를 세는 법) 순서다. HEART 다섯 범주(만족, 참여, 채택, 유지, 과업 성공) 중 무엇을 재는지 적는다.

| ID | 지표 (HEART 범주) | 기준값 | 목표값 | 측정 방법 | 측정 시점 | 실패선 |
|---|---|---|---|---|---|---|
| SC-1 | 알림 받은 결제를 해지하거나 유지 결정한 비율 (과업 성공) | 0% (기능 없음) | 30% | 이벤트 로그 `alert_opened`, `sub_decided` | 출시 4주 뒤 | 10% 미만 |

- 기준값을 모르면 "측정 전"이라고 쓰고, 첫 측정을 계획의 첫 마일스톤에 넣는다. 빈칸으로 두지 않는다.
- 출시 자체("기능 배포")는 성공 기준이 아니다.
- 측정 수단이 아직 없으면 그 수단을 만드는 일을 범위에 넣거나 기준을 지운다.

## 7. 상태와 예외 표 (풀, 위저드)

화면이나 응답마다 아래 8행을 채운다. 해당 없으면 "해당 없음: 이유". 상태 이름은 `gotechy-design` 스킬의 상태 8종과 같다(와이어프레임의 상태 매트릭스가 이 표를 이어받는다).

| 상태 | 동작 |
|---|---|
| 로딩 | 0.5초(하네스 기본값) 넘으면 진행 표시, 미리 "없음"을 띄우지 않는다 |
| 첫 사용 빈 상태 | 무엇을 하는 곳인지 한 줄, 첫 행동 버튼 하나 |
| 결과 없음 | 적용한 조건을 보여 주고 조건 바꾸기 버튼 |
| 복구 가능 오류 | 무엇이 안 됐는지와 고치는 법(입력 오류면 입력 칸 옆에), 다시 시도 버튼, 입력한 내용 보존 |
| 복구 불가 오류 | 사실과 대안 경로(연락처, 나중에 하기), 입력한 내용 보존 |
| 부분 실패 | 성공한 것과 실패한 것을 나눠 보여 주고 실패분만 다시 시도 |
| 오프라인 | 연결이 끊겼다는 표시, 읽기는 마지막 데이터로, 쓰기는 막거나 대기열에 넣고 그 사실을 표시 |
| 권한 없음 | 이유와 권한을 얻는 방법, 다른 사람 데이터는 존재 여부도 드러내지 않음 |

완전히 빈 화면을 두지 않는다. 빈 상태는 사용법을 가르치고 핵심 작업으로 가는 길을 바로 준다(NN/g).

## 8. 내부 FAQ와 보도자료 (제품 단위, 선택)

제품이나 큰 기능이면 스펙 앞에 한 쪽짜리 보도자료를 써 본다. 제목(고객이 아는 말), 부제(누가 무엇을 얻나 한 문장), 요약, 문제, 해결, 고객 인용(가상임을 표시), 시작하는 법. 고객 말로 가치가 서지 않으면 스펙을 쓰지 않고 `gotechy-discover`로 돌아간다.

내부 FAQ는 가장 어려운 질문 3개를 먼저 꺼낸다. 예: "개인정보를 어디에 얼마나 보관하나", "푸시 비용은 사용자 1만 명에서 얼마인가", "알림이 틀렸을 때 누가 어떻게 고치나". 답을 모르면 `[NEEDS CLARIFICATION: ...]`.

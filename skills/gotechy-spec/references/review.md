# 적대적 리뷰

언제 여는 파일인가: 풀 스펙이나 위저드 10-prd와 20-features 초안을 다 쓴 뒤, 확정 전에. 미니 스펙은 이 목록으로 스스로 한 번 훑는다.

## 실행 방법

1. **서브에이전트가 있으면 위임한다.** 쓸 수 있는 서브에이전트 목록에 `spec-reviewer`(또는 같은 역할의 읽기 전용 리뷰어)가 있으면, 스펙 파일 경로와 이 파일 경로, `references/bar.md` 경로를 넘기고 "아래 관점으로 깨뜨려 달라"고 맡긴다. 리뷰어가 프로젝트의 대상 사용자 정의 문서를 따로 갖고 있으면 그것도 읽게 한다.
2. **없으면 스스로 한다.** 다른 역할을 맡는다고 선언하고(만든 사람이 아니라 승인을 거절하려는 시니어 리뷰어) 아래 관점을 순서대로 적용한다. 쓴 문서를 처음 보는 사람처럼 다시 연다.
3. 결과는 스펙 끝 `## 리뷰 기록`에 날짜와 리뷰 방식(서브에이전트, 자기 검토)과 함께 남긴다.

## 관점 (순서대로)

1. **불편함 검증.** 실제 불편에서 출발했나, 멋져 보여서인가. 대상 사용자가 정말 쓸까. 증거가 `[의견]`이나 `[가정]`뿐인가.
2. **범위 누수.** non-goals가 비었거나 물렁한가. appetite 안에 끝나는 크기인가. 아니면 어디서 잘라야 하나.
3. **모호한 성공 기준.** "좋아진다", "빠르게"처럼 관찰할 수 없는 기준을 전부 찾는다. 기준값과 실패선이 없는 행을 찾는다.
4. **빠진 상태.** 상태 8종(로딩, 첫 사용 빈 상태, 결과 없음, 복구 가능 오류, 복구 불가 오류, 부분 실패, 오프라인, 권한 없음)과 동시 편집, 시간대와 날짜 경계를 설계했나(풀, 위저드).
5. **검증 가능성.** 수용 기준마다 테스트 하나로 판정되나. EARS 문형인가. 한 문장에 요구가 여럿인가.
6. **추적.** 요구사항, 기능, 수용 기준, 성공 기준이 ID로 이어지나. 유저 플로우의 노드가 모두 기능에 연결되나.
7. **모순.** 문서 사이(10, 20, 30)나 문서 안에서 같은 것을 다르게 부르거나 서로 다르게 정한 곳이 있나.
8. **보안, 법, AI.** 인증, 결제, 개인정보, 외부 입력을 건드리면서 권한과 오류 기준이 없나. 있으면 계획에 `gotechy-security` 리뷰를 넣으라고 지적한다. 개인정보, 위치정보, 결제, 광고나 마케팅 메시지, AI 기능, 접근성 의무를 건드리는데 `gotechy-comply-kr`로 넘긴 기록이 없거나, LLM 기능인데 `gotechy-ai-eval`로 넘긴 기록이 없으면 지적한다.
9. **숨은 위험.** 이 스펙대로 만들었는데 실패한다면 가장 그럴듯한 원인 하나를 지목한다.

## 출력 형식

심각도 세 단계로 나누고, 지적마다 "왜 문제인가"와 "어떻게 고치나"를 한 쌍으로 쓴다.

| 심각도 | 뜻 | 처리 |
|---|---|---|
| 막음 | 이대로 만들면 틀린 것을 만들거나 판정할 수 없다 | 에이전트가 기각할 수 없다. 반영하거나 지적 원문 그대로 사용자에게 올린다 |
| 고침 | 품질이 bar 아래로 떨어진다 | 반영하거나 기각 이유를 리뷰 기록에 남긴다 |
| 제안 | 더 좋게 만들 수 있다 | 반영 여부만 기록한다 |

외부 리뷰어의 말은 이렇게 옮긴다. `spec-reviewer`의 진행 차단, 수정 권장, 제안은 막음, 고침, 제안이다. `security-auditor`의 즉시, 이번 주, 권장은 높음, 중간, 낮음이고, 보안 지적의 처리는 `gotechy-security` 스킬의 기준을 따른다. 옮긴 뒤에도 막음은 에이전트가 기각할 수 없다.

```markdown
## 리뷰 기록

### 2026-10-16 (서브에이전트 spec-reviewer)

- [막음] SC-1 실패선이 없다. 왜: 출시 뒤 실패를 판정할 수 없다. 고치는 법: "4주 뒤 10% 미만"처럼 숫자로. 처리: 반영
- [고침] F1-1에 IF THEN 기준이 없다. 왜: 푸시 실패 때 동작이 즉흥으로 정해진다. 고치는 법: 재시도 횟수와 기록을 AC로. 처리: 반영
- [제안] 보도자료 한 단락을 앞에 두면 가치 설명이 짧아진다. 처리: 기각(기능 단위라 과함)
- 실패한다면 가장 그럴듯한 원인: 알림 발송 비용 가정이 틀려 무료 플랜에서 막힌다.
```

지적이 없으면 없다고 쓰되, "실패한다면 가장 그럴듯한 원인"은 반드시 하나 쓴다.

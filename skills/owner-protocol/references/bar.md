# owner-protocol bar: 오너가 3분 안에 이해하고 결정하는 보고

이 bar가 지키는 것은 하나다. 오너가 HANDOFF 한 건만 읽고 무엇이 됐는지, 무엇을 정해야 하는지, 무엇을 믿으면 안 되는지 3분 안에 알고 결정한다. 일을 통째로 맡기면 맡긴 사람의 이해가 떨어진다는 실험 결과가 있어서, 이해를 돕는 장치(새 용어, 말해 보기, 사실 표시)를 보고 형식에 넣는다.

- Anthropic 실험에서 AI를 쓴 군의 이해도 퀴즈 평균은 50%, 직접 짠 군은 67%였다(17점 차이, p=0.01). 개념 질문만 하거나 코드와 설명을 함께 요청한 사람들은 65% 이상을 유지했다. 그래서 보고에 "새 용어"와 "말해 보기"를 둔다.
- 쉬운 글 지침은 독자를 먼저 정하고, 결론과 할 일을 앞에 두고, 전문어를 피하거나 풀라고 한다. 오너 보고의 순서(결정, 요약, 근거, 리스크)가 여기서 나온다.

## 측정형 체크리스트

| 번호 | 판정 | 항목 | 합격선 |
|---|---|---|---|
| O1 | [기계] | 8개 절이 계약 순서대로 있고 frontmatter가 스키마에 맞다 | 오류 0건. 도구: `gotechy handoff lint` |
| O2 | [기계] | 한 줄 요약 | 60자 이하 한 문장. 도구: `gotechy handoff lint`의 `handoff-summary` 규칙 |
| O3 | [기계] | 막는 결정과 기본값 결정 | 막는 결정 3개 이하. 선택지 2개 이상, 추천은 선택지 중 하나, 이유 한 줄. 막는 결정이 있으면 status는 `needs-decision`. 도구: `gotechy handoff lint`의 `handoff-decision-format`, `handoff-blocking-limit`, `handoff-blocking-status` 규칙 |
| O4 | [기계] | 한 일과 리스크 항목의 사실 표시 | 항목마다 `[확인]`, `[추론]`, `[추정]` 중 하나. 도구: `gotechy handoff lint`의 `handoff-fact-tag` 규칙 |
| O5 | [기계] | 증거 | `` `명령`: 결과 `` 형식만. 도구: `gotechy handoff lint`의 `handoff-evidence-format` 규칙 |
| O6 | [기계] | 리스크 절 | 3개 이하, 없으면 "없음". 도구: `gotechy handoff lint`의 `handoff-risk-limit` 규칙 |
| O7 | [기계] | 문체 | 화살표, em-dash, 가운데점, 이모지, 번역투, 상투어 0건. 도구: `gotechy text lint` |
| O8 | [사람] | 결정 필요에는 오너만 고를 수 있는 것만 둔다 | 워커나 리드가 근거로 정할 수 있는 항목 0건 |
| O9 | [사람] | `[확인]` 표시 | 표시한 항목마다 증거 절에 실제 실행한 명령이 있다 |
| O10 | [사람] | 새 용어 | 처음 쓰는 현업 용어마다 쉬운 설명 한 줄. 설명에 다른 전문어를 쓰지 않는다 |
| O11 | [사람] | 말해 보기 | 1~2문항. 외운 것이 아니라 결정의 결과나 이유를 묻는다 |
| O12 | [기계] | 교차 감사를 돌렸으면 근거가 확인된 지적 | 0건이거나, HANDOFF를 고치고 리스크 절에 올렸다. 도구: `gotechy audit` |

## 등급 판정

- A(최고 전문가): O1~O12 모두 통과. lint가 run과 커밋 단계에서 강제되고, 최근 4주에 HANDOFF 다시 쓰기(형식 오류)가 0건이다.
- B(출시 가능): O1~O12 모두 통과. 사람 항목(O8~O11) 일부는 리뷰 없이 작성자 판단이다.
- C(부채 있음): 미달 항목이 리스크 절이나 부채 목록에 적혀 있다.
- D(위험): 실행하지 않은 일에 `[확인]`을 붙였거나, 오너가 정해야 할 결정을 기본값으로 숨겼거나, 실패를 완료로 보고했다.

## 최고 전문가가 더 하는 것

- 결론과 결정을 맨 앞에 둔다. 오너가 첫 화면만 보고도 고를 수 있게 선택지마다 결과가 어떻게 달라지는지 이유 한 줄에 담는다.
- 숫자에는 비교 대상을 붙인다(전과 후, 목표와, 대안과). "빨라졌다" 대신 "12초에서 3초로"라고 쓴다.
- 확인한 것과 짐작한 것을 문장 단위로 나눈다. 모르는 것은 모른다고 쓴다.
- 되돌리기 어려운 결정은 그 사실을 질문에 밝힌다(설계, 데이터 구조, 보안, 외부 발행).
- 같은 개념은 끝까지 같은 낱말로 부른다. 오너가 쓰는 낱말을 따른다.
- 다음 단계는 오너가 할 일과 리드가 할 일을 나눠 한 줄씩 쓴다.

## 흔한 실패와 고치는 법

| 실패 | 고치는 법 |
|---|---|
| 한 일을 시간 순서 일기로 쓴다 | 결과 단위로 묶고, 결과마다 사실 표시를 붙인다 |
| 테스트를 돌리지 않고 "통과"라고 쓴다 | 실행한 명령과 출력만 증거에 쓰고, 못 돌린 것은 리스크 절에 적는다 |
| 결정 필요에 "괜찮을까요?" 같은 열린 질문만 둔다 | 선택지 2개 이상, 추천, 이유를 붙인다 |
| 리스크를 "없음"으로 비워 둔다 | 건너뛴 것과 확인 못 한 것부터 찾는다. 정말 없을 때만 "없음" |
| 전문어를 풀이 없이 쓴다 | 새 용어 절에 쉬운 설명을 남긴다 |
| 결정을 이미 내렸다고 쓰고 진행한다 | 확신이 없으면 막는 결정으로 올리고 status를 `needs-decision`으로 둔다 |
| 감사 지적을 숨기거나 반박만 한다 | 근거가 확인된 지적은 고치거나 리스크로 올린다 |
